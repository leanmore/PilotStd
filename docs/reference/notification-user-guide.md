# 通知系统说明

> **这份文档给谁看**：日常使用本系统的同事。全文不含代码，只讲"什么情况下会收到通知""通知长什么样""为什么有时合并成一条""想加一种新通知要动哪里"。
>
> **一句话概括**：系统在后台跑定时任务、扫描、下载、归档、检查标准时效性。每当这些事有了结果（成功、失败、或需要注意），它就会按你配置的渠道（微信 / 钉钉 / 飞书 / Telegram / 电脑桌面）给你发一条消息。

---

## 一、会发通知的事件清单

一共 **40 种**事件。按用途分成 **12 类**。下表"什么时候会收到"一列说的是实际情况。

### 1. 业务进展类（你最常收到的）

#### 时效性检查（6 种）
定期核对"这个标准还有效吗"。

| 事件 | 什么时候会收到 |
|---|---|
| 标准状态有变化 | 系统查到某个标准的状态变了（如"现行"变成"废止"，或"即将实施"变成"现行"） |
| 标准首次登记 | 某个标准第一次被系统记录并纳入跟踪 |
| 批量检查报告 | 一轮批量时效性检查跑完，有结果要汇报 |
| 轮次汇总报告 | 一整轮检查结束后的总账（检查了几个、变了几个、失败几个） |
| 单个标准检查失败 | 检查某个标准时出错（如来源打不开），只影响这一个 |
| 检查系统出错 | 整个时效性检查机制出了问题（不是单个标准） |

#### 扫描 / 导入（3 种）
把你放进"待处理目录"的文件收进系统。

| 事件 | 什么时候会收到 |
|---|---|
| 扫描完成 | 扫描目录跑完，有成功也有失败时（标题会写"有 N 个无法识别"） |
| 扫描结果为空 | 扫描跑完了，但目录里没有可收的文件 |
| 自动扫描失败 | 扫描过程整体失败（如目录不存在、没有权限） |

#### 查询（3 种）
系统去外部来源查标准信息。

| 事件 | 什么时候会收到 |
|---|---|
| 批量查询汇总 | 一批标准查询跑完（查出几个、没查到几个） |
| 查询失败 | 查询过程中出错 |
| 查询无结果 | 查询正常跑完但一条都没查到 |

#### 下载（2 种）
把标准文件下载到本地。

| 事件 | 什么时候会收到 |
|---|---|
| 批量下载完成 | 一批下载跑完（成功几个、失败几个、跳过几个） |
| 单个下载失败 | 某个标准下载失败（会写明标准号与失败原因） |

#### 收藏链（4 种）
"收藏"是你要系统去弄到手的标准。它有一整条处理链。

| 事件 | 什么时候会收到 |
|---|---|
| 已收藏 | 你新增了一个收藏（系统已记下） |
| 开始下载 | 某个收藏标准开始下载 |
| 下载完成 | 某个收藏标准下载好了 |
| **收藏已放弃（不会再自动重试）** | **系统重试多次仍失败，已彻底放弃这个标准。这条会写明放弃总数、原因分类，以及你该怎么做**（见下方说明） |

> **关于"已放弃"这条，你需要知道**：一旦进入"已放弃"，**系统永远不会再自动尝试**——它不像"下载失败"那样下一轮还会自动重试。
> 所以这条通知是**告终通知**，收到就说明需要你介入了。它会告诉你两件事：
> 1. **一共放弃了几个、分别是什么原因**（例如"版权受限"这类重试没用的，还是"网络超时"这类重试有用的）；
> 2. **建议怎么办**——如果原因是临时性的（网络、限流、已修复的系统缺陷），**重新收藏一次**通常就能成功；
>    如果是永久性的（版权受限、来源未收录），重试也没用，需要人工线下取件。

#### 规范化（2 种）

| 事件 | 什么时候会收到 |
|---|---|
| 规范化完成 | 文件名/编号整理（规范化）跑完 |
| 规范化失败 | 规范化过程出错 |

#### 归档（3 种）
把文件按分类放进规范的目录结构。

| 事件 | 什么时候会收到 |
|---|---|
| 归档完成 | 一批文件归档完毕 |
| 归档失败 | 归档过程出错（如目标目录只读、文件被占用） |
| 归档放弃 | 某个文件的归档链路彻底放弃（重试也过不去） |

#### 废止处理（2 种）

| 事件 | 什么时候会收到 |
|---|---|
| 废止标准已迁移 | 被判为废止的标准已挪到单独的位置 |
| 未找到替代标准 | 某个标准废止了，但系统没找到替代它的新标准 |

#### 公告抓取（4 种）
从公告来源抓取标准相关公告。

| 事件 | 什么时候会收到 |
|---|---|
| 公告抓取完成 | 一轮公告抓取跑完 |
| 公告核对完成 | 公告与本地标准的核对跑完 |
| 公告抓取失败 | 抓取公告时出错 |
| 公告抓取汇总 | 多个来源的抓取结果汇总成一条 |

### 2. 系统运维类（6 种）

| 事件 | 什么时候会收到 |
|---|---|
| 自动备份 | 定时备份跑完（成功或失败都会告知，含备份文件大小/路径） |
| 镜像有更新 | 检测到有新版本可用（顺便提示版本号与更新说明） |
| 后台任务出错 | 定时任务执行失败（含任务名与错误） |
| 工作进程出错 | 后台工作进程抛出异常（含错误与堆栈） |
| 查询配额已用尽 | 某个来源的每日查询次数用完了（含配额上限与重置时间） |
| 可信 IP 更新 | 企业微信可信 IP 列表发生变更 |

### 3. 提醒类（1 种）

| 事件 | 什么时候会收到 |
|---|---|
| 日期提醒 | 到了你设置的标准相关日期（如实施日、作废日临近） |

### 4. 安全告警类（4 种）—— 请务必留意

这四类**与普通通知不同**：它们**不参与合并、不受静默时段影响**，会**立刻**发出。
原因很直白——如果"通知渠道的凭证被人改了"这条消息被压后到 5 秒后甚至静默时段之后才发，
那它可能已经被发到**攻击者的新地址**上去了，等于没告警。

| 事件 | 什么时候会收到 |
|---|---|
| 通知渠道凭证被改 | 通知渠道的配置（地址、密钥等）被修改 |
| 账号密码被修改 | 有人修改了登录密码（会写明改完之后有没有踢掉已登录的会话） |
| 静态令牌被轮换 | 系统的静态访问令牌被刷新 |
| 登录失败告警 | 同一来源在短时间内连续多次登录失败（可能有人在试密码） |

## 二、一条通知长什么样（模板结构）

### 2.1 四个层次

每条通知由**四层**组成。不是每条通知都四层齐全——有几层就显示几层。

| 层 | 作用 | 举例 |
|---|---|---|
| **① 标题** | 一眼看出是什么事 | 「第 3 轮有效性汇总报告」 |
| **② 摘要** | 一句话说清关键数字 | 「轮次：3，检查总数：50，变更数：4，失败数：1」 |
| **③ 明细** | 具体是哪些条目（列表 / 字段对照 / 状态变化） | 「GB/T 1234-2020 现行 → 废止」 |
| **④ 操作** | 一个可以点进去看全部的链接 | 「查看完整列表」 |

标题旁边还有一个**颜色/级别**标记，用来传达紧急程度：

| 级别 | 含义 | 飞书卡片上的颜色 |
|---|---|---|
| 信息 | 正常完成，知道就行 | 蓝色 |
| 警告 | 完成了但有需要注意的地方（如"有 2 个失败"） | 橙色 |
| 错误 | 出问题了，需要处理 | 红色 |

### 2.2 一个具体例子

**事件**：轮次汇总报告（一整轮标准时效性检查结束后的总账）

**系统内部的数据**（这是"内容"，不是"排版"）：
- 标题层：第 3 轮有效性汇总报告
- 摘要层：轮次：3，检查总数：50，变更数：4，失败数：1
- 明细层（表格/列表）：GB/T 1234-2020 现行 → 废止；GB/T 5678-2021 现行 → 即将实施
- 级别：信息（蓝色）

**同一条内容，在不同渠道上实际长这样**（下面是系统真实渲染出来的，不是示意图）：

#### 微信 / 钉钉 / 飞书（群机器人文字消息）

```
## 第 3 轮有效性汇总报告

轮次：3，检查总数：50，变更数：4，失败数：1

**变更详情**（共 4 条）
- GB/T 1234-2020 现行 → 废止
- GB/T 5678-2021 现行 → 即将实施
```

（标题用大字，数字行是摘要，下面是带小圆点的明细列表。）

#### Telegram

```
*第 3 轮有效性汇总报告*

轮次：3，检查总数：50，变更数：4，失败数：1

📋 *变更详情*（共 4 条）
• GB/T 1234-2020 现行 → 废止
• GB/T 5678-2021 现行 → 即将实施
```

（标题加粗；列表前多一个 📋 小图标；标准号里的点号会被加反斜杠转义——这是 Telegram 的格式要求，肉眼看不出来。）

#### 飞书（卡片消息）

飞书收到的是一个**结构化卡片**：顶部蓝色标题栏写「第 3 轮有效性汇总报告」，下面依次是：
1. 一行文字：轮次：3，检查总数：50，变更数：4，失败数：1
2. 一行小标题：**变更详情**（共 4 条）
3. 一个**两列的表格**，每行一条变更：

| 详情 |
|---|
| GB/T 1234-2020 现行 → 废止 |
| GB/T 5678-2021 现行 → 即将实施 |

（飞书是唯一把明细渲染成**表格**的渠道；其它渠道是列表。）

#### 电脑桌面（右下角弹窗）

```
第 3 轮有效性汇总报告  轮次：3，检查总数：50，变更数：4，失败数：1  变更详情：GB/T 1234-2020 现行 → 废止 等 4 条
```

（桌面弹窗没有排版空间，系统会把四层**压成一行**：标题 + 摘要 + 明细的**第一条** + "等 N 条"。
明细**不会展开**——只取第一条给你一个预览。这样做是因为 Windows 桌面通知的正文有长度上限，
超过就会被系统截断；与其被系统随机截断，不如由系统自己取一小段有代表性的内容。）

### 2.3 带"字段对照"的例子（安全告警）

安全告警会多用一种**字段对照**的明细形式。以「登录失败告警」为例：

**微信 / 钉钉 / 飞书：**
```
## 登录失败告警

同一来源在 5 分钟内连续失败 5 次登录

**目标账号**：admin

**来源地址**：203.0.113.45

若非本人操作，请立即检查账号安全并考虑更换密码。
```

**Telegram：**
```
*登录失败告警*

同一来源在 5 分钟内连续失败 5 次登录

目标账号: admin

来源地址: 203.0.113.45

若非本人操作，请立即检查账号安全并考虑更换密码。
```

**桌面：**
```
登录失败告警 同一来源在 5 分钟内连续失败 5 次登录 目标账号: admin 来源地址: 203.0.113.45 ...
```

### 2.4 为什么各渠道长的不一样

因为**内容**和**排版**是分开做的：

- 系统只负责产出"**内容**"：标题、摘要、明细条目、级别、链接。它不关心你用什么渠道。
- 每个渠道有一个自己的"**翻译员**"，把同一份内容翻译成该渠道**能识别的格式**：
  - 微信/钉钉：Markdown（`##` 表示大字、`**` 表示加粗、`-` 表示列表）
  - 飞书：先试结构化卡片（表格、颜色栏）；不行才退化成 Markdown 文字
  - Telegram：它自己的 HTML 方言（`*加粗*` 加反斜杠转义）
  - 桌面：纯文本，压成一行

**好处**：加一个新渠道时，**40 种事件的文案一个字都不用改**——只要写一个新的"翻译员"。

## 三、什么情况下会合并成一条

系统**不会**每发生一件事就发一条消息，否则批量处理时会把你刷屏。

### 3.1 合并的规则

**分组依据**：**事件类型 + 关联对象**。

- 同一种事件、**同一个对象** → 合成一条；
- 同一种事件、**不同对象** → **不会**合并（各自成条）；
- 不同事件类型 → 永不合并。

举例：
- 10 个标准同时"状态变化" —— 每个标准是不同对象，会分成多组（但更常见的情形是同一批检查产出同一个汇总事件，见下）
- 同一批"扫描完成"的 3 次结果 → 合为一条

### 3.2 时间窗口

| 参数 | 默认值 | 含义 |
|---|---|---|
| **首次延时** | **5 秒** | 第一条消息到达后等 5 秒，把这段时间内的同类消息攒起来一起发 |
| **数量上限** | **50 条** | 攒满 50 条就**立刻发**，不等窗口结束 |
| **最长等待** | **5 分钟**（硬上界） | 无论攒了多少，从第一条起算超过 5 分钟**强制发出**，绝不无限等 |

**关键细节**：计时器**从第一条消息开始算，后续消息不会把它往后推**。
也就是说，持续不断有消息进来时，系统仍然每 5 秒发一次，而不会永远在等"下一波"。

### 3.3 什么时候实时发、什么时候合并发

| 情形 | 行为 |
|---|---|
| **安全告警**（改密、改通知凭证、轮换令牌、登录失败） | **立即发，不合并，也不受静默时段影响**（见 1.4 的理由） |
| 普通事件（业务进展、系统运维、提醒） | **合并发送**：等 5 秒 / 攒满 50 条 / 最多 5 分钟 |
| 你**关闭了聚合开关** | 所有普通事件改成**每条实时发**（安全告警本来就不合并） |

### 3.4 合并后的消息长什么样

- 保留**第一条消息的完整结构**作为骨架（标题、级别、明细的样式都沿用第一条）；
- 摘要里会写明**共 N 条**；
- 明细最多**逐条列出前 5 条**（每条只保留首行前 60 个字符，避免一条消息过长）；
- 超出部分不丢失——消息里有链接可以点进去看全部。

### 3.5 相关设置在哪里

在「设置 → 通知」里可以调整：

| 设置项 | 默认 | 说明 |
|---|---|---|
| 启用聚合 | 开 | 关掉就每条实时发 |
| 聚合窗口（秒） | 5 | 上面说的"首次延时" |
| 单批最大条数 | 50 | 上面说的"数量上限" |
| 静默时段 | **关** | 打开后，在指定时间段内**不打扰**你（默认 22:00–07:00）。注意：**安全告警不走静默时段** |
| 渠道 × 事件 订阅 | — | 可以精确指定"哪些事件发到哪个渠道"（例如只在钉钉收安全告警） |

## 四、模板的复用程度，以及新增一种通知要动哪里

### 4.1 复用了哪些东西

| 复用的部分 | 说明 |
|---|---|
| **四种内容块** | 所有通知都由这四种积木拼成：纯文本、字段对照（名称: 值）、状态变化（旧 → 新）、列表（标题 + 若干条目）。40 种事件都是这四种的组合，没有例外 |
| **三个级别** | 信息 / 警告 / 错误，所有事件共用 |
| **四种"翻译员"（渲染器）** | 四个渠道各一个。**事件增加时不需要改它们** |
| **一套文案字典** | 三语（简体 / 繁体 / 英文）各一份，按 `notification.<分类>.<事件>.<字段>` 命名。目前 **221 条**通知文案键，三语**数量一致** |
| **统一的发送流程** | 所有事件走同一条路：构建内容 → （可选）合并 → 按你的订阅规则选渠道 → 各渠道翻译并发送 → 记发送日志 |

### 4.2 你**不需要**动的地方（新增事件时）

- 不用碰四个渲染器（排版逻辑与事件无关）；
- 不用碰发送/重试/日志（流程是共用的）；
- 不用碰合并逻辑（分组和时间窗口是通用的）；
- 不用为每个渠道各写一份文案（文案只有一份，渠道差异由渲染器处理）。

### 4.3 新增一种通知，需要动 **9 处**（这是项目自身规定的准入清单）

> 说明：以下步骤是给开发者看的。列出来的目的是让你知道"**加一个通知并不只是加一句话**"，所以需要多久、容易漏什么。

| # | 要动的地方 | 做什么 | 漏了会怎样 |
|---|---|---|---|
| 1 | 事件登记表 | 登记新事件的名称 | 系统不认识这个事件 |
| 2 | 内容构建器 | 写"这个事件的消息由哪几块拼成" | 收到空通知 |
| 3 | 构建器注册 | 把新构建器接到事件名上 | 事件登记了但发不出内容 |
| 4 | **三语文案** | 简/繁/英各加一份文案，**且占位符必须一致** | 英文用户看到键名而不是文字 |
| 5 | 术语表登记 | 把文案里的固定说法登记进术语表 | 术语一致性检查会报错 |
| 6 | **默认渠道规则** | 指定这个事件默认发到哪个渠道 | **事件"注册了但发不出去"** ← 最容易漏的一步 |
| 7 | 端到端契约 | 在测试清单里登记事件名、触发它的代码文件、用到的字段 | 自动化检查会失败 |
| 8 | 安全类额外要求 | 若是安全事件，触发处必须写审计日志 | 安全类检查会失败 |
| 9 | 跑三项自动检查 | 覆盖度检查 / 术语检查 / 敏感端点审计 | 提交会被拦下 |

**特别提醒第 6 步**：前 8 步都做完，但如果没在第 6 步指定默认渠道，这个事件**在策略表为空时找不到任何收件渠道**，结果是"看着配好了，实际一条都发不出去"。

### 4.4 为什么合并机制不会"吃掉"重要通知

- 安全告警**设计上就绕开合并**（见 1.4）；
- 合并只在**同类型 + 同对象 + 5 秒内**发生，不会把"下载失败"和"归档完成"混成一条；
- 合并后的消息会写明**共 N 条**，不会让你以为只有一条；
- 超过 5 条时，消息里给链接，能点进去看全部。
