## 0. 先说数据局限（这决定了本文能回答到什么程度）

| 局限 | 说明 |
|---|---|
| **不是"有记录以来"** | 通知日志有**自动清理**（保留 **30 天**）。所以最早的记录是 2026-09-01，**更早的发送记录已经不存在了**。本文所有统计都只是"最近 32 天"，不是全部历史。 |
| **只有 1 个渠道** | 全部 1,148 条记录都是 **Telegram** 一个渠道。微信/钉钉/飞书的订阅清单是**空的**（见 3.4），所以它们一条都没发。 |

> **前 3 名占 85.7%**（489+427+68 = 984 / 1,148）。也就是说，**这 32 天的通知几乎全是"下载过程"的碎消息**（"开始下载"+"下载失败"），真正有信息量的汇总类通知很少。

**为什么"开始下载"会发 427 次**：每个标准每次尝试下载都会单独发一条"开始下载"。系统对失败的标准会自动重试最多 **7 次**（代码常量 `MAX_RETRIES = 7`），所以一个标准会产出"7 条开始下载 + 7 条下载失败" = **14 条**通知。

**实测印证**：
```
失败 7 次的标准: 67 个
失败 6 次的标准: 1 个
失败 14 次的标准: 1 个（两轮）
合计标准数: 69   合计失败通知: 489
```
且 `download_failed` 的发送时刻**高度集中在 04:00–04:05**（04:01 有 231 条）——那是每天凌晨的定时任务窗口，说明**这些是系统自动重试，不是用户手动操作**。

### 1.5 渠道发送失败/重试记录

**有失败记录，而且很严重。** 629 条失败的构成：

| 失败原因 | 条数 | 占比 |
|---|---:|---:|
| **Telegram 限流**（`HTTP 429 Too Many Requests`） | **599** | **95.2%** |
| 读取超时（`The read operation timed out`） | 19 | 3.0% |
| **消息格式错误**（`HTTP 400: can't parse entities: Character '\|' ...`） | **7** | 1.1% |
| 连接被重置 | 3 | 0.5% |
| SSL 握手失败 | 1 | 0.2% |

#### 1.5.1 限流细节：为什么重试也救不回来

系统**已经实现了重试**：Telegram 渠道最多尝试 **3 次**，退避 **2 秒 + 4 秒**（合计只等 6 秒），并把 429 判定为"可重试"。

**但 Telegram 在 429 响应里要求的等待时间是 `retry after 3 ~ 44 秒`**（实测 599 条全带此字段，最常见值是 36/34/32 秒）。**6 秒的退避远小于对方要求的 3–44 秒**，所以 3 次尝试全部撞上限流，最终记为失败。

**依据**：`pilotstd/core/notification/channels/telegram.py:23`（`_MAX_ATTEMPTS = 3`）、`:24`（`_RETRY_BACKOFF_SECONDS = (2, 4)`）、`:147`（`return False, e.code == 429 or e.code >= 500`）；实测 599 条 `error_msg` 含 `HTTP 429`，`retry after` 范围 3–44 秒。

#### 1.5.2 限流的时间线（为什么集中在某几天）

| 日期 | 尝试 | 成功 | 失败 |
|---|---:|---:|---:|
| 09-01 ~ 09-13 | 4~14/天 | 全部成功 | **0** |
| **09-14** | 133 | 108 | 25 |
| **09-15** | 133 | 43 | **90** |
| **09-16** | 133 | 48 | **85** |
| **09-17** | 133 | 43 | **90** |
| **09-18** | 132 | 49 | **83** |
| **09-19** | 133 | 39 | **94** |
| **09-20** | **201** | 50 | **151** |
| 09-21 ~ 09-30 | 4~17/天 | 基本全部成功 | 0~6 |
| 10-01 ~ 10-02 | 4~11/天 | 基本成功 | 0~1 |

**即：正常时每天只发 4 条（很轻）；09-14~09-20 突然涨到每天 133~201 条**，Telegram 直接限流，**那一周 60%~75% 的通知没送到**。

> 那一周正好是"收藏批量下载失败"集中发生的时期。**用户最需要被告知的时候，通知恰好送不到。**

#### 1.5.3 格式错误细节：一个事件**从未成功过**

**"新标准首次登记"** 发了 **7 次，全部失败**，原因完全一致：

```
HTTP 400: Bad Request: can't parse entities:
Character '|' is reserved and must be escaped with the preceding '\'
```

**原因**：该事件的明细用列表展示，列表的分隔符是竖线 `|`。Telegram 使用的格式（MarkdownV2）把 `|` 当作**保留字符**，必须在前面加反斜杠转义。Telegram 的渲染器**没有转义 `|`**，所以 Telegram 每次都拒绝这条消息。其它渠道（微信/钉钉/飞书）对 `|` 不敏感，所以只有 Telegram 受影响。

**发生时间**：2026-09-28（6 次）、2026-10-01（1 次）。**修复后需重新验证**。

### 1.6 关于"已读"字段：**不是问题，是设计使然**（原报告此处判断错误，已更正）

> **本节原先把"未读率 100%"当作一个问题。该判断是错的，现更正如下。**

**更正后的结论**：

1. **通知渠道不提供已读回传**。Telegram Bot API 不返回"用户是否已读"；微信/钉钉/飞书的机器人消息同样不回传。所以**系统在原理上无法知道用户是否看过通知**——这是平台能力限制，不是系统缺陷。
2. **通知日志页的定位是诊断工具**：用于排查"通知有没有发出去、发失败了什么原因"，**不是让用户阅读通知的地方**。在这个页面上放"已读/未读"会给人一个**错误的暗示**——好像系统知道用户读没读。
3. **数据库的 `is_read` 字段仅仅表示"用户在 Web 界面点过『标记已读』"**（`POST /api/notification/read`），**与通知是否送达、是否被看过无关**。
4. **本次已移除该页的"已读"显示、筛选与相关操作**（数据库字段保留，不迁移）。字段的真实用途只剩一处：顶部**通知铃铛**（`NotificationBell.vue`）的未读角标与"全部标记已读"——那是用户自己的**收件箱**语义，成立且保留。

**因此**：
- 本报告**不再以"未读率"作为任何指标**；
- 原"需你确认：通知页你看过吗"这一问**已作废**（问的是不存在的信息）；
- 关于"用户是否知道下载失败了"，只能从**其他证据**推断（例如收藏页有 99 条一直未下载、上一份诊断报告实测的重试次数），**不能用已读率推断**。

**依据**：部署实例 `/api/notification/logs` 返回 10 个字段且含 `is_read`（值全为 0），但该字段**无渠道回传来源**；`docker/api/notification.py:386-403` 的标记接口只写"用户点过"；前端消费方核实见下节"移除内容清单"。

### 2.1 本节最重要的一条

**用户遇到的"没下载"，系统其实"想通知"——但通知在关键时刻送不到。**

三组数字放在一起看：

| 事实 | 数字 |
|---|---|
| 进入"放弃"终态的收藏 | **99 条** |
| 其中因 `'super'` 缺陷被永久冻结、`last_attempt` 全为 2026-09-20 的 | **61 条** |
| 那一周（09-14~09-20）通知发送**失败**的条数 | **599 条（占全部失败的 95%）** |

**即**：系统在 09-14~09-20 期间**确实在尽力通知**（每天尝试 133~201 次），**但被 Telegram 限流挡掉了大部分**；而同一时期正是下载集中失败、61 条收藏被永久冻结的窗口。

**后果**：用户既没收到"下载失败"的告警，也没收到"已放弃，不会再试"的告终提醒，直到自己去收藏页看到 99 条一直没下载。

## 3. Task 3：缺口与冗余分析

### 3.1 缺失（用户实际遇到、需要知道，但没有通知）

| # | 缺失项 | 判定依据 | 严重度 |
|---|---|---|---|
| M1 | **"已放弃、不会再自动重试"这件事没有独立、显眼的告终通知** | 收藏进入 `abandoned` 是**终态**——系统**永远不会再试**（调度只捡 `pending`/`failed`）。虽然 `archive_abandoned` 事件存在，但它**只在"归档链路放弃"时发**；对于"下载阶段就失败 7 次"的标准，用户收到的是 7 条零散的"下载失败"，**没有一条明确说"这个标准已经放弃了，需要你介入"** | **高** |
