# A-21 第三步方案：事件路径上下文与系统任务归属

> 状态：**方案（未写代码）**。MoviePilot 调研结论见 `docs/research/2026-11-01-moviepilot-notification-design.md`。

## 1. 核心数据结构

```python
@dataclass(frozen=True)
class NotificationContext:
    scope: Literal["user", "admin", "system"]
    user_id: int | None = None      # scope="user" 时必填
```

规则：

- `scope="user"` → `user_id` 必填（真实用户）；
- `scope="admin"` → `user_id` 可为 None（管理员范围，落库 0？不，见下）；
- `scope="system"` → `user_id=None`，落库 **0**（系统任务）。

**落库规则**：`user_id = context.user_id if context.user_id is not None else 0`，禁止 `or 1`。
`users` 表不建 id=0 的行；所有用户列表查询 `WHERE id > 0`。

`send_event` 签名（向后兼容）：

```python
def send_event(self, event_type, event_data=None, *,
               context: NotificationContext | None = None, ...):
    context = context or NotificationContext(scope="system")
```

旧调用不传 → system（0），不再读 `self._user_id`。

## 3. 线程上下文贯穿（A-35 解法）

- 不在 manager 上设置可变 `_user_id`；
- `_dispatcher.send_event(host, ..., context)`：
  - `policy.get_channels_for_event(effective_user_id)`：user 用 `context.user_id`；system/admin 用 `None`（按默认策略）；
  - 渠道凭据读取：user 用该用户 `user_credentials`；system 用全局/管理员配置（现有 `_user_id` 绑定需改为参数）；
  - `_log(..., user_id=resolved)`：写 0/真实用户；
  - 按钮 token owner：`resolved_user_id`；
- **聚合器**：入队 key 增加 user_id（不同用户同事件不得合并）；
- **静音队列**：`enqueue(..., user_id=resolved)` 已有列；
- 事件处理全程不读 `host._user_id`。

## 4. release_suppressed 定位修正

它不是“系统任务”，是**用户静音消息的补发**。

现状：`release()` 一次取所有 suppressed 行，不按用户。
改法：

- 队列表已有 `user_id`；
- manager 的 `release_suppressed_notifications`：
  1. `expire()`（全量过期，系统关也执行）；
  2. 若系统关 → return；
  3. 查 `SELECT DISTINCT user_id FROM notification_queue WHERE status='suppressed' AND scheduled_time<=now`；
  4. 逐 user 调 `queue.release(user_id=uid)`，单用户失败只记该用户；
- `queue.release(user_id)` 的 SQL 增加 `AND user_id=?`；
- 补发时 `_send_now` 的 user 来源就是队列行的 user_id；
- 系统任务（0）的静音消息正常按 0 补发（管理员可见）。

## 5. 系统汇总的 scope

`batch_summary`、`daily`、备份、校验汇总 → **system（0）**，理由：

- 普通用户不应看到“全系统汇总”；
- 管理员 `all=true` 能看到 0 的记录；
- 不归到某个管理员 id，避免管理员换人后历史归属错。

## 6. get_logs 查询确认

现有 API：

- 普通用户：`user_id=current_user` → `WHERE user_id=?`，**看不到 0**；
- admin `all=true`：`user_id=None` → 不加过滤，**自然包含 0**；
- admin 不传：只看自己（不是 0）。

SQL 已天然满足，无需改。

## 8. 分阶段实施

1. **3a 数据结构与写路径**：`NotificationContext`、`send_event` 接收并解析、`_log/_send_now/enqueue` 传 user_id、system=0；现有调用默认 system（不传 context）。
2. **3b 用户入口接线**：API/CLI 的 scan/query/download/organize/auto/favorites 传 `context=user(current)`；engine/services 接收 context；favorites 事件改成 user。
3. **3c 补发与聚合**：release 按 user、聚合 key 加 user_id。
4. **3d 测试与全量**：上表 8 类；然后回家部署验证。

## 9. 风险与边界

- 现有调用不传 context 会从“按 manager._user_id（1）”变为 system(0)：**单用户日志归属会变**，这是预期；A-40 旧数据不回溯。
- 渠道凭据读取改为显式 user_id，需确认 system 路径用哪个配置（建议全局/管理员），否则系统通知可能发不出。
- 聚合 key 变更会影响既有聚合行为，需回归 `aggregate_buffer` 测试。
- 不在本阶段做：MoviePilot 式 targets 多账号、广播、未绑定跳过（渠道回退保持现状，记 A-21 后续）。

## 10. 3a 前确认（2026-11-01 实测）

### 10.1 admin scope 落库

已改为：admin 必须传真实管理员 user_id，落库真实 id；system 才写 0。三层可区分：
user=普通用户、admin=管理员手动、system=系统自动。

### 10.2 渠道凭据现状（关键）

- 渠道实例在 NotificationManager._init_channels() 时按 self._user_id 从 user_credentials 一次性构造；
- _dispatcher 发送时只使用已初始化的 host._channels，**不在每次发送时读凭据**；
- 因此 3a 把日志归属改成 0，**不会影响渠道凭据/发送**（仍用 manager 构造时的渠道实例）；
- 真正的“按用户凭据投递”需 3b：按 user 重建/缓存渠道实例，system 用全局/管理员配置；
  **3a 不改凭据路径，避免系统通知发不出**。

### 10.3 3b 拆分

- **3b-1**：API 入口（favorites/scan/query/download/organize/auto）构造 context=user(current_user) 传给 facade；
- **3b-2**：facade → engine/services 贯穿 context（每模块单独改+测）；
- **3b-3**：后台任务（favorite_download/date_reminder/favorite_chain_processor）的 context 来源：
  当前 	ask_queue **没有 owner 字段**；建议新增 	ask_queue.user_id（v72，默认 0），
  创建任务时写入，执行时读出构造 context。**本轮不实施**，先确认 v72 方案。

### 10.4 3a 中间状态声明

3a 完成后、3b 接线前：

- 未接线的调用全部落 user_id=0；
- 用户登录“我的历史” WHERE user_id=1 **看不到新日志**；
- 管理员 ll=true 能看到全部（含 0）；
- 不丢数据、不串号，但用户视角“新通知在列表里看不到”——这是预期中间态，部署/验收时必须说明。
