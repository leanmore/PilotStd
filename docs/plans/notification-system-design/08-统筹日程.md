> **本文件的用途**：把"通知系统还有哪些没做完"变成一张**可执行、可勾销**的单子，并按统筹法（华罗庚《统筹方法平话》）

> **用法（重要）**：每完成一项，就在【三、待办清单】对应行的**状态列**把 `☐` 改成 `✅`，并写上**提交 hash**；

> **维护纪律**：改代码就同步本文；本文只写**事实 + 日程**，不写"建议/应当"这类判断词（与本簿风格一致）。

## 一、统筹法的三个落点（本项目的实际含义）

| 统筹法要点 | 原文寓意 | 本项目的落点 |
|---|---|---|
| **① 抓主要矛盾（关键路径）** | "泡茶"先烧水——水不开，别的都白等 | 通知系统剩余工作里，**只有一条真正的串行长链**：`聚合键灰度开关 → 阶段 2（任务视角三模块）→ 阶段 4（事件模型重构）`。这条链上的每一步都改变**数据/契约语义**，必须先做前一步 |
| **② 能并行的务必并行** | 烧水的同时洗茶壶、洗茶杯 | **三渠道分段接入**、**失败明细读侧**、**阶段 3 补取证** 三条支路**不依赖**关键路径，可与它同时推进（各自独立提交、独立回滚） |
| **③ 压缩工序衔接的固定开销** | 减少等水开的空转 | 本仓每批都有**固定开销**：`ruff`＋快闸（23～25 项）＋`mypy` 全量＋G-031 文档同步＋契约测试。⇒ **同主题合批**（如"分段 + 读侧"若同窗可一并做）比拆成多批更省；但**语义不同的必须拆**（回滚粒度优先） |

### 1.1 本项目的"硬约束"（比工期更硬的边界，任何排程都不能违反）
1. **契约同批**：`payload_keys` 声明与生产者采集**必须同批落地**，否则 `tests/test_notification_e2e.py` 必红（G-045 双向契约）；
2. **文档同批**：改 `pilotstd/manager/` ⇒ 同批 `docs/architecture/modules/manager.md`；`pilotstd/core/` ⇒ `core.md`；`pilotstd/download/` ⇒ `docs/reference/download-pipeline.md`（G-031，**以门禁原文为准**）；
3. **窗口机制不动**：`aggregate_buffer` 的 `_timers` / `_window_start` / `_buffers` 结构不得改（键分层只能改 `_group_key` 与还原辅助）；
4. **红灯不提交**：任一门禁/测试红 ⇒ 先修绿再提交（这也是每批的固定开销之一）。

## 二、依赖图与关键路径（实测得出，非设想）

```
                        ┌──────────────────────── 关键路径（串行、不可并行） ────────────────────────┐
                        │                                                                              │
 [P1] 聚合键灰度开关 ──▶ [P4a] 阶段2 前置确认（只读） ──▶ [P4b] 阶段2 三模块 ──▶ [P6] 阶段4 原子批次
   (无前置，可立即做)        (依赖 P1 的键语义稳定)        (依赖 P4a 清单定稿)      (依赖 P4b 的数据结构)
                        │                                                                              │
                        └──────────────────────────────────────────────────────────────────────────────┘

 并行支路（不占关键路径、互不依赖）：
   [P2] 三渠道分段接入        ← 独立（只动 channels/* 与 renderer；已有 TG 先例）
   [P3] 失败明细读侧          ← 独立（只动 API/前端；落库列 v67 已就绪）
   [P5] 阶段3 补取证（只读）  ← 独立（钉钉更新接口 / 企微缺口）

 触发式支路（不排期，条件出现才做）：
   [P7] T-40 部署补测 ｜ #33/T-21/T-31/T-36/T-38/T-35 ｜ C-14b ｜ C-09 ｜ 遗留②（可选）
```

**为什么 P1 是关键路径的头**：本次改造把聚合键改成"①批次×收敛类／②日常桶"并**默认生效**，但**没有灰度开关**
（全库 `git grep NOTIFY_AGG_KEY` 零命中）。⇒ 这是"已改行为、无退路"的缺口；同时它决定 P4/P6 的键语义基线
（阶段 4 的"事件模型重构"也要在同一个键体系下做），所以它必须最先。

**为什么 P6 是瓶颈**：阶段 4 是**原子批次**（`notification_policy` 语义切换＋数值迁移＋前端双层配置＋
G-044/G-045/G-046 重设计＋`desktop_toast` 登记），要么整批成功要么整批回退 ⇒ 必须占**独立窗口**，
不能与其他批次并行（避免红灯互相掩盖）。

**排程原则（与统筹法一致）**：
- **关键路径优先**：第 1 批必须是 P1（它是 P4/P6 的语义基线）；

- **瓶颈不并行**：P6 占独立窗口，避免与其他批次的红灯互相掩盖。
