## 摘要（决策者读）

**A. 本轮裁决录入（6 项，§一）**
1. **`_enabled` 解耦**：【裁决】关闭推送后**仍写数据库日志**（Web 可查历史），只是不推送。
2. **用户时刻清单做第二 SSOT**：【裁决】进入代码，41 事件必须映射到它，**有断言校验**。
3. **分档策略由 Harness 拟初版**：见 §三（阈值基于**实测耗时**）。
4. **渠道双向范围 = 所有支持双向的渠道**：【裁决】不止 Telegram，**基础先行、按需启用**。
5. **两处更正**（企微可交互、消息编辑非进度用途）：见 §二，**阶段 3 定义随之重写**。
6. 其余 7 项原待裁决留到实施设计时逐个处理。

**B. 分档策略初版（§三，**核心实测**）**
- 实测三类样本：**一键管道 21 项 = 168 秒**；**单次适配器查询 0.10–2.71 秒（中位 1.61 s）**；**公告全量抓取单源 3–5 分钟、三源首末跨度 8 分钟**。
- **短/长阈值建议 = 30 秒**：依据是**桌面端既有熔断窗口恰为"30 秒内 3 条"**——30 秒既是用户感知分界，也是系统已有常量。
- **长阶段定期建议 = 60 秒**（或"每 25% 且间隔 ≥60 秒"取先到者）：**必须 >30 秒熔断窗口**，否则进度通知会自己触发熔断暂停。
- **终局 = 覆盖本次用户动作的全部阶段**（实测管道正好 5 阶段）。
- **警告 = 立即发送（绕过聚合）+ 5 秒滚动窗口同类合并**（沿用既有 `aggregate_window_seconds=5`）。
- 36 个 Docker 时刻分档：**短 18 / 长 5 / 纯警告 13**（+ 候选时刻 1）。

**C. 框架更新的核心变更点**
- **阶段 3 从"收缩为 URL 按钮"改为"分渠道升级形态 + 低频编辑 + 回调"**（§二）。
- 新增 **阶段 S（形态升级）**，置于交互阶段之前——**形态是交互的前置，不是交互的内容**。
- 新增 **5 个待裁决点**（§五），其中最紧要的是：**警告档与静默时段冲突**（现有实现在静默期会把警告也延后入队）。

## 二、两处更正（含阶段 3 重定义）

### 2.1 更正 1：企微**支持**交互（原判断作废）

| 项 | 原判断（作废） | 更正后 |
|---|---|---|
| 形态 | "企业微信群机器人"（不支持交互） | 企微**有两种形态**：**群机器人**（低端，不支持交互）与**企业自建应用**（支持菜单/按钮/回调） |
| 结论 | "企微归入做不到一类" | **四个渠道都有支持交互的形态**：钉钉=企业内部应用机器人、企微=企业自建应用、飞书=企业自建应用、Telegram=Bot API |
| 正确表述 | — | "**当前部署形态都做不到，升级后都能做到**"（现状对照见 [01](01-channel-capabilities.md) §四） |

**证据强度提示**（[01](01-channel-capabilities.md) §五 缺口 1–4）：企微的**交互卡片与回调**本轮只有官方 URL（正文为 JS 渲染未取到）+【裁定】；**飞书**有 MP 自建应用代码实证；**钉钉**有官方互动卡片文档全文；**Telegram** 最完整。→ 形态升级的**可行性评估需按渠道分别补证**。

### 2.2 更正 2：消息编辑的用途**不是**进度原地更新

| 项 | 原判断（作废） | 更正后 |
|---|---|---|
| 用途 | 进度原地更新（30% → 60%） | **状态变更 / 动作回执 / 汇总更新** 三类 |
| 频率 | 隐含高频 | **低频**（一条消息整个生命周期编辑几次） |
| 技术难度 | 高（需高频编辑 + 限流规避） | **显著降低** |
| 进度展示 | 原地更新 | **改由"再发一条新消息"承担** |

**更正后的编辑用途表**（决策者原话的落地口径）：

| 用途 | 例子 | 频率 | 触发者 |
|---|---|---|---|
| 状态变更 | "任务受理" → "任务完成"（同一条消息） | 每任务 1–2 次 | 系统 |
| 动作回执 | 用户点"重试" → 消息改为"已触发重试" | 每次用户动作 1 次 | 用户 |
| 汇总更新 | 聚合消息"3 条失败" → "2 条失败" | 每次状态变化 1 次 | 系统 |

### 2.3 阶段 3 重定义（替换 00-framework §2.3 的"大幅收缩"）

| 项 | 原定义（作废） | **新定义** |
|---|---|---|
| 范围 | 收缩为"URL 按钮 + 能力缺失降级文本"，**不做回调、不做编辑** | **分渠道升级部署形态 + 低频编辑 + 回调**；基础先行、按需启用 |
| 前置 | 无 | **新增阶段 S（形态升级）**：凭证模型随之变更（四渠道各自的企业级形态） |
| 编辑能力 | 不做 | **做**，但限定为 §2.2 的三类低频用途；**进度不入编辑** |
| 回调能力 | 不做（因"渠道做不到"） | **做**（更正 1 后前提成立）；按渠道能力矩阵逐个启用 |
| 渠道顺序 | 先 Telegram 验证闭环，再做飞书 | **基础先行**：先做渠道无关的公共能力（改写句柄抽象、回调端点骨架、验签骨架），**再按渠道启用**（TG 形态已就绪可首启；钉钉需卡片更新路径补证；企微需能力补证） |
| 锚点抽象 | 假设统一 `message_id` | **按渠道分别提供"改写句柄"**：[01](01-channel-capabilities.md) §四 已证明四家锚点不同（飞书/TG=`message_id`；钉钉=`outTrackId`；企微=[未找到]） |
| 保留项 | — | 原 Q5 裁决（交互按钮**默认只读**、需显式开启"允许远程操作"）与原 Q7/Q8（动作权限重新鉴权、破坏性动作二次确认）**继续有效** |

### 3.2 四档规则与阈值建议

| 档 | 决策者原话 | 判定条件（**建议**） | 通知时机（**建议**） | 依据 |
|---|---|---|---|---|
| **短阶段** | 等完成再通知 | 预计耗时 **≤ 30 秒** | 完成时**一条**（含结果摘要） | 实测最小操作 ≈1.6 s；30 s 内用户通常在场 |
| **长阶段** | 定期或定进度通知 | 预计耗时 **> 30 秒** | **每 60 秒** 或 **每 25% 且间隔 ≥60 秒**（取先到者）**再发一条新消息** | **必须 > 桌面熔断的"30 秒内 3 条"窗口**，否则进度通知自己触发熔断暂停（5 分钟） |
| **终局** | 汇总全过程 | 本次**用户动作**所属流水线结束 | 流水线结束时**一条汇总**（覆盖全部阶段） | 实测一键管道正好 **5 个阶段/168 秒**；用户关心的是"这一键跑完没" |
| **警告** | 第一时间通知 + 聚合 | 任何失败/需人处置/安全类时刻 | **立即发射**（绕过聚合缓冲）+ **5 秒滚动窗口**内同类合并 | 沿用既有 `aggregate_window_seconds=5`；bypass 机制已存在 |

**阈值 30 秒的三重依据**：① 实测把"秒级操作"（查询 1.6 s）与"分钟级阶段"（公告 3–5 min、管道 2.8 min）分开；② **桌面端既有常量恰为 30 秒**（30 秒内 3 条警告/错误 → 暂停 5 分钟），复用同一分界便于解释与测试；③ 30 秒是"用户在桌前"的经验边界。

**"定期"取 60 秒的理由**：现有桌面熔断窗口是 30 秒内 3 条 → 若按 30 秒发进度，**3 条/90 秒**虽未越界但余量过小；60 秒给出 2× 安全边界，且与 5 秒聚合窗口不存在共振。

### 3.4 七个必答问题的结论汇总

| # | 问题 | 结论 |
|---|---|---|
| 1 | "短"与"长"的阈值 | **30 秒**（三重依据见 §3.2） |
| 2 | 长阶段"定期"多久 | **60 秒**，或 **每 25% 且间隔 ≥60 秒**取先到者 |
| 3 | 长阶段进度的聚合规则 | **按 `task_kind` + 同一运行合并为一条**；**只保留最新进度**（不累积 30/60/90 三条）；发送方式 = **再发新消息**（决策者已裁决不做原地更新） |
| 4 | 终局汇总的粒度 | **覆盖本次用户动作的全部阶段**（整条流水线），而非单个阶段 |
| 5 | 警告的聚合规则 | **立即发射（bypass）+ 5 秒滚动窗口同类合并**；聚合**不延迟**首发 |
| 6 | 分档如何与用户时刻对应 | §3.3 对照表（过程档 + 终局 + 警告三个维度） |
| 7 | 判定依据在何处 | **静态声明为主**（写进"用户时刻清单"的默认档，可供门禁校验）**+ 运行期只允许升档、不允许降档**；理由：实测同类操作规模差异大（查询 3 条 vs 大批），静态保证可测可审，动态兜底"声明短但实际长" |

### 4.1 Docker 端

| 序 | 阶段 | 目标 | 验收标准 | 回滚 | 变更说明 |

| **D** | 可见性解耦【裁决 1 落地】 | 关闭推送仍写库日志、Web 可查 | 关闭投递时 `notification_log` 仍落库、Web 历史可见 | 环境开关回退 | 由"建议"升级为**已裁决** |

### 4.2 Windows 端

| 序 | 阶段 | 目标 | 验收标准 | 回滚 | 变更说明 |
|---|---|---|---|---|---|
| **W1** | 任务中心改造 | 行单位 = 一次用户操作；用户语言；清除语义修正 | 真实操作一轮可读、清除语义正确 | 纯 UI 回退 | 不变 |

### 4.3 依赖与顺序

- **新增依赖**：**S 必须先于 B**（形态不具备则回调与编辑无法落地）。
- **保留依赖**：**W2 先于 C**（C 要按端重排清单）；**D 最先做**（改变后续阶段的验证口径）。
- **建议顺序**：Docker `D → S → A → B → C+E`；Windows `W1 → W2 → W3`（与 Docker 并行）。
- **通道并行性**：S 阶段**按渠道可独立推进**（TG 形态已就绪可首启；钉钉/企微需先补能力证据，见 [01](01-channel-capabilities.md) §五）。
