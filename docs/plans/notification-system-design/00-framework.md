## 摘要（决策者读）

1. **Docker 端要发的用户时刻 = 36 条**（03 报告 37 条中剔除 1 条 Windows 专属）。承载它们的是 Docker 侧 40 个事件的 **25 个**；另有 **5 重复 / 7 粒度错配 / 3 多余**，以及 **1 个时刻完全无事件**（待确认项）。
2. **不新增"通知系统"这一层**：Docker 端沿用现有链路，Windows 端改造任务中心——两端**各自解决自己的用户时刻**。
3. **7 类通知事件保留**（原 Q1 裁决"双层"不变），但**新增"用户时刻清单"作为第二 SSOT**——这是消除"加事件成本高"病根的唯一位置（现在 4 份清单没有一份以用户视角校验）。
4. **13 个新字段全部保留**，但按端明确用途：Docker 用 9 个（投递/聚合/交互）、Windows 用 3 个（任务/进度）、保留不消费 1 个（`attachments`）。
5. **阶段 2.5b 建议降级**：只做 `notify_event × target_id` 二元切换；`correlation_id` 至今恒空，三元会退化。
6. **阶段 3 建议大幅收缩**：4 渠道实测**都拿不到消息 ID**、飞书仅 URL 按钮 → 消息编辑与回调的**前置条件不成立**；建议只保留"URL 按钮 + 降级文本"。
7. **阶段 4 保留但改输入源**：`assert len(EVENTS)==41` 必须拆（这是"加事件成本高"的直接病灶），输入源从单一 `ALL_EVENTS` 改为 **`用户时刻清单 × ALL_EVENTS` 双向闭包**。
8. **Windows 端目标形态**：任务中心从"任务队列表"改为**"我做过的/在跑的事"**——一行 = 一次用户操作，显示业务名与结果摘要，而非 task_id/task_type。
9. **三个技术发现各有唯一合理处置**：清除语义改为真删；`_enabled` 解耦为"投递"与"记录"两件事；共享事件**按端分流**（Windows→托盘）而非切断。
10. **MoviePilot 学 6 条 / 不学 6 条 / 避免 6 条**（§五）。
11. **实施路径**：Docker 5 阶段（D→A→B→C+E）、Windows 2 阶段（W1→W2）；**唯一顺序约束**：W2 必须先于 C。
12. **待裁决 11 项**（§七），每项含备选与建议。

### 1.4 【本轮新增判断】流程编排级错配（1 处）

`POST /api/auto`（`docker/api/auto.py:11-16`）一次用户动作 = "一键处理：扫描→查询→下载→归档"（`mgr.auto_run()`），但**四个阶段各自发通知**（`scan_complete` → `batch_query_summary` → `batch_download_complete` → `archive_complete`，均为 Docker 侧事件）。
用户视角：**这是 1 个时刻**（"我提交的一键处理跑完了"），却收到 4 条。
差异性质：不是"某事件多余"，而是**事件编排缺一层"管道级汇总"** → 建议在方案阶段决定"是否需要一个管道级时刻"（§七 待裁决 11）。

## 三、Windows 端方案方向（Q3）

### 3.1 目标形态（用户视角）

**改造后的任务中心 = "我做过的 / 正在做的事"清单**，一行 = **一次用户操作**（不是 task_id），显示：**我在做什么**（业务名）→ **现在怎么样**（进行中/完成/失败/已放弃）→ **结果摘要**（成功 N / 失败 M）→ **时间**。
它**不是通知中心**：没有事件名、没有级别、没有渠道、没有"已读"。

### 3.2 【本轮新增判断】数据源现实：两端各有历史表，互不写

| 端 | 历史数据源 | 谁写 | 谁读 |
|---|---|---|---|
| **Windows** | `task_queue` | 桌面 `_register_task`（`pilotstd/ui/main_window/parts/_dialog_ops.py:107-121`） | 桌面任务中心（`pilotstd/ui/pages/task_page.py:94`） |
| **Docker** | **`pipeline_runs`**（另有 `task_queue`） | **仅 `docker/api/*`**（scan/query/download/normalize/archive） | Web `TaskManager.vue` / `TaskView.vue`；`docker/api/tasks.py:154` |

**实测**：`pilotstd/ui/**` 对 `pipeline_store`/`PipelineRun` **零引用**。
**含义**：① 桌面端历史只能来自 `task_queue`，**不能复用 Docker 的管道视图**；② Docker 端的"回看"需求**已由 Web 的任务/管道视图满足** → 进一步削弱"通知历史"的必要性。

### 3.3 具体改造点（现状 → 目标）

| 维度 | 现状（实测） | 目标 | 依据 |
|---|---|---|---|
| 行单位 | `task_id`（UUID） | **一次用户操作**（业务名 + 时间 + 结果） | 用户看不懂 UUID |
| 类型列 | `task_type`（5 值：scan/query/download/organize/**expire**，`pilotstd/task/models.py:8-15`） | **业务名**（且需覆盖 desktop 只映射 4 类的事实——`_dialog_ops.py:112-117` 无 expire） | 用户语言 |
| 状态列 | 6 值枚举（pending/running/paused/completed/failed/cancelled） | **用户语言 4 态**：进行中 / 已完成 / 失败 / 已放弃 | 减少术语 |
| 错误列 | `error_log` 原文 | **"需要我做什么"** 的一句话 + 明细可展开 | 03 报告 §二：用户要的是"要不要我动手" |
| 结果摘要 | 仅进度 `completed/total` | 追加**"成功 N / 失败 M / 跳过 K"** | 03 报告 #7/#12 时刻 |
| 刷新 | 手动（`task_page.py:46-47`） | 保持手动或跟随任务结束事件刷新 | 用户在桌前，无需轮询 |

### 3.4 托盘气泡 / 历史回看 / 已读未读 / 进度呈现

| 项 | 判断 | 理由 |
|---|---|---|
| **托盘气泡机制** | **保留** | 【已有结论】双端 01 §2.4：已建成"3 秒同标题去重 + 主题分组 + 30 秒 3 条熔断暂停"（`pilotstd/platform/notify.py:93-111`）；它是**离席场景的唯一通道**（长任务） |
| **历史回看** | **需要，但由任务中心承担**；不引入"通知历史" | 【本轮新增判断】通知是瞬时的（气泡 3 秒即过），有价值回看的是"我做过什么、结果如何"——这正是任务中心；引入第二套历史会与 `task_queue` 语义重叠 |
| **通知 vs 任务记录的分界** | 通知 = **瞬时、不落库、不可回看**；任务记录 = **持久、可回看、以用户操作为单位** | 【本轮新增判断】据此，"桌面端要不要写通知日志"的问题变为"不需要" |
| **已读/未读** | **不引入** | 【本轮新增判断】用户在桌前，气泡瞬时可见；任务中心是操作历史而非消息流。若未来有"未查看的结果"，用**高亮新完成项**即可，不需要"已读"状态机 |
| **进度呈现** | **够用**（统一管道 + 缓动 + 阶段信号） | 【已有结论】双端 01 §2.2：`unified_progress` + `progress_changed`/`status_changed` + 各 Worker 的 `batch_ready`/`stage_changed` 已覆盖"进行中" |

### 3.5 共享事件空转（15 个）—— **按端分流**（不切断）

| 选项 | 评价 |
|---|---|
| 切断（Windows 端删掉 `send_event` 调用） | ❌ 会丢失"将来打开推送即可用"的能力；且切断后事件在**两端都不产生**，`notification_log` 的审计轨迹断裂 |
| 保留现状（空转，只留一行 debug） | ⚠️ 可接受但语义糊涂：代码看起来在发通知，实际什么也没发生 |
| **按端分流（Windows→托盘气泡；Docker→渠道）** | ✅ **建议**：【本轮新增判断】桌面端**已经有** `NotifyService`（托盘）这套实现，场景真实（长任务离席），且分流点是单一门面——把"事件 → 用户可见信号"的表达按端落地，而不是让 15 个调用点在 Windows 端空转 |

## 四、技术发现处理（Q4）

| # | 发现 | 判断 | 理由 |
|---|---|---|---|
| 1 | **"清除已完成"不删记录**（`task_page.py:110-120` → `queue.cancel()` → 状态改 `CANCELLED`，而 `list_all` 无过滤） | **修语义**（真删或前端隐藏二选一） | 【本轮新增判断】现状下点完列表不变 → 用户会重复点；且 `cancel` 的本意是"取消运行中的任务"，被复用来表达"清理"是语义污染 |
| 2 | **WS 广播已在阶段 0 删除**（`manager.py:580-581`；06-阶段0-1 §1.2） | **不恢复**；但**必须解耦 `_enabled`** | 【本轮新增判断】恢复 WS 与"Web 端 30s 轮询"重复（原 Q13 已裁决不重建）。**真正的问题**是：`_enabled=False`（默认）时 `send_event` 在**第一行早退** → 既无渠道投递、**也无 `notification_log`** → Web 端**完全看不到**这些事件。⇒ "是否投递渠道"与"是否记录/可见"**必须拆成两件事**（§七 待裁决 6） |

## 五、MoviePilot 学 / 不学 / 避免（Q5）

### 5.1 学（6 条，均带落点）

| # | 学什么 | PilotStd 落点 | 来源 |
|---|---|---|---|
| 1 | **粗类别 + 细调用点分层** | 印证 7 类 + 41 事件方向正确；**不因它改结构** | 01 报告 §一 Q2/Q5 |
| 2 | **渠道能力矩阵（12 项 + 量化上限）** | 渠道差异现在是"调用点各自判断"；矩阵可把差异变成**数据** | 01 报告 §三 Q11 |
| 3 | **"声明 vs 实现"必须有校验** | 学矩阵的**同时**加校验门禁（见 5.3-1） | 01 报告 §三 Q11（QQ 漂移） |
| 4 | **消息编辑链路形态**（先发拿 ID → 存 ID → 原地改写；失败回退新发） | 与 `channel_message_ids` 闭集约定同构；**但前置条件未满足**（渠道拿不到 ID） → 只学形态、暂不实施 | 01 报告 §二 Q8；01-现状盘点 §1.3 |
| 5 | **"人在场就不发"的原语** | MoviePilot：`need_notify and (background or not manual)`；PilotStd：可作为"分流"的判据之一 | 01 报告 §一 A 组/§四 |
| 6 | **把窗口合并做成通用基础设施** | `EventCoalescer` 的存在说明"合并"应是基建；PilotStd 已有聚合器（**印证，非新增**） | 03 报告 §五 5.1 |

### 5.2 不学（6 条）

| # | 不学 | 理由 |
|---|---|---|
| 1 | 放弃事件身份（只留 9 类别） | 41 事件是资产：i18n 层级键、e2e 契约、订阅粒度、G-045 覆盖度全挂在上面（02 报告 §四） |
| 2 | 无事件清单 | 导致 4 处漂移（QQ 能力、前端清单等）；PilotStd 要清单，但要从 4 份收敛为"用户时刻 + 事件"2 份 |
| 3 | i18n 不接线 | 826×2 叶子 + 250 条中文正则，通知链路 0 调用（01 报告 §六 Q23） |
| 4 | Jinja2 模板机制 | 与三语键形成双重真相，且与 G-045/G-047 冲突（02 报告 §五） |
| 5 | 多用户路由（`targets`/`action`/`*_ADMINS`） | 单用户部署（05-待裁决 §一 Q6） |
| 6 | 12 渠道规模 | PilotStd 是 4 渠道闭集（`CHANNEL_KEY_WHITELIST`） |

### 5.3 避免（6 条反模式 + 对策）

| # | 反模式（MoviePilot 实证） | PilotStd 对策 |
|---|---|---|
| 1 | 能力矩阵**声明与实现分家**（QQ 声明内联按钮却从不传 `buttons`；`Web`/`WebAgent` 有矩阵无模块） | **新增"声明 vs 实现"校验门禁**（§七 待裁决 9） |
| 2 | 60 秒去重**跨分钟失效**（键含"当前分钟"，`ttl=60` 形同虚设） | 沿用**滚动窗口**聚合（现有聚合器即是），禁止引入时钟粒度键 |
| 3 | Telegram 限流**不读 `retry_after`**，3 次后**丢弃** | 保留 `delivery_health`（连败 + 失败率双触发）；补充渠道级退避（框架层仅登记需求） |
| 4 | 每渠道各写一份权限校验（8 份重复） | 不适用（单用户），但**同类教训**记为"同一逻辑抄 N 遍"的告警 |
| 5 | 枚举线值用**中文/品牌名**（`"微信"`/`"资源下载"`） | PilotStd 的 `event_type`/渠道名已是英文键 → **保持** |
| 6 | 两代配置模型并存（旧 `NotificationSwitch` 死代码） | **清单治理时同步清理**（并入阶段 C 的"多余/重复"处置） |

## 六、实施路径（Q6）

### 6.1 Docker 端（已完成：阶段 0 / 1 / 2a / 2b / 2.5a）

| 序 | 阶段 | 目标（一句话） | 验收标准（一句话） | 回滚（一句话） |
|---|---|---|---|---|
| **D** | 可见性解耦【新增】 | "是否投递渠道"与"是否记录/可见"变成两件事 | 关闭投递时 `notification_log` 仍在写、Web 端仍可见 | 环境开关回退到"耦合" |
| **A** | 聚合键（原 2.5b 修订） | 聚合键切 `notify_event × target_id` 二元 | v1/v2 对照分组断言 + 批量链路采样无 429 恶化 | `NOTIFY_AGG_KEY=v1`（已有裁决机制） |
| **B** | 交互（原 3 收缩） | 只做 URL 按钮 + 能力缺失降级文本 | 4 渠道均产出可点链接、无编辑/回调路径 | `NOTIFY_REDESIGN_STAGE=2` |
| **C+E** | 治理重组（原 4 修订）+ 清单处置 | 门禁输入源改为"用户时刻 × 事件"双向闭包；多余额处置 | 三连门禁 EXIT=0 + 双向闭包断言 + 前端双层渲染 | `NOTIFY_REDESIGN_STAGE=3` + 订阅映射回滚脚本 |

**C 与 E 合并**：04-影响面 §六 判定 `assert len(EVENTS)==41` 属"无法渐进迁移"的原子批次，清单变更与门禁变更必须同批。

### 6.2 Windows 端

| 序 | 阶段 | 目标（一句话） | 验收标准（一句话） | 回滚（一句话） |
|---|---|---|---|---|
| **W1** | 任务中心改造 | 行单位从任务变为"一次用户操作"、文案改为用户语言 | 桌面真实操作一轮，任务中心可读且"清除"语义正确 | 纯 UI 回退（无数据变更） |
| **W2** | 共享事件分流 | Windows 端的事件转 `NotifyService`（或明确 no-op） | 长任务离席后仍能收到托盘气泡；事件不再"两头都不落" | 分流开关回退到现状 |

### 6.3 依赖与顺序

- **两端独立推进**（Docker 侧改 `notification/` 与 `docker/`；Windows 侧改 `pilotstd/ui/` + 一个门面分流点）。
- **唯一顺序约束**：**W2 必须先于 C**——C 要按端重排"用户时刻 × 事件"清单，而 W2 决定"哪些调用属于哪一端"。
- 建议顺序：**D → A → B → C+E**（Docker）；**W1 → W2**（Windows，与 Docker 并行）。
- **D 必须最先做**：它改变"关闭通知时的可观测性"，会影响 A/B/C 的验证口径。
