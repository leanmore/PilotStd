## 二、Task 2：目标架构设计文档

### 2.0 一句话架构

```
业务事件层（41 个，内部语义，代码直呼）
      │  ── 映射表：business_event → notify_event + content_type + task_kind
      ▼
通知事件层（7 类，用户视角，决定"这算什么事、要不要发、发到哪、能不能点"）
      │  ── 声明式：NOTIFY_EVENT × 渠道能力矩阵
      ▼
内容类型层（6 种内容块，决定"长什么样"，与渠道渲染器解耦）
      │
      ▼
渠道适配层（4 渠道 + 桌面 + Web，各自声明 capabilities；不支持的动作自动降级）
```

**三层各自回答一个问题**：业务事件回答"发生了什么"；通知事件回答"这对用户是什么事"；内容类型回答"怎么表达"。现状把它们压在一层（`event_type` + `_build_*_message` + 5 个渲染器）里，导致每个新需求都要动 41 个构建器之一。

### 2.1 事件模型：三层分离的具体设计

#### 第一层：业务事件（Business Event）——**不新增、不重命名、不删除**

保留现有 41 个 key 与 51 个调用点原样。新增一份**业务事件登记表**（新增文件，只读元数据，不放行为）：

#### 第二层：通知事件（Notify Event）——**7 类，替换"41 个用户可见事件"这一假设**

设计原则：**按"用户收到后要做什么"分类，而不是按产生它的系统模块分类。**

| # | 通知事件 key | 用户视角含义 | 归入的现有业务事件 | 默认 level | 交互需求 | 渠道取向 |
|---|-------------|-------------|------------------|-----------|---------|---------|
| 1 | `task_lifecycle` | "我交办的事有进展/有结果了" | download_started, download_complete, download_failed, favorite_created, archive_complete, archive_failed, archive_abandoned, normalize_complete, normalize_failed, expire_standard_moved, replacement_not_found, scan_complete, scan_empty | info（失败分支 warning/error） | **中**（查看详情 / 重试 / 忽略） | 全部渠道；进度类优先可编辑渠道 |
| 2 | `batch_summary` | "这批活干完了，结果如何" | batch_download_complete, favorite_abandoned_summary, batch_query_summary, query_empty, query_failed, auto_scan_failed, announce_fetch_summary, announcement_fetch_complete, announcement_check_complete, announcement_fetch_failed | info（有失败则 warning） | **中高**（查看明细 / 重试失败项） | 全部渠道；明细类优先列表能力强的渠道 |
| 3 | `anomaly_alert` | "出问题了，可能需要你处理" | task_execution_failed, worker_error, auto_backup(success=False), image_update_available(error 分支), quota_exhausted, validity_standard_failed, validity_system_failed, validity_batch_report(有失败分支), validity_round_summary(有失败分支) | error / warning | **高**（重试 / 查看日志 / 静音该类） | 全部渠道；**必须 bypass 聚合** |
| 4 | `security_alert` | "有人动了你的配置/凭证" | notification_credential_changed, security_password_changed, security_token_refreshed, security_login_failed | warning（凭证类为 error 级语义） | **低**（只看，不允许远程操作） | **强制旧渠道直连**（现有 `security_notifier` 路径不变） |
| 5 | `schedule_reminder` | "到时间了，该做这件事" | date_reminder, standard_status_changed, standard_first_registered | info | 中（查看详情 / 稍后提醒） | 全部渠道 |
| 6 | `system_health` | "系统自己出状况了" | notification_delivery_failed | error | 低（查看详情） | **旁路渠道**（现有 target_channels 机制不变） |
| 7 | `manual_test` | "这是我手动发的测试" | （新增，仅 `POST /api/notification/test` 使用，`event_type="test"`） | info | 无 | 调用方指定单渠道 |

**收敛比：41 → 7（其中 6 个承载现有业务事件，1 个是测试专用）。**

**三条硬约束（写入设计，不是建议）**：
1. **通知事件数量封顶 7 ± 1。** 超过 8 类说明分类维度又滑回"按系统模块"。新增一类的准入条件：**现有 7 类中没有任何一类的"默认渠道 + 默认 level + 交互需求"三者能容纳它**。
2. **`security_alert` 与 `system_health` 永久豁免"用户配置入口"。** 它们不是"用户可订阅的内容"，而是"系统必须送达的事实"。`security_alert` 已实测绕过策略表（`security_notifier.py:166-171` 注释明文），`system_health` 已实测定向旁路（`manager.py:397-398`）。**把它们塞进用户配置页是安全倒退**——凭证变更告警的收件人不能由"能被凭证变更影响的那个配置"决定。
3. **`task_lifecycle` 内必须区分"进度型"与"终局型"。** 进度型（可编辑、可原地更新）与终局型（一次性、不可编辑）的渠道能力要求完全不同；混在一类会让阶段 3 的降级逻辑无法收敛。

> **裁决补充（2026-10-02）**：用户在 Q1 选择**双层配置**（7 类为主 + 折叠的"高级：按业务事件细分"）。即：**路由/治理粒度是 7 类**（本节不变），**用户配置入口保留 41 项可读**（折叠展示）。两层的关系是"粒度不同"而非"两套模型"——41 项只是 7 类的展开视图，其勾选状态在阶段 4 由映射表换算。

#### 第三层：内容类型（Content Type）——**6 种，取代"各自渲染器"这一假设**

| # | 内容类型 | 对应现有 Block | 新增/改动 | 渠道降级规则 |
|---|---------|---------------|----------|-------------|
| 1 | `text` | `TextBlock` | 不变 | 全渠道原生 |
| 2 | `field_list` | `KeyValueBlock` | 不变 | 全渠道原生 |
| 3 | `status_change` | `StatusChangeBlock` | 不变 | 全渠道原生 |
| 4 | `list` | `ListBlock` | 不变 | 桌面只显示首条预览（现状不变） |
| 5 | `task_progress` | — | **新增**（`current`/`total`/`percent`/`stage`/`eta`） | 飞书/Telegram → 进度条文本 + 可编辑；钉钉/企微/桌面 → 纯文本百分比 |
| 6 | `action_prompt` | — | **新增**（`actions[]` + `text`，即"带按钮的提问"） | 有按钮能力 → 真按钮；无 → 降级为文本 + 深链 URL |

**关键设计：内容类型与渠道能力解耦。** 现状是"每个渠道一个渲染器，渲染器各自处理全部块类型"（5 个渲染器 × 4 种块 = 20 个渲染分支，且飞书渲染器**返回 dict 而非 str**，`renderer.py:312` 用 `# type: ignore[override]` 掩盖了契约分歧）。新模型下：**内容类型 → 渠道渲染器**是二维矩阵，每个格子的产出是"该渠道该类型的表达方式"，能力缺失时走**声明式降级**（而非 `if channel == "xxx"`）。

### 2.2 消息模型：新增字段定义

在 `NotificationMessage` 上**追加**字段，全部带默认值，**零调用点改动**（这是阶段 1 能做到零行为变更的前提）。

| 新字段 | 类型 | 默认 | 语义 | 为什么必需 |
|--------|------|------|------|-----------|
| `message_id` | `str` | `""` | 通知消息的稳定 ID（`uuid4().hex[:16]` 或 `corr-seq`） | 回调要能定位消息；`notification_log.id` 是行号，不能反查渠道消息 |
| `correlation_id` | `str` | `""` | 同一次业务运行的关联键（如"2026-10-02 收藏链第 3 批"） | 让 N 条通知在数据层可归组；现状只能靠 `standard_number` 事后猜 |
| `task_id` | `str` | `""` | 关联 Task 实体（见 §2.3） | 进度型通知的原地更新锚点 |
| `notify_event` | `str` | `""` | 三层模型中的通知事件（`task_lifecycle` 等 7 类之一） | 路由/配置/治理的新粒度；为空时回退用 `event_type` 推导（阶段 1–3 兼容） |
| `content_type` | `str` | `""` | 主内容类型（6 种之一） | 渲染降级与"该不该发"的策略判断依据 |
| `delivery_status` | `str` | `"pending"` | `pending`/`sent`/`failed`/`suppressed`/`edited` | **刻意不复用现有 `status` 字段**（后者是业务结果态 `success`/`failure`，见 Q3 裁决） |
| `ack_status` | `str` | `"none"` | `none`/`delivered`/`read`/`acted` | 交互闭环的落点；现状渠道契约只有 `-> bool`，无法表达"用户点过" |
| `actions` | `list[ActionSpec]` | `[]` | 可交互动作声明（见下） | 按钮的唯一数据源 |
| `callback_data` | `str` | `""` | 回调载荷（编码后 ≤ 64 字节，见 §2.4） | 渠道对回调数据有长度限制 |
| `attachments` | `list[AttachmentSpec]` | `[]` | 图片/文件附件（`kind`/`url`/`name`/`size`） | 现状无任何附件通道；实测四渠道均无图片发送代码 |
| `task_context` | `dict[str, Any]` | `{}` | 任务上下文快照（Task/TaskItem/TaskProgress 的扁平投影） | 让"任务视角"的通知不必把语义塞进 `event_type` |
| `channel_message_ids` | `dict[str, str]` | `{}` | 渠道名 → 该渠道返回的消息 ID | 消息编辑的唯一凭据；**留空即表示该渠道不支持编辑** |

**新增的动作规格**（`ActionSpec`）：

```python
@dataclass(frozen=True)
class ActionSpec:
    action: str          # view_detail / retry / ignore / snooze / open_logs / mark_done
    label_key: str       # i18n 键，调用期 t()（沿用现有约定，禁止模块级求值）
    style: str = "default"   # default / primary / danger —— 供渲染器映射
    args: dict = field(default_factory=dict)  # 动作参数（如 record_id）
    requires_confirm: bool = False  # 破坏性动作必须二次确认（见 Q8 裁决）
```

**动作白名单（闭集，禁止自由扩展）**：

| 动作 | 语义 | 改变状态？ | 最低权限 | 支持渠道 |
|------|------|-----------|---------|---------|
| `view_detail` | 打开站内详情/日志 | 否 | 接收者 | 全渠道（无按钮时降级为链接） |
| `open_logs` | 打开通知日志页 | 否 | 接收者 | 全渠道（同上） |
| `retry` | 重试失败项（写 `task_queue`） | **是** | 管理员 | 仅交互渠道 |
| `ignore` | 忽略/确认（记录 `ack_status=acted`） | 否（仅回执） | 接收者 | 仅交互渠道 |
| `snooze` | 稍后提醒（写延后队列） | **是**（延迟） | 接收者 | 仅交互渠道 |
| `mark_done` | 人工标记完成 | **是** | 管理员 | 仅交互渠道 |

> **裁决补充（2026-10-02）**：Q5 选择**默认只读**——`actions` 默认只含 `view_detail`/`open_logs`；`retry`/`mark_done` 需用户在设置页显式开启"允许远程操作"。因此阶段 3 的默认产物是"带链接的消息"，而非"带操作按钮的消息"。

### 2.3 任务模型：Task / TaskItem / TaskProgress

**关键发现：通用任务表已经存在，新增 Task 表面会导致双源。** 实测现有三张任务相关表：

| 现有表 | 字段（实测） | 能否承载目标模型 |
|--------|-------------|-----------------|
| `task_queue`（`_migrate_v16_v49.py:168-191`） | `task_id`(唯一) / `task_type` / `status` / `total_items` / `completed_items` / `failed_items` / `created_at` / `updated_at` / `result_json` / `error_log` / `retry_count` / `max_retries` / `timeout_seconds` / `started_at` / `finished_at` / `priority` / `queue_name` | **✅ 就是 Task 实体本体** |
| `fetch_task`（`:48-52`） | `id` / `task_type` / `status` / `progress` / `result_data` / `error_msg` / `created_at` / `updated_at` | 公告抓取专用，**已被 `task_queue` 覆盖语义**（技术债候选，Q9 附带项：归并列入阶段 4 待议） |
| `task_execution_history`（`:466-476`） | `task_name` / `status`(success/error) / `error_message` / `started_at` / `finished_at` / `duration_ms` | 定时任务执行流水；可作 Task 的终局归档 |

**因此目标设计为：**

```python
    finished_at: str        # ← finished_at
    notify_event: str       # 派生：task_kind → 通知事件（task_lifecycle / batch_summary）
    correlation_id: str     # 派生：同一批次；建议 = f"{task_kind}:{started_at[:19]}"
    message_ids: dict[str, str]  # 该任务已发出的通知 message_id 列表（含渠道消息 ID）

@dataclass
class TaskItem:
    """任务内的单个条目（内存投影，不落表——明细已在 result_json / 各业务表内）。"""
    item_key: str           # 标准号 / 公告号 / 文件名 —— 业务主键
    label: str              # 展示名（标准名称等）
    status: str             # pending/running/succeeded/failed/skipped/abandoned
    error: str = ""
    attempts: int = 0
    detail_url: str = ""

@dataclass
class TaskProgress:
    """进度快照：驱动 task_progress 内容类型与"原地更新"节流。"""
    task_id: str
    current: int
    total: int
    stage: str = ""             # fetch / parse / download / archive / normalize
    eta_seconds: int = 0
    updated_at: str = ""

    @property
    def percent(self) -> int: ...        # total 为 0 时返回 0，不抛
    @property
    def should_push(self) -> bool: ...   # 节流：percent 变化 ≥ 10 或 stage 变化或终局
```

**`task_kind` 值域（有限集，禁止自由新增）**：`announce_fetch` / `scan` / `query` / `organize` / `normalize` / `favorite_download` / `validity_check` / `backup` / `image_update`。九个值恰好对应现有 9 个定时任务名（`_builders_system.py:24-34` 的 `_TASK_NAME_KEY_MAP`）——**复用既有词表，不发明新词**。

**TaskManager（拟新增 `pilotstd/core/task/manager.py`）职责边界**：
- **只做投影与通知编排**：从 `task_queue` 读权威状态 → 构造 `Task` → 生成 `TaskProgress` → 触发通知事件。**不写任务状态**（写状态仍由现有业务代码负责），避免双写。
- **不实现通用队列**：现有 `task_queue` 已有 `priority`/`queue_name`/`retry_count`/`timeout_seconds`，不重复造。
- **幂等**：`should_push` 节流保证同一进度不重复发；`correlation_id` 保证同一批次可归组。

</details>

**Task 实体与通知的关系（一句话）**：**进度型通知不是"又一条通知"，而是"同一个 Task 的同一个 message_id 被反复 edit"。** 这正是 §2.4 消息编辑机制的动机。

### 2.4 交互模型：回调端点 / callback_data / 消息编辑

#### 回调端点设计

| 项 | 设计 |
|----|------|
| 路径 | `POST /api/notification/callback/{channel}`（channel ∈ telegram / feishu / dingtalk / wechat） |
| 鉴权 | **不能走 Cookie+CSRF**（外部渠道没有 Cookie）。必须在 `docker/auth.py:176-187` 的 `AUTH_WHITELIST` 增加该前缀，并在 handler 内**逐渠道验签**（这是唯一安全边界） |
| 验签（逐渠道） | Telegram：`X-Telegram-Bot-Api-Secret-Token` 头比对；飞书：`challenge` 握手 + `verification_token` + `encrypt_key` 解密；钉钉：HMAC 签名头；企微：`Token` + `EncodingAESKey` AES 解密 |
| 防重放 | 每条回调带 `message_id` + `nonce`，落 `notification_callback_log`（唯一约束 `message_id+action+nonce`），重复即幂等返回 200 |
| 响应 | **必须 200 且快**（渠道有 3–5s 超时）：只做"验签 + 入队 + 返回"，实际动作丢 `task_queue` 异步执行 |
| 大小 | 各家对回调数据长度限制不同，统一约束 `callback_data` **≤ 64 字节** |

**`callback_data` 格式（v1，定长、可解析、不加密敏感信息）**：

```
v1|<message_id:16>|<action:12>|<arg:32>
```
- 固定 4 段，`|` 分隔，总长 ≤ 68 但**约定 ≤ 64**（飞书/Telegram 更严）；
- `message_id` 用 16 位 hex（`uuid4().hex[:16]`）；
- `action` 取自 §2.2 的 6 个动作白名单；
- `arg` 存放业务定位（record_id / standard_number 的短哈希），**禁止放明文凭证、token、文件路径**；
- **服务端必须重新鉴权**：`callback_data` 来自外部（可被篡改），解析后一律以"消息记录 → 属于哪个 user → 该 user 是否有权做该 action"重新判定，**绝不信任回调里的 user_id**。

#### 消息编辑机制（分渠道能力，实测 + 官方文档核对）

| 渠道 | 能否编辑已发消息 | 依据 | 结论 |
|------|----------------|------|------|
| **Telegram** | ✅ 可以 | Bot API `editMessageText`（配合 `sendMessage` 返回的 `result.message_id` 与 `callback_query`） | 需把当前 webhook-only 发送升级为 Bot API 双向（长轮询或 webhook），见 [Long Polling - grammY](https://mintlify.wiki/grammyjs/grammY/advanced/long-polling) |
| **飞书** | ⚠ 有条件 | 更新卡片需 `PATCH /open-apis/im/v1/messages/{message_id}`（[更新已发送的消息卡片](https://open.feishu.cn/document/server-docs/im-v1/message-card/patch)、[更新卡片](https://open.feishu.cn/document/feishu-cards/update-feishu-card)） | **当前群机器人 webhook 形态拿不到 message_id**（`channels/feishu.py:48-55` 只读 `code`）→ 必须改用**企业自建应用机器人** |
| **钉钉** | ❌ 不可 | 群机器人 webhook 无更新消息接口 | 只能"再发一条回执" |
| **企微** | ❌ 不可（当前形态） | 群机器人 webhook 只收 markdown；交互卡片需**企业自建应用**（见 [企业微信二次开发：按钮/卡片交互](https://damodev.csdn.net/6aba0773ad85947e68ccb413.html)） | 同钉钉：回执补偿 |
| **桌面** | ❌ 不可 | `QSystemTrayIcon.showMessage` 无句柄 | 回执补偿（重新弹一条） |
| **Web** | ✅ 可以（前端自由） | 无后端推送，只能轮询；但前端可自由重渲染 | **本轮不实现**（无入站通道）；轮询通路见 [06-阶段0-1实施方案.md](06-阶段0-1实施方案.md) |

**设计结论（重要，避免过度承诺）**：
1. **"消息编辑"只在 Telegram 与飞书（自建应用形态）上成立**，且都需要从"webhook-only"升级为"双向 Bot"。这不是代码改动能绕过的——是渠道产品形态限制。
2. **其余渠道采用"回执补偿"**：动作执行后**发一条新的短回执**（"已忽略"、"已重试"），关联 `message_id` 使其在日志中可归组。
3. **不支持按钮的渠道不因此降级为"不发"**：动作以文本 + 深链表达（`view_detail` 本来就可降级为链接）。

> **裁决补充（2026-10-02）**：Q2 选择分两步——**阶段 3 先做 Telegram**（验证闭环），再做飞书自建应用。
