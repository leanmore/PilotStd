## 二、三条风险点的实测结论

### 风险 1：敏感信息脱敏（**必须新增**）
- **现状**：本链路**没有**任何脱敏环节（全库 grep `redact/sanitize/脱敏` 命中的都是**无关模块**：`file_utils`/`_credentials`/`wechat_ip` 等）。
  今日已在暴露的 `error_msg` 也未脱敏 —— 属**既有面**，本批需为**新透出的 `failed_items.error_message` 建立拦截**。
- **数据来源（实测）**：
  - `pilotstd/manager/facade/_organize.py`：异常文本（可能含**绝对路径**、标准号）；
  - `pilotstd/download/engine.py`：任务 `error_message`（可能含**下载 URL 及其查询串**——其中可能有临时签名/会话参数 ⚠️）。
- **设计要求（后端透出前拦截）**：
  1. **URL 查询串抹除**：保留 `scheme://host/path`，查询串与 `#fragment` 以 `?…`（或 `<已省略>`）替换；
  2. **路径收敛**：绝对路径只保留**末段文件名**（用户不需要服务器目录结构）；
  3. **令牌样式掩码**：连续 ≥24 位 `[A-Za-z0-9_\-]` 或 ≥32 位十六进制 ⇒ 掩码为 `***`；
  4. **邮箱/手机号**掩码（用户名保留首字符）；
  5. **长度上限**：`≤120` 字符（与既有 4 列口径一致 ⇒ 超长截断加省略号）；
  6. **只做展示侧拦截**：**不改落库内容**（排障需要原文；落库已在同权限的 DB 内）——即"落库存真、展示脱敏"。

### 风险 2：大表分页与性能（**列表已达标；明细需"按需取"**）
- **列表**：API 已强制 `page/page_size`（上限 100）+ `COUNT(*)` 分页 ✅；前端 `pageSize=20` ✅。
- **明细（新接口/新字段）的设计约束**：
  1. **禁止全量拉取**：不得给列表接口加"把每条的 `failed_items` 一并返回"（一条批次可能上千条 ⇒ 响应体爆炸）；
  2. **独立端点按需取**：新增 `GET /api/notification/logs/{id}/failed-items?page&page_size` ⇒
     **服务端解析 JSON 后分页**（`page_size` 上限同样 100），返回 `total/items`；
  3. **单条上限**：原始 `error_message` 与脱敏后文本都截断到 120 字符（落库侧已截断，展示侧再兜一次）；
  4. **可选**：仅当 `total > 0` 时前端才显示"查看明细"入口（避免无谓请求）。

### 风险 3：错误码 i18n（**必须补前端三语**）
- **现状**：`error_type` 的枚举口径为 `not_found/parse/network/timeout/unknown`（B1 裁定）；**后端**已有
  `pilotstd/i18n/*.json` 的 `notification.error_type.*` 三语（用于消息渲染）；**前端 locales 没有这三语键** ❌
  ⇒ 若直接把 `error_type` 透出，前端会显示英文枚举（如 `not_found`），正是要避免的"暴露技术码"。
- **设计要求**：
  1. **前端三语键**：`web/src/locales/{zh-CN,en,zh-TW}.json` 补 `notification.error_type.{not_found,parse,network,timeout,unknown}`；
  2. **前端映射函数**：未知取值 ⇒ 回退 `unknown` 的文案（**不显示原始取值**）；
  3. **`error_message` 的定位**：作为**次要信息**（折叠/"技术详情"）呈现，主列只显示**已翻译的类别** +
     标准号 + 标准名 + 次数 ⇒ 用户第一眼看到的是可读信息，而非堆栈。
  4. **不在本批做**：把底层技术错误码（如 `SMTP_AUTH_FAILED`）**逐码**映射为用户话术——那属于通知系统之外的
     渠道/网络层词表（需专门词表与取证）；本批先保证"类别层可读 + 技术文本降级为次要"，并把该点登记为后续项。
