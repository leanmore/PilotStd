## 一、方法：运行时插桩（静态字符串匹配已证明不可靠）

**为什么不用静态匹配**：首轮用"事件键是否出现在 `trigger_file`"做判定，得出 3 处"不一致"，
深查后全部是**误报**（`manager/facade/_organize.py:266` 明确写着"发送归档完成通知失败"⇒ 声明是对的，
只是事件键以**变量/门面转发**形式出现）。静态匹配无法覆盖动态触发与门面层转发。

**插桩点（三层，进程内 hook）**：

| # | 插桩点 | 覆盖的触发方式 |
|---|---|---|
| 1 | `NotificationManager.send_event` | 业务规范入口（绝大多数事件） |
| 2 | `NotificationAggregator.push` | 聚合入口（含 L2 **直构消息**，如 `desktop_toast`） |
| 3 | `_dispatcher.send_now` | 最终投递（额外提供渠道与聚合上下文） |

**采集方式**：仓库外脚本（`C:\Temp\mp_probe\runtime_map.py`）在**进程内**打桩后
`pytest.main([...])` 跑测试，对每次触发记录 `(事件, 触发方式, 调用方 文件:行号, 当时的测试)`；
调用方取**第一个非通知包内部、非 pytest、非脚本自身**的栈帧（首轮曾把自己记成触发点，已修）。

**范围**：全量 `tests/`（排除 `tests/gui`，GUI 用例不产生业务通知且耗时极长）。
**实测规模**：**5309 passed / 11 skipped**（13 分钟）。

**局限（如实声明）**：
1. 覆盖的是**测试可驱动**的业务路径；真实部署中的手工 UI 操作、外部回调触发的路径不在其中；
2. 测试用桩（Mock）较多，未被任何测试驱动的分支**不会**出现在地图里；
3. 因此本报告给出的是"**测试可达性**"权威地图，而非"生产可达性"全集。

   强制覆盖会引入大量 mock 与脆弱测试，违背运行时测绘的初衷；
2. **不预设 P7 条目**——待本基线清晰后，再按业务优先级挑选；
3. **门禁可维护性优先**——必须是**声明式**（事件注册时必填字段），**不是过程式**（不必每次跑全量插桩）。

**落地设计（已实施）**：

| 层 | 内容 | 成本 |
|---|---|---|
| **① 声明期（最强、最便宜）** | `EventSpec.verify` **无默认值** ⇒ 新增事件漏填时 **import 期直接 `TypeError`**（无需跑任何测试即可兜底） | 0 |
| **② 静态审计（进快闸）** | `scripts/_notification_spec_read.py::spec_field_problems` 增校验：`verify` 落闭集 `(e2e, manual, ui_only)`；非 `e2e` **必带机器可读枚举理由** `verify_reason ∈ VERIFY_REASON_CODES`；`e2e` **不得**带理由（防用理由掩盖分类） | 毫秒级 |
| **③ 按需运行时校验（不进快闸/CI 阻断链）** | `scripts/audit_notification_trigger_map.py`：三层插桩 + 精简（≈90s）/全量（≈13min）两档，输出"声明 vs 观测"地图与差异；仅 `--strict` 才返回非 0 | 仅手动运行 |

**分类结果（按实测地图回填）**：
- `verify="e2e"` **12 个**：全量套件可观测其**生产触发点**（如 `manager/facade/_scan.py:75`、
  `services/favorite_chain_processor.py:239`、`docker/api/users.py:191` 等）；
- `verify="manual"` **28 个**：环境相关或真链路未被现有用例驱动；理由码分布 ＝
  `real_chain_only 15`、`data_condition 3`、`env_dependent 3`、`chaos_condition 2`、
  `external_state 2`、`time_based 2`、`external_event 1`；
- `verify="ui_only"` **2 个**：`desktop_toast`、`worker_error`（仅桌面 UI 层触发）。

**理由码闭集（8 个，定义在 `scripts/_notification_spec_read.py`）**：
`env_dependent`（真实环境/凭证/用户动作）、`external_state`（外部系统状态）、`external_event`（外部事件推送）、
`time_based`（真实时钟/定时任务）、`data_condition`（特定数据条件）、`chaos_condition`（故障场景，如库损坏类告警）、
`real_chain_only`（真实链路完成才触发）、`ui_only`（仅桌面 UI）。

**为什么这样最省负担**：新事件只需在注册处写一个必填的 `verify=`（漏写当场失败）；
既不必为它构造运行时场景，也不必在门禁里跑任何插桩。

**测试**：`tests/test_event_verify_declaration.py`（10 例）——注册期必填（含 `TypeError` 断言与
"字段无默认值"断言）、真实 42 条自洽、"允许存在非 e2e 事件"的口径固化、审计函数对
**四类反例**（越界值／非 e2e 缺理由／理由码越界／e2e 带理由）必须报错。

## 五、结论、已实施项与待确认项

**已实施（按用户 2026-10-06 修正口径）**：
1. `EventSpec` 新增 **`verify`（注册期必填，无默认值）** 与 `verify_reason`（机器可读枚举码）；
2. 42 条声明**全部回填**：`e2e 12 / manual 28 / ui_only 2`（理由码 8 类，闭集定义在审计读侧模块）；
3. 静态门禁接入既有覆盖审计（`audit_notification_coverage.py` 的规格字段维度）⇒ **毫秒级**；
4. 按需诊断工具 `scripts/audit_notification_trigger_map.py`（精简/全量两档，**不进快闸、不阻断 CI**）；
5. 契约基线同步（`EXPECTED_FIELDS` 15 → 17、AST 关键字数 15 → 17、字段计数用例改名）；
6. 新增 `tests/test_event_verify_declaration.py`（10 例）并全绿。

**待确认/后续（不在本批）**：
1. **G1**：`worker_error` 已声明为 `ui_only`；若后续无头端也需要该告警，再补生产触发点（届时改声明即可）；
2. **G2 逐项分类复核**：28 个 `manual` 事件的**理由码**是按证据初判的，若你认为某项应改为 `e2e`
   （并愿意补可驱动用例），改一行声明即可；
3. **P7 条目挑选**：按你的裁定，**待本基线清晰后**再按业务优先级挑选（本批不预设任何 P7 条目）。
