## 三、数据迁移设计（草案，待评审）

**现状**：`notification_policy(user_id, channel, events JSON)`，`events` 存 **41 个原始事件名**的数组。

**目标**：能表达两种粒度（Q1 双层）——
- 层 1：**10 类**（`notify_event`）；
- 层 2（高级）：**41 个业务事件**（保留现有表达力）。

**两个候选方案**（需裁定，见 §六）：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **甲：加列** | 新增 `event_classes TEXT DEFAULT '[]'`，保留 `events` 原样 | 语义清晰、互不干扰；回滚只需忽略新列 | 多一列 + 读侧要合并两个来源 |
| **乙：复用 `events`** | 在 `events` 里同时接受类别名与事件名（读侧按 `NOTIFY_EVENTS` 判定） | 不动表结构（迁移最轻） | 同名冲突难以校验；历史数据无法区分"故意订阅了类别"还是"拼写巧合" |

**共同要求（无论哪个方案）**：
1. 迁移**幂等**（重复执行不报错，用 `PRAGMA table_info` 探测列是否已存在）；
2. 迁移**不改既有语义**（默认 `enabled=1`、`events` 原样保留 ⇒ 新旧读侧都能跑）；
3. 迁移**前**做数据备份（见 §四）；
4. 迁移**只用前滚**（P-106：不得事后改迁移源码）。

### 第 1 层：应用层开关（**首选，秒级回滚，无需改代码**）

|---|---|---|---|

### 第 2 层：数据层备份与恢复（**兜底**）
| 动作 | 时机 | 做法 | 验证 |

### 8.2 用户额外关注：**本地状态缓存 / 乐观更新**（专项结论）

| 关注点 | 实测结论 | 影响面（4b 必须处理） |
|---|---|---|
| **本地状态缓存** | **存在**，但**不是** `localStorage`/`sessionStorage`，而是**内存型"内容级缓存"**：`loadChannelSpecs()` 在 `!force && specHash.value === resp.spec_hash && specs.value.length` 时**早退**（`NotificationConfig.vue:123`），注释明确"哈希未变时不会重建（避免清空用户正在编辑的内容）" | ⚠️ **高风险**：若 4b 只加"类别层"而**不改 `spec_hash` 的计算口径**（或未新增"层版本"判据），则该早退会让新层**永不初始化**（前端看不到类别层）⇒ 必须二选一：①把层级能力纳入后端 `spec_hash` 计算；②新增 `config_layers_version` 并纳入早退判据 |
| **乐观更新** | **无**：`saveConfig()` 全量 `await`（先 `putNotificationConfig`，再逐渠道 `putNotificationPolicy`），随后 `await loadChannelSpecs()`，最后置 `saved` | 无需为"回滚乐观状态"加逻辑；但见下一条 |
| **静默降级（吞错）** | **有两处**：①策略写入 `catch { /* 策略 API 不可用时静默降级 */ }`（`:213`，逐渠道）；②`loadConfig` 中 `getNotificationPolicies()` 失败时 `catch {}`**保持 config.json rules**（`:166`） | ⚠️ **前后端不一致风险**：策略层写入失败时 UI **仍报"已保存"**；双读/双写切换后会出现"看起来保存成功、实际类别层没落库"。4b 必须让该失败**可见**（至少 `console.warn` + 计数提示，理想是错误气泡），并把"策略为空"与"策略 API 失败"分开呈现 |
| **其它隐式行为** | `saveConfig` 会**同时写两条路径**（config.json `rules` 全矩阵 + 策略表逐渠道）；`testChannel()` 用 spec 的全部字段发测试消息；静音时段走 `useUserPreferences`（独立区，不涉双层） | 4b 的双层保存要同时覆盖两条路径，避免"类别层只落一边" |
