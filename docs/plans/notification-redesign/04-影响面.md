## 四、Task 4：影响面分析

### 4.1 41 个事件在阶段 1–3 如何保留、阶段 4 如何迁移

**阶段 0–3：41 个业务事件 key、51 个调用点、41 个构建器、240 个 i18n 键——全部原样保留。** 阶段 0 只动前端与 WS 死代码；阶段 1 只在 `NotificationMessage` 与 `notification_log` 上**追加**字段/列；阶段 2 只让 `notification_log.notify_event` 开始有值（11 个终局事件）；阶段 2.5 只改聚合分组键（带开关）；阶段 3 只加交互通路（默认只读）。**任何阶段都不改 41 个构建器、不改 i18n、不改渠道渲染器。**

**阶段 4：迁移方式 = 映射表 + 兼容读取**，逐事件归属（与 [02-目标架构.md](02-目标架构.md) §2.1 第二层表对应）：

| 迁移目标 | 事件数 | 事件清单 | 迁移动作 |
|---------|-------|---------|---------|
| → `task_lifecycle` | 13 | download_started, download_complete, download_failed, favorite_created, archive_complete, archive_failed, archive_abandoned, normalize_complete, normalize_failed, expire_standard_moved, replacement_not_found, scan_complete, scan_empty | 策略迁移 + 前端入口合并 |
| → `batch_summary` | 10 | batch_download_complete, favorite_abandoned_summary, batch_query_summary, query_empty, query_failed, auto_scan_failed, announce_fetch_summary, announcement_fetch_complete, announcement_check_complete, announcement_fetch_failed | 同上 |
| → `anomaly_alert` | 9 | task_execution_failed, worker_error, auto_backup, image_update_available, quota_exhausted, validity_standard_failed, validity_system_failed, validity_batch_report, validity_round_summary | 同上；`auto_backup`/`image_update_available`/`validity_*` 是**分支归属**（成功走 `task_lifecycle`，失败走 `anomaly_alert`）→ 映射需按 `data` 内容判定，不能只看 key |
| → `security_alert` | 4 | notification_credential_changed, security_password_changed, security_token_refreshed, security_login_failed | **不进用户配置入口**（安全约束）；投递路径不变 |
| → `schedule_reminder` | 3 | date_reminder, standard_status_changed, standard_first_registered | 策略迁移 |
| → `system_health` | 1 | notification_delivery_failed | **不进用户配置入口**；旁路投递不变 |
| → `manual_test` | 1 | `test`（非 ALL_EVENTS 成员，`docker/api/notification.py:331`） | 保持独立 |
| **合计** | **41** | 13+10+9+4+3+1 = 40，加 `test` = 41 | — |

**两个必须在映射层显式处理的例外**：
1. **分支归属（4 个事件）**：`auto_backup`（`docker/scheduler.py:163` 成功 / `:176` 失败）、`image_update_available`（`error` 分支 / 版本变更分支）、`validity_batch_report`（有失败 / 无失败）、`validity_round_summary`（同上）——同一个 key 会落到不同通知事件，`project()` 必须读 `data` 而非只读 `event_type`。
2. **共用物理调用点（3 个事件）**：`notification_credential_changed`/`security_password_changed`/`security_token_refreshed` 共用 `security_notifier.py:174` 且 **event_type 是变量**——静态扫描与门禁都识别不了，映射表必须人工登记（这也是 [01-现状盘点.md](01-现状盘点.md) §1.2 里"间接载荷 3 处"之一）。

### 4.2 治理机制在各阶段的适配方案

| 机制 | 阶段 0 | 阶段 1 | 阶段 2 | 阶段 2.5 | 阶段 3 | 阶段 4 |
|------|-------|-------|-------|---------|-------|-------|
| **13 步准入**（原 9 步） | 不动 | 不动（新增字段不属于"新事件"） | 扩为 **10 步**：+「登记 `notify_event` 归属」 | 不动 | 扩为 **12 步**：+「动作声明」「内容类型声明」 | 扩为 **13 步**：+「收件人声明（`owner_user_field`）」；并把"业务事件"与"通知事件"拆成**两张清单表** |
| **G-045 覆盖度** | 不动（`ALL_EVENTS` 仍是 41） | 不动 | **扩维度**：新增"每个已映射业务事件都能 `project()` 到目标类"的断言；`trigger_file` 单值改多值（实测 9 个事件有 2–3 个产出点） | 不动 | 新增维度：动作可渲染性（每个 `actions` 在目标渠道有定义好的降级） | **切换输入源**：`ALL_EVENTS` → 业务事件登记表 + 通知事件注册表；删除 `assert len(EVENTS)==41`；矩阵标题改为"41 业务事件 × 7 通知事件"；`desktop_toast` 正式登记 |
| **G-046 链路审计** | 不动 | 不动（新字段不产生新吞错面） | 扩到 `mapping.py`（新文件纳入审计，防新的静默吞错） | 不动 | 扩到 `edit_message`/回调 handler | 审计对象从"41 个构建器"改为"41 构建器 + 7 类投影 + 动作定义"，`--strict` 零基线保持 |
| **G-044 术语表** | 不动 | 不动 | 新增文案进 `notification.<notify_event>.<field>` 命名空间 | 不动 | 按钮文案键（`notification.action.<action>`）登记 | 术语表 `keys` 扩容到覆盖新命名空间；`forbidden` 词表增补"任务/作业/进度"等易漂移词 |
| **G-043 敏感端点审计** | 不动 | 不动 | 不动 | 不动 | **必须登记**回调端点（`SENSITIVE_ROUTES`/`EXEMPT_ROUTES` + 理由），并按 L-01 的 `AUDIT_WRAPPERS` 机制处理鉴权包装 | 不变 |
| **CI 接线** | 前端单测 | 迁移测试 | 映射表驱动测试 | 分组键对照测试 | 验签 + 越权测试 | 双向闭包测试 |

**新增门禁建议（阶段 4 一并定）**：
- **G-047 通知事件闭包**：业务事件 → 通知事件的映射**双向**完整（每个业务事件有归属、每个通知事件有来源、无孤儿）。
- **G-048 渠道能力一致性**：`ChannelCapabilities` 声明的能力与渠道渲染器实际产出**一致**（防"声明支持按钮但渲染器不产按钮"）。

### 4.3 哪些改动可以渐进、哪些必须一次完成

| 类别 | 项 | 理由 |
|------|----|------|
| **✅ 可以渐进** | 消息模型加字段（阶段 1，3 批） | 默认值即现状语义；逐步填充；`NOTIFY_REDESIGN_STAGE` 可逐批回滚 |
| | 业务事件登记表 | 纯新增，无消费方 |
| | Task/TaskItem/TaskProgress 投影 | 只读 `task_queue`，不双写 |
| | `project()` 映射函数（阶段 2） | 带 `notify_event=""` 回退路径，可逐事件灰度 |
| | 聚合键变更（阶段 2.5） | 独立开关 `NOTIFY_AGG_KEY`，单独回滚 |
| | `capabilities` 声明（阶段 3） | 新增属性，渠道行为不变 |
| | 内容类型 5/6（`task_progress`/`action_prompt`） | 新类型，老渠道走降级 |
| | 前端 `useNotification` 轮询（阶段 0） | 纯前端，与后端零耦合 |
| **❌ 必须一次完成（原子）** | **`assert len(EVENTS) == 41` 的改动** | `tests/test_notification_e2e.py:739` 是硬断言；改它必须同批改 e2e 条目、矩阵标题、`desktop_toast` 登记——**这正是 `desktop_toast` 至今不登记的同一原因**（`notification_coverage.md:224` 原文："登记会必然即红……需一次性改 6 个文件并引入'平台层事件'新分类"） |
| | **`notification_policy.events` 语义切换 + 数据迁移** | 用户既有订阅数据与前端读取逻辑必须同批切换，否则"策略表有值但读不懂"→ 静默不发 |
| | **`notification_log` 列语义变更**（若要把 `status` 改为投递态） | 生产库历史数据语义无法回填，只能新增列；**若图省事复用 `status`，历史数据的 `success`/`failed` 会被误读为投递态** → **裁决 Q3 已定为"新增 `delivery_status`/`ack_status`，不动 `status`"**（本设计正是绕过该原子项） |
| | **渠道凭证模型变更**（飞书 webhook → 自建应用） | 凭证表、迁移、前端表单、`get_config_schema`、安全告警的"旧渠道直连"路径（`security_notifier.py:191`）**必须同批**，否则凭证变更告警会发到无效地址 |
| | **回调端点的白名单与验签** | 白名单是安全边界，**不能先放行后补验签**（哪怕一小时） |

## 六、无法渐进迁移的部分（明确标注）

> 按 AGENTS.md 要求，凡"无法渐进"者必须明确标注，不得含糊。本表是 [03-实施路径.md](03-实施路径.md) 阶段划分的依据。

| # | 无法渐进的项 | 为什么必须一次完成 | 可否绕过 |
|---|-------------|------------------|---------|
| 1 | `tests/test_notification_e2e.py:739` 的 `assert len(EVENTS) == 41` | 硬编码断言；改它就必然同时改 e2e 条目、矩阵标题、`desktop_toast` 登记（6 文件） | ❌ 不可绕过（除非放弃 e2e 契约，等于放弃 G-045 的一半判别力） |
| 2 | `notification_policy.events` 语义切换 | 用户既有订阅数据 + 前端读取 + 后端路由必须同批，否则策略静默失效 | ❌ 不可绕过（可用兼容双读降低风险，但语义切换本身是原子的） |
| 3 | 渠道凭证模型变更（飞书 webhook → 自建应用） | `user_credentials`、迁移、`get_config_schema`、前端表单、`security_notifier` 的旧渠道直连路径**同批**，否则凭证变更告警发到无效地址 | ❌ 不可绕过（可先并行保留两套凭证字段，但**告警路径必须一次改对**） |
| 4 | 回调端点白名单 + 验签 | 白名单是安全边界，先放行后补验签 = 开放未鉴权写端点 | ❌ 不可绕过（这是设计红线，不是工期问题） |
| 5 | `notification_log.status` 语义（若要把投递态与业务结果态合并） | 生产历史数据无法回填语义 | ✅ **可绕过**（本设计正是绕过：新增 `delivery_status`/`ack_status`，不动 `status`） |
| 6 | `notification_queue` 补发路径的字段白名单 | `manager.py:463-465` 用**白名单**从 JSON 重建消息——**新字段不扩白名单就会在补发时静默丢失**（`message_id`/`correlation_id`/`task_id` 全丢） | ✅ 可绕过（但**必须记得扩**；这是最隐蔽的一处，阶段 1 每批都要加断言防回归） |
| 7 | 聚合器不搬运新字段 | `aggregate_buffer.py:397-407` 显式构造 `merged` 只搬运 9 个字段——新字段不加就**永远为空** | ✅ 可绕过（阶段 1 每批显式搬运 + 单测锁定） |
| 8 | `task_queue`/`fetch_task` 双源 | 若选"新增 Task 表"则双写不可避免 | ✅ **可绕过**（Q9 已裁 A：投影 `task_queue`，不新增主表；`fetch_task` 归并列入阶段 4 待议） |
