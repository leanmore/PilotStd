> **调查对象**：`pilotstd/core/task/manager.py`（拟新增，P4b-2）——从既有 `task_queue` 读权威状态、

> **审核关注点**（用户 2026-10-05 提出）：①读取性能（防 N+1）②`result_json` 容错 ③约束显式化。

**调查日期**：2026-10-05　**基线**：`007dcbfb`

## 一、读取性能：**批量接口已存在，无需自造，且必须用批量**

| 结论 | 证据 |
|---|---|
| 既有 DAO 是 **`pilotstd/task/queue.py::TaskQueue`**，已有**批量**与**单条**两类接口 | `get(task_id)`（单条）；**`get_all(status_filter=None, limit=100) -> list[dict]`**；`list_all(limit=50) -> List[TaskInfo]`；`get_pending()` |
| `get_all` 是**一次 `fetchall` 批量查询**（非逐条） | 实测实现：`SELECT * FROM {TASK_TABLE} WHERE status=? ORDER BY created_at DESC LIMIT ?`（无过滤时为不带 WHERE 的同构查询）⇒ **一次 SQL 取 N 行** |
| **有索引支撑**（列表查询走索引，不会全表扫描） | 迁移实测：`idx_task_queue_status`、`idx_task_queue_updated`、`idx_task_queue_status_created` |
| ⇒ **N+1 是可以避免的，且必须避免** | 投影入口的规定动作：**一次 `get_all()` 取整批 → 内存里循环构造 `Task`**；**禁止**在循环里逐条 `get(task_id)` |

**对实现的硬要求**：`TaskManager` 提供 `list_tasks(limit=...)`（**一次批量读**）与
`get_task(task_id)`（单条读，用于进度快照）；任何"遍历任务再逐条查库"的写法在评审中直接否决。

**顺带发现（不影响本批）**：`docker/api/tasks.py:138` 直接调用了 `mgr.task_queue._persist(task)`
（下划线私有方法）⇒ 已存在的**越界调用**；本批**不动**它（R-002 精准修改），仅登记在此供后续清理。

## 二、`result_json` 容错：**本表该列至今没有消费方 ⇒ 本项目要做"第一个消费者"，防御式解析必须自己写**

| 结论 | 证据 |
|---|---|
| `task_queue.result_json` **当前无读取方**（本批将是首个） | `git grep result_json -- pilotstd` 命中的都是**别的表**（`network_cache` / `announcement_cache` 的缓存列，见 `core/_file_index_query.py:123/131/138`） |
| 既有同类解析多为**防御式**（可参考写法） | `_file_index_query.py:141 cached = json.loads(result_json)`（该处位于 `_apply_cache_result`，需要按同款思路包 try 并回退） |
| 通知侧已有"容错 JSON"工具，但**不适合直接复用** | `pilotstd/core/notification/_json_codec.py` 的 `loads_dict`/`loads_list` 语义是"通知落库列（actions/attachments）"，跨包复用会把两个域的契约绑死 |
| ⇒ **实现方案** | 在 `manager.py` 内写**本地** `_loads_result_json(raw) -> dict`：`raw` 为空/非 `str` ⇒ `{}`；`json.loads` 抛错 ⇒ `{}`；结果非 `dict` ⇒ `{}`；**永不抛**。并在 docstring 写明"历史数据 schema 可能不一致 ⇒ 只保底不解释，缺字段由调用方按默认值处理" |

**为什么"只保底不解释"**：`result_json` 由各业务写入、历史 schema 不一（用户关注点②）；
投影层不该猜业务语义 ⇒ 拿不到就返回空字典，由上层决定默认值（与 `_json_codec` 的既有哲学一致）。

## 三、约束显式化：**"只读、暂不触发通知"要写进代码与提交说明**

| 位置 | 写法 |
|---|---|
| `manager.py` 模块 docstring | 三句硬约束：①**只读** `task_queue`（写状态仍归现有业务代码）②本批**不触发任何通知**（`task_progress` 维持"只加数据结构"的 2026-10-02 裁决）③**不改**聚合键与 `notification_policy`（后者属阶段 4） |
| 每个读取方法的 docstring | 标注返回的是**内存投影**（非权威状态）＋"调用方不得据此回写" |
| 提交说明 | 标题与正文显式写"只读、暂不触发通知"，并在正文列出"本批不做"的边界清单 |
| 防误补 | 在 `task_progress`/`should_push` 相关代码旁注明"**尚未接线**；接线需先经裁定"（避免后来者顺手补上） |

## 七、实施期补充发现（P4b-2 编码时实测，2026-10-05）

| 发现 | 证据 | 处置 |
|---|---|---|
| **`TaskStatus` 实际取值与设计文档不一致** | `pilotstd/task/models.py::TaskStatus` ＝ `pending/running/paused/**completed**/failed/**cancelled**`；而 `02-目标架构.md §2.3` 的设计词表是 `pending/running/succeeded/partial/failed/abandoned` | `TERMINAL_STATUSES` **两套词表都纳入**（否则真实数据上的终局会被节流闸拦住 ⇒ **静默丢终局通知**）；`Task.status` 保持**原样镜像**表值（投影层不做翻译，避免信息丢失） |
| **`TaskType` 只有 5 个值**（`scan/query/download/organize/expire`），而 `mapping.TASK_KINDS` 更多（含 `favorite_download`/`normalize`/`announce_fetch`） | `pilotstd/task/models.py::TaskType` vs `mapping.py::TASK_KINDS` | 本批**不做映射**（投影层不发明翻译）；两值域的收敛留给"接线通知"的批次 |
| **`get()` 与 `get_all()` 返回形状不同** | `get()` → `TaskInfo` 数据类；`get_all()` → `list[dict]` | `manager.py` 提供两个私有投影函数做形状归一（`_task_from_row` / `_task_from_info`）＋ 单测覆盖 |
