**总原则**：阶段 0 只修用户可见的坏体验；阶段 1 只用"加字段 + 加表列"，**零行为变更**；阶段 2 引入任务视角但**不改 41 个构建器、不动聚合键**；阶段 2.5 单独改聚合行为（**风险最高，独立灰度**）；阶段 3 才动渠道产品形态（唯一需要外部配置/凭证变更的阶段）；阶段 4 做破坏性重组，**且必须一次性完成**。

### 3.0 一键回滚机制（贯穿全阶段）

新增单一环境变量 **`NOTIFY_REDESIGN_STAGE`**（取值 `0|1|2|2.5|3|4`），语义 = "当前生效到哪个阶段"：

| 取值 | 行为 | 默认 |
|------|------|------|
| `0` | 通知链路完全按现状（新字段不写入、映射不生效） | — |
| `1` | 新字段写入 `notification_log`（旧 11 列语义不变），映射不生效 | ✅ **阶段 1 交付后的默认值** |
| `2` | `project()` 映射生效（终局通知按 `notify_event` 归类），聚合仍用 v1 键 | 阶段 2 交付后的默认值 |
| `2.5` | 聚合键切 v2 | 阶段 2.5 灰度通过后的默认值 |
| `3` | 交互能力启用（回调端点 + 动作） | 阶段 3 交付后的默认值 |
| `4` | 三层模型全面生效（配置粒度切 7 类主 + 41 项折叠） | 阶段 4 交付后的默认值 |

**实现约束（写入方案，防"开关变成第四套逻辑"）**：
1. 开关只在**一处**读取（`pilotstd/core/notification/stage.py` 的 `current_stage()`），禁止在 41 个构建器或渠道内散读环境变量。
2. 开关**只控制新路径的启用**，不改变旧路径语义——即 `current_stage() <= 1` 时，`notification_log` 的旧 11 列必须与现状逐列相等（这是可断言的回滚判据）。
3. 每个阶段交付时，**默认值 = 该阶段**；回滚 = 把变量改成前一阶段的稳定值（不需要改代码、不需要回滚迁移）。
4. 阶段 2.5 另有**独立**开关 `NOTIFY_AGG_KEY`（默认 `v1`）——因为"映射生效"与"聚合键变更"是两件可独立回滚的事，不应绑在一个变量上。

### 3.3 阶段 2.5：聚合行为变更（独立灰度，风险最高）

> **裁决调整（2026-10-02）**：原设计的聚合键变更**从阶段 2 拆出**，单独做、单独验证、单独回滚。

| 项 | 内容 |
|----|------|
| **改动范围** | `aggregate_buffer._group_key()` 从 `event_type + \x1f + target_id` 二元组改为 `notify_event + \x1f + correlation_id + \x1f + target_id` 三元组（**`notify_event` 为空时回退 `event_type`**，保证阶段 1 前的事件与未知事件行为不变） |
| **开关** | `NOTIFY_AGG_KEY=v1\|v2`，**默认 v1**；灰度验证通过后把默认值改 v2 |
| **影响面** | **所有 41 个事件的聚合行为都会变**——同类合并范围从"同事件类型 × 同实体"变为"同通知事件 × 同运行 × 同实体" |
| **风险** | ① **`target_id` 与 `correlation_id` 不等价**：前者是"关联实体"，后者是"同一次运行"——**必须保留 `target_id` 作为第三段**，否则不同实体的通知会被混成一条（这正是 2026-09-26 第 3 批修过的缺陷，见 `docs/architecture/modules/core.md` 的"聚合分组键"记录）；② 合并范围变大 → 单条消息条目数变多 → **可能触及 Telegram 4096 字符上限**（现状渲染已可能溢出）；③ 合并范围变大也会让 `aggregated_count` 语义变化，`notification_log` 的历史对比失真 |
| **验证方式** | ① 对照测试：同一批输入分别以 v1/v2 聚合，**逐组断言分组键与条数差异**（表驱动，禁止只测"能跑通"）；② 压力对照：构造 50 条同类事件（超过 `aggregate_max_events=50`）验证批上限仍生效；③ 生产观测：v2 打开后采样 ≥3 次真实批量链路，比对"通知条数 / 单条长度 / 429 次数"；④ 判别力：注入"去掉 target_id 段"的错误实现，断言有测试 FAIL |
| **回滚** | `NOTIFY_AGG_KEY=v1`（**无需回滚代码**） |

### 3.5 阶段 4：事件模型重构（业务事件与通知事件分离 + 治理重设计）
