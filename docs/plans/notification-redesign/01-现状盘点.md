## 一、Task 1：现状盘点报告

### 1.1 `NotificationMessage` 完整字段（实测）

数据类定义只有 13 个字段（`pilotstd/core/notification/channel.py:17-33`）：

| # | 字段 | 类型 | 默认 | 语义 | 消费方 |
|---|------|------|------|------|--------|
| 1 | `title` | `str` | 必填 | 标题 | 全部渲染器 / 日志 / 桌面 |
| 2 | `blocks` | `list[NotificationBlock]` | `[]` | 结构化消息体（**真正的正文载体**） | 渲染器 |
| 3 | `body` | `str` | `""` | 向后兼容：`blocks` 为空时回退 | 聚合摘要 / 日志 / 桌面 / Web |
| 4 | `level` | `str` | `"info"` | `info` / `warning` / `error` | 渲染器配色、聚合取最严重、桌面图标 |
| 5 | `standard_number` | `str \| None` | `None` | 关联标准号 | 日志列 |
| 6 | `event_type` | `str` | `""` | 事件键（**分组键的一半**） | 聚合器、日志、WS |
| 7 | `link` | `str \| None` | `None` | 站内跳转链接 | 渲染器（仅飞书列表块）/ 日志（**日志 API 不返回**） |
| 8 | `icon` | `str \| None` | `None` | 图标标识（`pi pi-*`） | 日志（**日志 API 不返回**） |
| 9 | `aggregated_count` | `int` | `1` | 合并条数 | 日志（**日志 API 不返回**） |
| 10 | `status` | `str` | `""` | 单条结果标记：`""`/`success`/`failure` | 桌面聚合的 `status` 入参 |
| 11 | `target_id` | `str` | `""` | 聚合分组子键 | 聚合器 `_group_key` |
| 12 | `elapsed_ms` | `int` | `0` | 单条耗时 | 聚合汇总 |
| 13 | `changed_at` | `str` | `""` | 状态变更时间（ISO） | 聚合展示 |

**缺口（对照目标架构所需字段，目标字段定义见 [02-目标架构.md](02-目标架构.md) §2.2）**：

| 目标字段 | 现状 | 后果（实测证据） |
|---------|------|-----------------|
| `message_id` | **不存在** | `notification_log.id` 是发送日志行号，不是渠道消息 ID；渠道 `send()` 不返回 ID |
| `correlation_id` | **不存在** | 同一次业务运行的 5 条通知（如扫描的 complete/empty/failed 分支）在数据层无关联键 |
| `status`（投递态） | 被**占用**为业务结果态（#10） | **命名冲突**：新模型需要 `delivery_status`/`ack_status`，不能复用 `status` |
| `actions` | **不存在** | 四渠道 payload 无 `reply_markup` / `actions` / `keyboard`（grep 0 匹配） |
| `callback_data` | **不存在** | 无入站端点，回调无处可去 |
| `attachments` | **不存在** | 图片/文件无法随消息下发（通知一直是纯文本/卡片） |
| `task_context` | **不存在** | 任务语义只能编码进 `event_type`（**这正是"按系统模块分类"的根因**） |

> 值得注意：`link` / `icon` / `aggregated_count` **写进了 `notification_log`**（`pilotstd/core/notification/_manager_ops.py:56-58` 的 11 列 INSERT），但 `GET /api/notification/logs` **显式只构造 10 个字段返回**（`docker/api/notification.py:368-382`），前端 TS 类型注释也确认了这一事实（`web/src/api/notification.ts:71-77`）。**即：库里有，接口不给，前端声明了又标注"不可用"**——三层各自记录了一次"这件事还没打通"。

**关键观察：分类维度是"系统模块"，不是"用户意图"。** 上表 10 组里，"下载/收藏"与"配额/提醒"对用户而言是同一件事（我要的文件到了没）；"扫描/归档/整理"对用户是同一件事（我丢进去的文件处理完了没）；而"安全"与"系统/任务"是**系统自己的事**（用户看的是"谁动了我的配置""备份坏了"）。**41 个 key 里没有一个能表达"这是同一件任务的前后两步"**——`download_started` 与 `download_complete` 只能靠 `standard_number` 事后关联，且 `favorite_download.py` 的两次调用不共享任何 ID（`favorite_id` 传了但构建器不读）。

### 1.4 现有治理机制与"事件 = 用户可见"假设的耦合点

三道门禁 + 一份 9 步准入清单，**全部以 `ALL_EVENTS` 为唯一事件全集**：

| 机制 | 实现 | 与"事件 = 用户可见"的耦合（逐条实证） |
|------|------|------------------------------------|
| **G-045 覆盖度基线** | `scripts/audit_notification_coverage.py`；对 `ALL_EVENTS` 每个事件校验 4 维度（i18n 三语齐备 / 出现在 e2e `EVENTS` 且 `trigger_file` 物理存在 / 安全类必须 `write_audit` / 术语登记） | **耦合最深**：① 事件全集 = `ALL_EVENTS`，即"注册了事件"**就等于**"用户可见"；② `tests/test_notification_e2e.py:739` 的 `assert len(EVENTS) == 41` **硬编码**——加一个事件必须同时改 6 个文件；③ 矩阵标题写死"41 事件 × 4 维度"（`notification_coverage.md:31`）；④ 唯一已知盲区 `desktop_toast` 的处置是"不登记 + 在 `[覆盖摘要]` 里声明"，并**明文写出**"登记会必然即红"（`notification_coverage.md:224`）——**这正是"SSOT 假设"不允许存在"非用户可见事件"的铁证**；⑤ 登记 `desktop_toast` 的触发条件之一是"引入第 2 个平台层事件时"（`:226`）——而新架构会引入**多个**平台层/内部事件（进度、回执、动作结果） |
| **G-046 通知链路审计** | `scripts/audit_notification_chain.py`（零基线，`--strict`） | 判定对象是"构建器"：空文本风险、缺空值守卫、静默吞错。隐含假设"**每件事都由 `_build_<x>_message(data)` 产出**"——一旦内容类型（进度条、图片、按钮组）不再由构建器直出，审计口径必须重写 |
| **G-044 术语与禁用词** | `scripts/check_terminology.py` + `docs/governance/glossary.json` | 作用域限 `notification.*`，键命名约定 `notification.<category>.<event>.<field>`（三级以上）。隐含假设"**文案键以事件名为中间段**"——新增的"任务视角"文案（不隶属任何单一事件）没有合法命名位置 |
| **9 步准入清单** | `docs/governance/notification_coverage.md:121-129` | 9 步全部围绕"加一个 `ALL_EVENTS` 条目"：注册常量 → 加构建器 → 加映射 → 加三语键 → 术语登记 → 加默认规则 → 加 e2e 条目 → 安全类加 `write_audit` → 跑门禁。**步骤里根本没有"内容类型""动作""回调"这三类产物的位置**，也没有 `user_id`/`correlation_id` 的登记要求（因此本篇 §1.2 里 7 个事件藏着 `user_id` 却无人管） |

**一句结论**：现行治理体系把"**注册事件**"与"**承诺用户可见**"绑成了同一件事。一旦业务事件（41 个，内部语义）与通知事件（6–8 个，用户视角）分离，**G-045 的输入就会从 41 变成两组数字**，而 `assert len(EVENTS) == 41`、矩阵标题、`desktop_toast` 的豁免声明会**同时失效**——这是阶段 4 必须一次性完成的结构性原因（见 [04-影响面.md](04-影响面.md) §4.3）。
