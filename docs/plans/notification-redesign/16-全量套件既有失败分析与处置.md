## 二、根因一：测试库隔离**只 patch 了一处绑定**（主体原因）

`tests/conftest.py` 的 autouse 夹具 `_isolate_fernet_db` 只做了：

```python
monkeypatch.setattr("pilotstd.core.config.paths.get_db_path", lambda: str(tmp_path / "pilotstd.db"))
```

但生产代码里有大量 `from pilotstd.core.config import get_db_path` ——**导入即绑定名字** ⇒ 这些调用点读到的是
**未打补丁的原函数** ⇒ 在全量运行中**直连开发库 `data/pilotstd.db`**：多个测试互相写同一个库，
后跑者读到前者的残留（实测表现：**迁移 checksum 报错**、docker_api/manager/cli/health 等 60+ 项在
"全量顺序"下失败、单独跑却全绿）。

**处置（已实施，`tests/conftest.py`）**：把**包级再导出**一并重定向：

```python
db_path = str(tmp_path / "pilotstd.db")
monkeypatch.setattr("pilotstd.core.config.paths.get_db_path", lambda: db_path)
monkeypatch.setattr("pilotstd.core.config.get_db_path", lambda: db_path, raising=False)
```

**验证**：修复后 `test_docker_api + test_manager + test_cli + test_health` **联合跑 91 passed**（5 skipped）。

## 五、根因四：**1 项真实产品缺陷**（保留失败信号，单独立批）

`test_scheduler_timer_drift::TestRenewalNotOverProvisioned::test_final_send_is_close_to_deadline`
断言"强制发送贴近上界（≥0.5×MAX）"，实测 `elapsed ≈ 0.000s`。

**根因（读码定位）**：`aggregate_buffer._on_timer()` 的**首轮判据**

```python
remaining = MAX_WINDOW_SECONDS - elapsed            # elapsed ≈ 0
if remaining > min(self._window * _TIMER_SLEEP_RATIO, _MAX_TIMER_SLEEP_CAP):
    ...  # 正常轮次：flush + 续期
else:
    ...  # 强制发送并清除 _window_start
```

当 `window` 相对 `MAX` **偏大**时该条件**不成立** ⇒ 首次回调即走"强制发送"分支 ⇒
**大窗口配置下聚合形同虚设**（不是测试错配：改大窗口后亦复现，与 window 大小直接相关）。

**处置**：**不改测试掩盖**（也不使用 `xfail`/`skip`——P-104），在用例 docstring 写明诊断与"单独立批"结论；
修法属**聚合热路径的行为修改**，须配套回归与灰度量测，故不夹带在 Step 4 批次里。
