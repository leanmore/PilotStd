## 二、结论速览（六条）

1. **现状不是"通知做得不好"，而是"通知系统只完成了单向广播这一半"。** 发送侧完整（41 事件 / 41 构建器 / 51 调用点 / 240 i18n 键 / 4 渠道 / 3 道门禁）；**接收侧完全为空**（全库无入站端点，渠道契约只有 `send() -> bool`，无消息 ID、回执、按钮、编辑）。
2. **"WebSocket 广播"是死代码**：生产唯一构造点不传回调（`pilotstd/manager/facade/_base.py:250/:271`），`_manager_ops.py:155-156` 恒早退；服务端实现已在 `1784ecbe` 删除 554 行。
3. **Web 端通知铃铛是装饰性的**：`web/src/composables/useNotification.ts:17` 的 `messages` 是恒空 `ref([])`，无轮询、不调 `getNotificationLogs` → 角标恒 0、列表恒空。
4. **用户配置入口比后端少 6 项**：前端硬编码 35 项（`NotificationConfig.vue:58-94`），后端 41 项；缺的 6 项里有 4 个是**有意绕过配置层**的安全事件。
5. **五个假设中两个被证伪一半**："单向广播"属实（比想象更彻底）；"41 个用户可见事件"不成立（**只有 35 个可配**）。
6. **核心判断**：不改 41 个构建器（文案与 i18n 契约是最贵的资产），而是**在它们之下加"业务事件 → 通知事件"映射**、**在它们之上加"消息身份 + 动作 + 渠道能力矩阵"** → 阶段 0–3 可做到零行为变更 + 零文案改动。

**三处硬阻塞**（详见 [01-现状盘点.md](01-现状盘点.md) §1.4 与 [04-影响面.md](04-影响面.md) §六）：① 用户归属缺失（表按用户设计、投递不按用户）；② 群机器人拿不到 message_id（无 ID 则无消息编辑）；③ 回调端点会被鉴权中间件拦死（白名单 + 逐渠道验签是安全边界）。

## 三、裁决结果（2026-10-02）

15 项全部裁决，**11 项同意原建议**，**4 项不同**：

| # | 决策点 | 裁决 |
|---|--------|------|
| Q1 | 事件配置入口 | **B 双层**：7 类为主 + 折叠的 41 项细分（原建议 A） |
| Q2 | 强交互渠道 | 同意分两步：**先 Telegram**，再飞书自建应用 |
| Q3 | 字段命名 | 同意 A：追加 `delivery_status`/`ack_status`，**不动** `status` |
| Q4 | 聚合器 | 同意保留，但**归入阶段 2.5**（独立开关 `NOTIFY_AGG_KEY`，默认 v1） |
| Q5 | 按钮默认开关 | 同意 B：**默认只读**，需显式开启"允许远程操作" |
| Q6 | 多用户收件人 | **降级为技术债**（单用户部署）；阶段 1 **顺手**改构造时注入（默认 1） |
| Q7 | 回调权限 | 同意 B：按消息收件人 + 动作白名单 + 角色**重新鉴权** |
| Q8 | 二次确认 | 同意 A：`retry`/`mark_done` 需确认 |
| Q9 | Task 落地 | 同意 A：投影 `task_queue`，**不新增主表**；`fetch_task` 归并列入阶段 4 待议 |
| Q10 | `desktop_toast` | 同意 A：借阶段 4 正式登记 |
| Q11 | 消息块快照 | 同意 B：阶段 2 起存 `blocks_json` |
| Q12 | 能力缺失降级 | 同意 A：降级为文本，**不惩罚投递** |
| Q13 | Web 实时通道 | 同意 A，且**提到阶段 0 优先做**（先修恒空数组） |
| Q14 | 配置兼容 | 同意 A：平滑双读 |
| Q15 | i18n 命名空间 | 同意 A：新增 `notification.<notify_event>.*`，不重组存量 |

**两项结构性调整**：① 原四阶段**拆为六阶段**（新增阶段 0 与阶段 2.5）；② 新增**一键回滚** `NOTIFY_REDESIGN_STAGE=0|1|2|2.5|3|4`（默认 = 前一阶段稳定值）+ 阶段 2.5 独立开关 `NOTIFY_AGG_KEY=v1|v2`。
