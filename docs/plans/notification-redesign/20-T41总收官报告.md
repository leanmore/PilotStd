## 五、附录：《`event_spec_data.py` 1b 拆分豁免说明》（用户 2026-10-07 裁定）

**体检结论（实测）**：
1. **内容构成**：docstring + 2 个 import + **一条** 484 行 `EVENT_SPECS: tuple = (...)`（42 条，13 个业务分组）
   ⇒ **纯静态单表**；全库检索 `update(`/`append(`/`setdefault(`/`pop(` 等**零命中** ⇒ **无"伪常量"隐藏可变状态**；
2. **导入扇出**：真实外部 import **仅 1 处**（`event_spec.py` 的延迟导入）⇒ 消费模式高度收敛；
3. **最小可拆族及其代价**：可迁出「安全告警族」（42 行 ≈35 有效行）使主文件降至 ~382，
   **但**需同批：改 G-045 读取器（支持组合元组 `(*A, *B)`，约 25 行新逻辑）+ 重写 `test_event_spec` 的
   AST 基线（"42 条字面量"改为跨模块口径）+ 引入模块间耦合。

**裁定**：**不做物理拆分**（用户 2026-10-07）。理由：① 该文件的认知模型是**扁平**的（一表、42 条同构记录），
按族拆分会把"线性查找"变成"跨模块跳转 + 心智拼接"，**违背 G-010"降低认知负载"的本意**；
② 为减 ~35 行而改动门禁读取器与契约基线，属"**为凑指标制造技术债**"；③ 417 行处于 **warning 档**、
未越 500 阻断档，不阻断交付。

**给 P7 的提示**：若未来该文件**突破 500 阻断档**或**新增变动频繁的族**，再评估"按族拆分 + 门禁读取器升级"；
彼时应**先行**完成读取器的组合元组支持（可独立小步、独立单测），再拆族。
