## 1.1 `useNotification.ts` 改造方案

### 现状（实测）

| 事实 | 证据 |
|------|------|
| `messages` 是恒空 `ref([])`，从不被填充 | `web/src/composables/useNotification.ts:17` |
| 只 import 了 `markNotificationRead`，**没调 `getNotificationLogs`** | `:4` |
| 无轮询 / 无定时器 / 无 WS / 无可见性感知 | 全文 42 行，无 `setInterval` / `visibilitychange` |
| 唯一生产消费者是 `NotificationBell.vue` | `NotificationBell.vue:10`（import）、`:14`（调用）；挂载点 `AppHeader.vue:73` |
| 因此铃铛角标恒 0、下拉恒空 | 由上述三条推出（组件读 `messages` 与 `unreadCount`） |
| `RouteTag` 已含 `/notification-logs`，可传 routeTag | `web/src/types/route-tag.ts:9`；`getNotificationLogs` 支持第二参 `routeTag`（`api/notification.ts:98-107`） |

### 目标行为

| 项 | 设计 | 理由 |
|----|------|------|
| **数据源** | `getNotificationLogs({ page: 1, page_size: 20 })`（**一拍两用**：列表与未读数同时刷新） | 后端只返回**当前页** `items`（`docker/api/notification.py:368-382`，10 字段），无"最近 N 条"接口；分页 `page_size` 上限 100（`Query(20, ge=1, le=100)`，`:344-346`） |
| **间隔** | `POLL_INTERVAL_MS = 30_000`（30 秒） | 单用户自建服务、通知非紧急；一个请求/30s 对 NAS 无感。设为具名常量便于调 |
| **首次请求** | `onMounted` 立即拉一次，然后起定时器 | 首屏不等 30 秒 |
| **可见性感知** | 页面隐藏（`document.hidden === true`）→ **停定时器**；恢复可见 → **立即拉一次 + 重启定时器** | 后台标签页不产生无谓请求（NAS 上 24 小时开着的浏览器尤其值钱） |
| **卸载** | `onUnmounted` 停定时器、摘 `visibilitychange` 监听、引用计数归零 | 防泄漏（现有测试用 `mount()`，卸载路径会被覆盖） |
| **多实例共享** | 模块级单例：`messages` / `loading` / `error` / `refresh` 在模块作用域；**定时器按引用计数**（首个订阅者启动、最后一个卸载停止） | 现在只有一个消费者，但 `useNotification()` 是 composable，多处调用会产生 N 个轮询循环（N 个组件 = N 倍请求） |
| **错误处理** | 失败**保留上次数据**（不清空），记录 `error` 与 `console.warn`；连续失败不额外处理 | Web 端已有的同类实践（`markAsRead` 的 `console.error`，`:32`）。清空会让角标"闪没"，比不刷新更差 |
| **手动刷新** | 暴露 `refresh()`（返回 Promise） | `NotificationBell` 的下拉"打开即刷新"、以及测试可控（不依赖真实定时器） |

### 必须做的一处**数据映射**（关键细节，容易漏）

后端 `items` 的字段与前端 `NotificationMessage` **不一一对应**，且 `is_read` 是 **0/1 数字**：

| 后端字段 | 前端字段 | 处理 |
|---------|---------|------|
| `is_read: number`（0/1） | `is_read: boolean` | `Boolean(item.is_read)` —— 否则现有 `messages.filter(m => !!m.is_read)` 与 `!msg.is_read` 判断会**把 0 当 false 但类型不符**，且测试断言 `toBe(false)` 会失败 |
| （无 `level`） | `level` | 后端**完全没有**该字段 → 映射时统一填 `'info'`；**同时把类型从 `'info' \| 'warn' \| 'error'` 纠正为 `'info' \| 'warning' \| 'error'`**（后端取值是 `warning`，`channel.py:24`；现有 `'warn'` 拼写在 `useNotification.ts:11`，是既有类型错误，`NotificationBell` 不消费该字段故无实际影响） |
| `body` | `body` | 后端 `body` 可能是 `null`（列可空）→ `item.body ?? ''` |
| `title` | `title` | 同上，`?? ''` |
| 无 `link` / `icon` / `aggregated_count` | — | **接口不返回**（`docker/api/notification.py:71-72` 前端注释已确认）→ 不声明、不消费，阶段 0 不碰 |

### 已知限制（须写进交付说明，不掩盖）

1. **角标是当前页未读数，不是全量未读数**：`recentMessages = messages.slice(0, 10)`（`NotificationBell.vue:17`），角标由 20 条当前页算得。全量未读有专门的 `GET /api/notification/unread-count`（`docker/api/notification.py:404`），但**使用它需要新增一次请求**（每 30s 两条请求）。阶段 0 采用"一拍两用"，**若你要求角标精确，则改为两请求**（代价：NAS 上的请求量翻倍）。
2. 若未来接 WebSocket/SSE，本方案的 `refresh()` 就是接缝（只需把定时器换成事件驱动，状态层不动）。

# 第二部分：阶段 1 实施方案（三批，每批独立交付）

**总原则**：每批只做"加字段 + 加列 + 扩搬运/白名单"，**零行为变更、零文案改动**。每批后跑全量回归 + 快照测试，并确认 `git diff` 不含 `pilotstd/i18n/*.json`、`web/src/locales/*`。

## 2.1 三批字段与迁移

| 批次 | 字段（`NotificationMessage`） | 新列（`notification_log`） | 迁移 | `CURRENT_SCHEMA_VERSION` |
|------|------------------------------|--------------------------|------|------------------------|
| **1a 核心身份** | `message_id: str = ""`、`correlation_id: str = ""`、`delivery_status: str = "pending"`、`ack_status: str = "none"` | 同名 4 列（`TEXT`，可空/default） | `@migration(62)` | 61 → **62** |
| **1b 任务视角** | `task_id: str = ""`、`notify_event: str = ""`、`content_type: str = ""`、`task_context: dict = {}` | 同名 4 列（`task_context` 存 JSON 文本） | `@migration(63)` | 62 → **63** |
| **1c 交互** | `actions: list = []`、`callback_data: str = ""`、`attachments: list = []`、`channel_message_ids: dict = {}` | 同名 4 列（list/dict **存 JSON 文本**） | `@migration(64)` | 63 → **64** |

**迁移函数形态（每批同构，幂等）**：

```python
@migration(62)
def _migrate_v62_notification_log_identity(db: Any) -> None:
    """notification_log 追加通知身份列（阶段 1a，零行为变更）。"""
    for col, decl in (
        ("message_id", "TEXT DEFAULT ''"),
        ("correlation_id", "TEXT DEFAULT ''"),
        ("delivery_status", "TEXT DEFAULT 'pending'"),
        ("ack_status", "TEXT DEFAULT 'none'"),
    ):
        try:
            db.execute(f"ALTER TABLE notification_log ADD COLUMN {col} {decl}")
        except Exception:
            pass  # 列已存在（幂等；与 v27/v29/v40 等既有迁移同款防御）
```
> 与既有迁移同风格（`_migrate_v27_notification_aggregation` 的 `try/except pass` 逐列追加）。**注意 R-009（SQL 安全）**：列名与类型是**同文件常量元组**，非外部数据拼接；同时 `ALTER TABLE` 的列名不可参数化，这是 SQLite 的固有限制，故必须用同文件常量。

**INSERT 扩展（`pilotstd/core/notification/_manager_ops.py:56-58`）**：每批把新列加入 INSERT 列表与实参，**旧 11 列的列名顺序与取值来源不变**（这是"逐列相等"判据的前提）。`_log()` 签名不改（值取自 `msg` 的新字段），**不新增形参**。

**回滚方式（每批）**：`NOTIFY_REDESIGN_STAGE=0` + 代码回退（见 [03-实施路径.md](03-实施路径.md) §3.0）。迁移是**追加列**，**不做 `DROP COLUMN`**（生产 SQLite 版本可能不支持；且历史行里的 NULL 无害）。
