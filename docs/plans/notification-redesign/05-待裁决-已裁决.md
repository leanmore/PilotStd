## 二、原始待裁决清单（含裁决行）

> 每项给出：**问题** / 备选 / **我的建议** / 影响范围。建议仅供参考（R-012 先批后做）——**裁决行由用户在 2026-10-02 填写**。

### A 组：事件与配置（决定阶段 4 的形态）

**Q1. 是否保留 41 个事件的用户配置入口？**
- A. 完全切到 7 类通知事件（旧 41 key 只做迁移读取）
- B. 双层：7 类为主 + 折叠的"高级：按业务事件细分"
- C. 保留 41 项不动（放弃三层分离的配置收益）
- **建议 A**。理由：实测前端硬编码 35 项与后端 41 项**已经不一致**（缺 6 项），说明"逐事件配置"从来就没真正做到；41 项对用户是认知负担（[01-现状盘点.md](01-现状盘点.md) §1.2 的按模块分类）。
- **✅ 裁决：B（双层）**。理由：个人项目用户可能想细调某几条，一刀砍到 7 类会丢失表达能力，双层不增加实现成本。

**Q2. 强交互（按钮 + 消息编辑）优先支持哪些渠道？**
- A. 只做 Telegram（改动最小，官方 API 完备，无需租户审批）
- B. Telegram + 飞书自建应用（覆盖国内主用场景，但需管理员审批）
- C. 四渠道全做（钉钉/企微在群机器人形态下**做不到编辑**，C 不可行）
- **建议 B，分两步**：先 A（验证闭环），再 B（补齐国内场景）。**注意**：钉钉与企微群机器人形态下**没有消息编辑接口**，这不是工作量问题。
- **✅ 裁决：同意分两步**——阶段 3 先做 Telegram（验证闭环），再做飞书自建应用。

**Q3. 消息模型新字段的命名与版本策略**
- A. 追加新字段（`delivery_status`/`ack_status`），旧 `status` 保留原语义
- B. 重命名旧 `status` → `outcome`，`status` 让给投递态
- **建议 A**。理由：`status` 已被 41 个构建器中的若干写入（如 `archive_complete`），重命名会波及构建器与快照测试，收益（省一个字段名）远小于风险。
- **✅ 裁决：同意 A**。

**Q4. 聚合器去留**
- A. 保留聚合器，聚合键改为 `notify_event × correlation_id × target_id` 三元组
- B. 取消聚合，改为"任务视角天然去重"（同一 Task 只发 3 条）
- **建议 A**。理由：聚合器解决了实测的真实事故（2026-09-21：1119 条通知中 622 条被 Telegram 429 拒绝，见 `defaults.py:86-88` 注释）；B 会让批量链路重新暴露。
- **✅ 裁决：同意 A，但归入阶段 2.5**（独立灰度 + 开关 `NOTIFY_AGG_KEY=v1|v2`，默认 v1；灰度通过后切 v2）。

### B 组：交互与安全（决定阶段 3 的边界）

**Q5. 交互按钮的默认开关：哪些通知默认带按钮？**
- A. 全部 `anomaly_alert` 默认带 `retry`/`ignore`（开箱即可点）
- B. 默认全部只读（`view_detail`），需用户在设置页显式开启"允许远程操作"
- **建议 B**。理由：`retry` 会写 `task_queue`（改变系统状态），而通知渠道的凭证安全等级低于 Web 登录会话（回调只验签，无第二因子）；默认开启等于把"能改系统状态的操作"暴露给"任何能拿到渠道回调权限的人"。
- **✅ 裁决：同意 B**。

**Q6. 分发范围：多用户下的收件人如何确定？**（原列为"三处硬阻塞"之一）
- A. 保持现状（`user_id=1` 单用户）
- B. 按 `event_data.user_id` 回退到 `user_id=1`（实测 7 个事件载荷里有 `user_id`）
- C. 全链路补 `user_id`：`send_event(..., user_id=)` + 51 个调用点逐一传 + `StandardManager` 单例与入口 user 注入（**改动最大**）
- **建议 B 为阶段 2 的第一步，C 单独立项**。理由：`notification_policy` 表已是 per-user（`UNIQUE(user_id, channel)`），但 `NotificationManager` 由 `facade/_base.py:250/:271` 硬编码 `user_id=1`——**表按用户设计、投递不按用户**。B 是零破坏的第一步（7/41 覆盖率），C 触及 `StandardManager` 单例构造，属独立工程。
- **✅ 裁决：降级为技术债，不作为阻塞**。理由：本项目是单用户部署（`192.168.1.18:9028`），`user_id=1` 就是唯一用户。但阶段 1 **顺手**把硬编码改为构造时注入（默认仍为 1，为将来留门），**不阻塞任何阶段推进**。
- **落地方式（阶段 1 顺手项，见 [06-阶段0-1实施方案.md](06-阶段0-1实施方案.md) §1.4）**：`NotificationManager.__init__` 已有 `user_id` 形参，只需把 `facade/_base.py:250/:271` 的实参从字面量 `1` 改为"注入值，默认 1"；**51 个调用点不改，`send_event` 不加 `user_id` 形参**。

**Q7. 回调动作的权限模型？**（回调只验签，无登录态）
- A. 按渠道凭证信任（能收到回调 = 有权操作）
- B. 按"消息记录的收件人 + 动作白名单 + 角色"重新鉴权（`retry`/`mark_done` 要求管理员）
- **建议 B**。理由：`callback_data` 来自外部可篡改——**服务端绝不能信任回调里的身份信息**。动作白名单（[02-目标架构.md](02-目标架构.md) §2.2）与 `requires_confirm` 是配套的最低防线。
- **✅ 裁决：同意 B**。

**Q8. 破坏性动作是否必须二次确认？**
- A. 是（点 `retry` → 编辑消息为"确认重试？[确认][取消]"）
- B. 否（点了即执行）
- **建议 A**，且仅对 `retry`/`mark_done` 两个改变状态的动作。代价是多一次回调往返（飞书/Telegram 均支持）。
- **✅ 裁决：同意 A**。

### C 组：模型与治理（决定阶段 1、4 的落地细节）

**Q9. Task 实体落地方式**
- A. **投影 `task_queue`**（不新增主表；`fetch_task` / `task_execution_history` 保持现状）
- B. 新增 `notification_task` 表（与 `task_queue` 双写）
- **建议 A**。理由：`task_queue`（`_migrate_v16_v49.py:168-191`）已有 `total_items`/`completed_items`/`failed_items`/`status`/`started_at`/`finished_at`/`retry_count`——**就是 Task 所需字段全集**；新增表必然双源漂移。附带待裁决：`fetch_task`（公告专用）是否在阶段 4 一并归并到 `task_queue`？
- **✅ 裁决：同意 A**；`fetch_task` 归并**列入阶段 4 待议**。

**Q10. `desktop_toast` 是否借阶段 4 正式登记进事件 SSOT？**
- A. 登记（引入"平台层事件"分类，`notification_coverage.md:226` 的触发条件已满足）
- B. 继续不登记 + 在覆盖摘要声明
- **建议 A**，且作为阶段 4 的原子批次一部分。理由：新架构会引入**多个**平台层事件（进度、回执、动作结果），继续用"摘要声明"逐个解释会腐化。
- **✅ 裁决：同意 A**（借阶段 4）。

**Q11. 消息块快照是否入库？**
- A. 只存 `body`（现状：`notification_log.body` 存渲染后的纯文本）
- B. 额外存 `blocks_json`（结构化快照，支持 Web 端富渲染与"历史消息重新渲染"）
- **建议 B（阶段 2 起）**。理由：Web 端目前只显示 `title`/`body`——`notification_log` 里有 `blocks` 的结构信息却被丢弃；存 JSON 是 Web 通知中心可用的前提。
- **✅ 裁决：同意 B**（阶段 2 起）。

**Q12. 渠道能力缺失时的降级策略**
- A. 降级为文本/链接（照发）
- B. 该渠道不发该消息
- **建议 A**。理由：B 会造成"用户在钉钉上永远收不到异常告警，因为钉钉不支持按钮"——**能力缺失不该惩罚投递**。
- **✅ 裁决：同意 A**。

**Q13. 是否重建 Web 实时通道？**
- A. 不做（Web 保持轮询/静态；`useNotification` 的恒空数组可先修成轮询 `GET /api/notification/logs`）
- B. 重建 WebSocket（提交 `1784ecbe` 刚删除 554 行）
- **建议 A（先修恒空数组）**。理由：`useNotification` 现在**根本没调 `getNotificationLogs`**（`useNotification.ts:4` 只 import `markNotificationRead`）——在讨论 WS 之前，先把"HTTP 轮询模式"这个注释兑现（**这是全链路最便宜、收益最直接的一处修复**）。
- **✅ 裁决：同意 A，且提到阶段 0 优先做**。

**Q14. 事件配置的兼容性策略**
- A. 平滑（旧 41 key 保留可读，双读一段时间）
- B. 硬切（迁移脚本一次性转换，旧 key 立即失效）
- **建议 A**。理由：`NotificationConfig.vue:139-155` 已是"双读"结构（先读 `config.rules`，再被策略 API 覆盖），沿用该结构做兼容的改造成本最低。
- **✅ 裁决：同意 A**。

**Q15. 术语表与 i18n 契约如何适配新命名空间？**
- A. 新增 `notification.<notify_event>.*` 命名空间，与现有 `notification.<category>.<event>.*` 并存
- B. 全量重组现有 240 键
- **建议 A**。理由：G-044 的键命名门禁要求"三级以上 + 二级分类白名单"，新增一级命名空间最省事；全量重组会触碰 41 个构建器与 14 处快照断言（**违反本设计的"零文案改动"约束**）。
- **✅ 裁决：同意 A**。
