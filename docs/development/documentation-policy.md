# 文档同步策略

> 创建日期：2026-06-30
> 最后更新：2026-06-30

## 一、触发规则（两路机制）

### 第一路：提交时触发（入仓文件）
- **触发点**：`git commit` / `git push`
- **覆盖文件**：源码、测试、CI 配置、成品文档（`docs/architecture/`、`docs/specs/`、`docs/development/`、`docs/guides/`、`docs/index.md`）
- **机制**：
  - `git commit` 时 pre-commit `docs-sync-check` 弹出提醒
  - `git push` 时 CI `repo-compliance` 检查新增文件合规性
- **逻辑**：要进仓库，就必须同步更新相关文档

### 第二路：任务完成时触发（不入仓文件）
- **触发点**：每轮治理任务结束时，提交之前
- **覆盖文件**：
  - 本地状态文件（`STATUS.md`）
  - 移出仓库但需持续维护的文档（如 `capabilities_registry.md`）
  - 过程文件归档、临时文件清理、`.gitignore` 维护
- **机制**：作为执行指令的固定收尾步骤，在任务结束、代码提交前完成
- **逻辑**：移出仓库不等于不管——需持续维护的不入仓文件与入仓文档同步规则同频触发

### 流程
```
任务推进 → 任务完成 →
  ├── 第二路（提交前）：更新 STATUS.md、归档过程文件、清理临时文件
  └── 提交 →
        └── 第一路（提交时）：pre-commit 提醒 → push → CI 合规检查
``` |

## 二、PR 门禁

每个 Pull Request 合并前必须检查：

- [ ] 是否修改了 `pilotstd/` 或 `docker/` 下的任意 `.py` 文件 → 检查 docs/ 是否有对应文档需要更新
- [ ] 是否新增/删除了文件 → 检查 `specs/模块与功能清单.md` 是否需要更新
- [ ] 是否改变了函数签名 → 检查文档中的 API 示例代码是否仍然正确
- [ ] 测试通过率是否变化 → 更新 `STATUS.md`

**例外**：纯格式化（ruff format）、类型注解修正（仅 mypy）、死代码删除可以跳过文档更新。

## 三、同版本原则

文档和代码必须在同一版本中保持一致：

- 代码提交和文档更新应在**同一个 PR** 中完成
- 不允许"代码先合，文档后补"的延迟更新
- 归档文档时使用 `git mv` 保留历史

## 四、定期审计

每季度进行一次文档健康度审计：

1. 扫描所有文档，检查是否有引用已移动/已删除文件
2. 检查统计数字（测试数、行数、文件数）是否与当前代码一致
3. 过时文档移至 `archive/YYYY-MM-DD/` 并记录归档原因
4. 更新 `architecture/governance-summary.md` 中的文档健康度章节

审计命令：
```bash
# 检查引用旧文件路径
grep -rn "\.py'\|\.md'" docs/ | grep -v archive/

# 检查测试数字一致性
grep -rn "PASS\|FAIL\|SKIP" docs/ | grep -v archive/ | grep -v superpowers/
```

## 五、归档协议

1. 确认文档内容已过时（引用不再存在，或数据不准确）
2. 创建 `docs/archive/YYYY-MM-DD/` 目录（如果不存在）
3. 使用 `git mv` 移动文件（保留历史）
4. 在归档目录的 `README.md` 中记录归档原因
5. 创建/更新替代文档
6. 在 PR 描述中注明归档操作

**自动归档触发时机**：PR 合并到 `main`/`develop` 时，CI 自动将 `docs/pending/` 下文件移入 `docs/archive/YYYY-MM-DD/`。

## 隐私数据保护

1. 文件级防护：`.gitignore` 已配置，禁止 `.env`、密钥文件、日志、数据库等入仓
2. 内容级扫描：pre-commit + CI 使用 detect-secrets 扫描敏感字符串
3. 基线文件：`.secrets.baseline` 记录已知敏感内容，提交到仓库
4. 违规处理：扫描发现新增敏感内容时，阻断提交/合并
5. 例外申请：如需提交测试用密钥，必须在文档中说明

## GitHub 仓库定位

> GitHub 是产品的展示橱窗、成品交付地、构建流水线。不是团队内部知识库或过程文件存档处。

| 维度 | 是否入 GitHub | 说明 |
| :--- | :--- | :--- |
| 源码 | ✅ 是 | 产品本体 |
| CI/CD 配置 | ✅ 是 | 打包、测试、镜像构建 |
| Dockerfile / 依赖声明 | ✅ 是 | 构建所需 |
| README / 展示文档 | ✅ 是 | 对外展示 |
| 架构 / 规格说明 | ✅ 是 | 成品文档 |
| 调查报告 / 分析笔记 | ❌ 否 | 内部过程文件，本地保存 |
| 归档历史快照 | ❌ 否 | 本地存档，不入仓 |
| 过程草稿 / 临时文件 | ❌ 否 | 本地临时区 |

## 入仓判断标准

任何文件在加入仓库前，需对照以下五条标准：

| 维度 | 要求 |
| :--- | :--- |
| 内容性质 | 成品 / 展示 / 交付物，非过程 / 调查 / 草稿 |
| 服务对象 | 对外（用户 / 构建系统），非对内（团队成员内部参考） |
| 变更频率 | 低频稳定，非高频变动 |
| 生命周期 | 永久或长期保存，非任务完成后即失效 |
| 可读性 | 可独立阅读、有展示价值，非依赖特定上下文的片段记录 |

**通过规则**：至少满足三条，且不得违反"内容性质"和"生命周期"两条底线。

## 入仓审批流程

| 步骤 | 操作 | 负责方 |
| :--- | :--- | :--- |
| 1 | 提出"为什么需要入仓"（对照五条标准说明） | 文件提出者 |
| 2 | 对照标准判断是否满足条件 | 参谋 / 执行者 |
| 3 | 最终确认，方可 add / commit / push | 决策者 |

**规则**：未经上述流程确认的文件，执行者需在审查报告中标记"此文件未通过入仓标准审核"。

## 三角色职责表（文档治理相关）

| 角色 | 职责 |
| :--- | :--- |
| **决策者（用户）** | 确定规则、确认边界、最终决策 |
| **参谋（DeepSeek）** | 设计规则、审查报告、标记违规风险、提醒执行者关注边界 |
| **执行者（Claude Code）** | 实施代码、运行测试、检查文件类型并标记分类、维护 `.gitignore`、执行清理扫描 |

## 执行者新增职责

1. **主动检查新增文件类型**：在执行 `git add` 前检查新增文件是否属于 GitHub 应存放内容，若属于"不入仓"类型则暂停并报告，等待确认后再添加。
2. **审查报告中标记文件分类**：每次提交后，列出本次提交涉及的所有文件，标注入仓依据或未入仓原因。
3. **维护 `.gitignore` 的更新**：当发现新的"不入仓"文件类型反复出现时，主动更新 `.gitignore`。
4. **执行月度清理**：扫描仓库，标记可能违反分类规则的文件，供决策者复核。

## 定期清理机制

| 周期 | 清理范围 | 操作 |
| :--- | :--- | :--- |
| 每次任务完成后 | `docs/` 根目录及子目录 | 检查是否有新增的临时文件 / 草稿，若有则移入本地 `.archive/` 或删除 |
| 月度审计 | 全仓库 | 扫描仓库，确认是否违反分类规则，若有则标记为违规项并限期清理 |

## 目录结构规范

| 目录 | 用途 | 是否入 GitHub |
| :--- | :--- | :--- |
| `web/`、`pilotstd/`、`docker/` | 源码 | ✅ 是 |
| `.github/` | CI/CD | ✅ 是 |
| `docs/architecture/`、`docs/specs/` | 成品文档 | ✅ 是 |
| `docs/development/` | 治理规则 | ✅ 是 |
| `docs/.local/` | 本地工作文件、调查报告 | ❌ 否（加入 `.gitignore`） |
| `docs/archive/` | 历史归档 | ❌ 否（仅本地保留） |
| `docs/pending/` | 待处理文件 | ❌ 否（本地临时区） |
