# 25 · 修复就绪度与颗粒度标准

> 回答：**现在的认知够不够直接修？**  
> 结论：**够判断方向、够出方案，不够对所有问题直接动代码；生产数据修复需额外 L4 证据。**

---

## 一、颗粒度分级

| 层级 | 内容 | 用途 |
|---|---|---|
| **L0 功能地图** | 有哪些功能域、入口、表 | 知道“有什么” |
| **L1 主流程** | 入口→阶段→输出 | 知道“怎么走” |
| **L2 状态/数据** | 状态机、读写表、关键分支 | 知道“为什么这样” |
| **L3 函数/事务/异常** | 具体函数、条件、事务、错误路径、测试 | **改代码的最低要求** |
| **L4 单实例证据** | 单条日志/DB 行/请求/批次 | **修数据、对账、复现的最低要求** |

## 三、改代码的最低颗粒度

每个修复必须能回答：

1. **现象/复现**：哪条日志、哪条数据、哪个入口；
2. **调用链**：入口 → 函数 → 表/文件，含 `file:line`；
3. **输入/输出/异常**：正常、空、重复、超时、并发；
4. **数据前置/后置**：读哪张表、写哪张表、约束/事务；
5. **影响面**：Web / Win / CLI / Docker / 通知；
6. **测试**：失败测试 + 相关回归；
7. **回滚/验证**：怎么证明修对、怎么退回；
8. **文档**：更新哪份 onboarding/reference。

缺 2/3/4 中任一项，就还停在“知道大概”，不应动代码。

---

## 四、修数据的最低颗粒度

- 单条记录级映射（old_key → new_key）；
- 冲突/无匹配/重复逐条列出；
- 事务前后行数/唯一键断言；
- 备份、dry-run、mapping.csv、回滚；
- 生产执行窗口与批准。

709 条方案已到这一层。

---

## 五、结论

- **方向/方案：够。**
- **低风险小修（注释、重试）：够。**
- **主链结构修复（Web 归档、monitor、空目录、有效性）：不够，需要 L3 调用链 + 目标问题相关 L4 证据。**
- **生产数据修复：方案够，执行需 L4 + 批准。**

> 下一阶段不应“按功能域再泛读一遍”，而应**按选定的修复问题做 L3/L4  dossier**；一个问题一份，不再全项目铺开。
