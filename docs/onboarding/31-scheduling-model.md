# 31 · 排期模型：容量约束下的关键路径排程（运筹学口径）

> 本文是 `AGENTS.md §0.0` 执行纪律的**展开版**。目的：把「并行/串行」从直觉判断
> 换成可计算的排程决策，减少总用时（makespan）与返工。
>
> 适用：多问题清单 / 任务包 / 任何需要外派与并行的批次。

---

## 一、把任务建成模型（系统工程第一步：定义系统边界与变量）

**任务 = 有向无环图（DAG） + 受限资源**

- **节点**：一个可独立验收的工作项（一条修复、一份摸底、一次迁移）。
- **边**：依赖（A 的产出是 B 的输入）。例：`P2 适配器 ← P1-7.1 编号缺口报告`。
- **节点属性**：`lead time`（从启动到可交付）、`改动面`（文件/模块）、`耦合度`（是否与其它节点共享文件/接口）、`验收成本`。

**资源（容量都是有限的，这是并行的真正约束）**

| 资源 | 容量 | 说明 |
|---|---|---|
| R1 主线注意力 | **1** | 我一次只能认真推进一件事；这是我视角下最强瓶颈 |
| R2 共享工作区写者 | **1** | 同一 worktree 多写者 ⇒ 不能提交、不能跑门禁 |
| R3 门禁 / CI | **1** | 全量门禁与 CI 是串行批处理资源 |
| R4 审查/整合带宽 | **1** | 合并前必须有人读懂 diff 并决定取舍 |

> **关键认识**：并行不会增加 R1/R3/R4 的容量。若无限制地多开 lane，只是把队列从
> 「我这边」搬到「等待我的审查」，**makespan 不变甚至变长**（Little 定律：`WIP = 吞吐 × 交付时间`，
> 吞吐被瓶颈锁住时，加 WIP 只拉长交付时间）。

---

## 二、四步排程程序

### 第 1 步：建图与标注
列出所有节点、依赖边、lead time、耦合点（共享文件）、验收方式。
**耦合点就是未来的冲突点**，标出来才能决定"能不能并行"。

### 第 2 步：算关键路径（CPM）
- **关键路径 = DAG 上最长路径**，它决定 makespan 的下界（再怎么并行也压不过它）。
- 关键路径上的节点：**主线独占、绝不排队、绝不空等**。
- 非关键路径节点有 **slack（浮动时间）**：可以晚启动、可以被抢占。

### 第 3 步：定 WIP 上限与启动时机
- **WIP 上限 = min(资源容量)**，不是"越多越好"。经验值：让最忙资源的利用率控制在 ≈80%，
  超过 ~85% 队列长度会非线性爆炸（Kingman 公式：等待时间 ∝ ρ/(1−ρ)）。
- **启动时机按 lead time 与耦合度分两类**：
  | 类型 | 特征 | 策略 |
  |---|---|---|
  | **前馈型**（long lead time、低耦合、后续要用） | 摸底/调研/长耗时验证 | **早启动**，让它在后台跑，主线继续 |
  | **即用型**（short lead time、高耦合、小改动） | 1~2 行修复、文档回写 | **JIT 串行**，临到需要时才做（过早做只会被后续改动返工） |

### 第 4 步：验证左移 + 整合点批处理
- **廉价检查左移**（shift-left）：单测、ruff、目标文件测试在节点内就跑，不拖到合并。
- **昂贵的全局检查批处理**（lean batch）：全量门禁、四件套、CI 只在**整合点**跑一次，
  避免"边写边跑"互相打红（本次实测：3 个 agent 同时改同一 worktree 时跑门禁 = 假失败）。
- **保护关键路径**：非关键任务**不得占用**关键路径资源；等价地：主线不在关键路径上空等。

## 三、映射到 git（隔离原语，不是"文件切分"）

```
main ──●──────────────●──────────────●────────→  （始终可构建/可发布）
        \            / \            /
         ●──●──●    /   ●──●──●    /             lane 分支（各自 CI 绿）
          (lane A)  /     (lane B) /
                    └─ 按拓扑序合并（依赖先合）
```

| 概念 | 对应 |
|---|---|
| 整合分支 | `main`，**任何时刻都必须可构建**；主线只接受已绿 lane |
| 并行隔离单元 | `feat/*` 分支 + `git worktree`（**写隔离**，消除 R2 冲突） |
| 整合单元 | PR；每个 PR 独立跑 CI，绿了才进入合并队列 |
| 合并顺序 | 依赖的**拓扑序**（被依赖的先合），不是按完成时间 |
| 门禁/CI | 每个 PR 一次 + 合并后 main 一次（批处理点） |

**反模式**：多个 lane 共享同一 worktree —— 触发 R2=1 的硬约束，导致
「谁都不能提交、门禁被半成品打红」。要么用 worktree 隔离，要么接受串行。

## 四、目标函数与观测指标

| 指标 | 定义 | 用途 |
|---|---|---|
| **Makespan** | 从开始到全部验收的总时长 | 主目标 |
| **Flow efficiency** | 增值工作时间 / makespan | 低说明在排队/等待 |
| **WIP** | 同时未完成的节点数 | 超过容量上限就要停 |
| **Rework rate** | 返工节点数 / 总节点数 | **历史最大成本项**（见 §六） |
| 队列等待 | 节点等待关键资源的时间 | 定位瓶颈 |

---

## 五、什么时候"不并行"是正确的

- 节点在**关键路径**上（并行也压不短）；
- **协调成本 ≥ 并行节省的时间**（典型：1~2 行修复，写 prompt 比自己做慢）；
- 会**占用同一资源**导致排队（同一文件、同一门禁窗口、同一审查人）；
- **验证成本高**且结果互相影响（改同一核心模块的多处解析逻辑，应串行改、一次验证）。

## 六、本项目的实测教训（这些错误都真实发生过）

| 错误 | 违反的模型约束 | 代价 |
|---|---|---|
| 串行做完 P0 才派 P1 摸底 | 前馈型任务 lead time 长，应早启动 | 摸底结果晚到，P2 排期推迟 |
| 3 个修复 agent 共享同一 worktree | R2=1（写者容量） | 门禁被半成品打红、无法提交、被迫等待 |
| 提交时才逐级撞门禁（G-055→G-031→README） | 未左移（shift-left） | 3 次提交失败返工 |
| `wait_agent` 空等子智能体 | 关键路径空等 | 主线停滞 |
| 无 WIP 上限地连续外派 | Little 定律 | 审查积压、整合成本升高 |
| "绝对并行"或"绝对串行" | 二元化，忽略容量与依赖 | 两种极端都劣化 makespan |

---

## 七、一页速查

```
1. 建图：节点/依赖/lead time/耦合点
2. 找关键路径：那条链主线独占、不排队、不空等
3. 限 WIP：上限 = 最紧资源容量；利用率别超 ~85%
4. 分类启动：前馈型（长 lead、低耦合）早启动；即用型（短 lead、高耦合）JIT 串行
5. 验证左移 + 整合点批量跑门禁
6. 用分支/worktree 做写隔离；main 始终可发布；按拓扑序合并
7. 算账：协调成本 ≥ 并行收益 → 立刻转串行
```
