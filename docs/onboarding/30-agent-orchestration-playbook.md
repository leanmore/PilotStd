# 30 · 多智能体调度 playbook（总用时最少原则）

> 来源：2026-11-24 单次会话实测（8 个子智能体、5 个批次）。**不是理论推演**，
> 每条都标注了本次踩到的真实浪费。
>
> 适用：主线 Agent 需要「自己控关键路径 + 外派可并行工作」时。

---

## 一、先分类：四象限

|  | 串行（有依赖链） | 并行（互不依赖） |
|---|---|---|
| **长线**（跨多轮/需连续决策） | **主线独占**：需求澄清、方案决策、PR 合并、部署与验收、门禁与 CI 收口、跨模块集成、文档回写 | 罕见（长线天然有依赖） |
| **短线**（可独立验证的一次性产出） | 主线自己做（依赖太多、派工成本 > 收益） | **外派子智能体**：补某目录单测、扫某类 TODO、核查某批台账、批量替换某组件 |

**判据（30 秒决定）**：

1. 这个产出**能不能被我自己 5 分钟独立验证**？不能 → 不派。
2. 它和别的工作**写不写同一个文件**？写同一个 → 不并行。
3. 我派出去的**描述成本**是否 ≥ 自己做的成本？是 → 不派（通常 < 100 行的活）。
4. 它是否在**关键路径上**？在 → 主线自己做，不要等。

---

## 二、总用时 = 关键路径，不是工作量总和

```
总用时 = 关键路径长度 + 返工时间
                     ↑ 返工是最大的隐形杀手
```

本次实测的返工：

| 浪费 | 原因 | 代价 |
|---|---|---|
| `test-gap-b` 派出去后要**重新压缩**（524 → 279 有效行） | 派工 prompt 里**没写 G-010 门禁** | 一轮往返 |
| `AppToast.test.ts` 我连写 2 版 | 凭猜测 import `ToastService`（正确是 `primevue/toastservice`） | 3 次试跑 |
| `test_final_gap_modules.py` 前 2 版断言失败 | 凭猜测 SQL 列名 / 函数签名 | 2 次试跑 |
| `test_gap_modules_backend.py` 曾让**全量门禁失败** | 子智能体跑的是「自己的单测」，我在它的文件未定稿时跑了 `check_all.sh` | 阻塞提交 |

**结论**：返工几乎全部来自「**没把约束前置**」和「**没先探针就写断言**」。

---

## 三、派工模板（六件套，缺一必返工）

每个子智能体 prompt 必须显式包含：

```
1. 【写范围】精确到文件路径，只准写这几个；禁止改生产代码/配置/其他测试
2. 【禁止动作】不要 git add / commit / push（主线统一提交）
3. 【门禁约束】有效代码行 ≤ 400（G-010 阻断档 500）；eslint 0 error；
   必须自己跑这两个检查并把输出贴回来
4. 【先探针后断言】先读源码 → 写临时脚本到 %TEMP% 验证实际行为 → 再写断言。
   禁止凭函数名/文档描述推测
5. 【口径冲突处理】若任务描述与源码不符，**以源码为准**，并在回报里明确指出
6. 【回报格式】每个文件几个用例/覆盖什么契约/实际输出/未能覆盖项及原因/有效行数
```

第 5 条尤其重要 —— 本次 `fe-utils` 正是靠它回报了我的 3 处错误假设
（`utils/cache.ts` 无 TTL/LRU、`taskPipeline.ts` 无状态机、`primevueLocale.ts` 无回退）。
**子智能体的反向纠错是额外收益，要主动索取。**

---

## 四、并行派工的硬约束

1. **写范围必须文件级不重叠**（本次 fe-api 5 个文件 / fe-utils 6 个 / fe-composables 5 个，零重叠）。
2. **不要在子智能体跑的时候跑全量门禁** —— 未定稿文件会被 G-010/ruff 判失败，
   白白阻塞主线的提交。等齐了再跑一次。
3. 子智能体**只跑自己文件的单测 + eslint**，全量四件套由主线在整合后跑。
4. 同批派 3 个是甜点；再多，主线的整合与审查会成为新瓶颈。

---

## 五、主线在等待期该做什么（这是「总用时最少」的核心）

外派后**不要 `sleep` / 不要空 `wait`**。立刻做**不依赖子智能体产出**的事：

| 本次等待期做的 | 价值 |
|---|---|
| 更新 PR 描述、写部署验收文档 | 收尾必需，且完全独立 |
| 写 `theme/config/AppToast` 测试 | 自己范围内的独立产出 |
| 跑真实部署自检、修 probe 端点错误 | 发现了 G-21 探测路径写错（真实缺陷） |
| 写批次 2 迁移授权 runbook | 推进下一批的前置 |

**反例**：本次有几次 `wait_agent(300s)` 空等 —— 应改为「派工后立刻转做主线活，
完成后再收集结果」。`job_output`/通知机制会自动把结果递回来。

## 六、串行链（必须主线亲自串）

本次的真实关键路径：

```
写测试/修复 → 四件套 + 门禁 → 提交 → 推送 → CI 全绿 → PR clean → 合并
                                                                    ↓
                                                        CI 构建镜像（仅 main 触发）
                                                                    ↓
                                                        部署端 pull + 重启
                                                                    ↓
                                                        probe_all + probe_batch1 验收
```

这条链上**任何一环都不能外派**，因为每一步的下一步都依赖上一步的**真实结果**
（不是预期结果）。尤其「合并后 CI 是否真的构建出镜像」必须自己看 GitHub Actions 的
`docker` job 结论 —— 本次正是靠这个才发现「分支改动不在镜像里」的关键结论。

---

## 七、反模式清单

| 反模式 | 后果 | 纠正 |
|---|---|---|
| 派工只写「给这 6 个模块写测试」 | 子智能体自由发挥 → 超行数/写错范围 | 用六件套模板 |
| 子智能体跑全量门禁 | 互相阻塞、假失败 | 只跑自己的单测 |
| 派工期间跑 `check_all.sh` | 未定稿文件导致门禁红 | 等齐再跑 |
| 空等子智能体 | 关键路径停滞 | 立刻做独立主线活 |
| 相信自己的任务描述 | 断言失败、返工 | 先探针 |
| 让子智能体 commit | 并发写 git 状态、格式破坏 | 主线统一提交 |
| 一个任务派给多个智能体 | 写冲突 | 文件级切分 |

---

## 八、一页速查

```
问：这件事派还是不派？
  能 5 分钟自己验完 → 自己做
  写同一个文件 → 自己做（或串行）
  在关键路径上 → 自己做
  < 100 行 → 自己做
  否则 → 派

问：派出去怎么写 prompt？
  六件套（范围/禁 commit/门禁/先探针/冲突以源码为准/回报格式）

问：派出去之后我干什么？
  立刻做不依赖它产出的事；不要空等

问：什么时候跑全量门禁？
  所有子智能体产出齐了、一次跑
```
