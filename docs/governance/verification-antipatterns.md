## V-1 用错口径即宣称通过

- **来源**：复核 G-038 执行能力时发现；回归由 `7835bd64`（第 2 批）引入，`e854f4cb` 修复。
- **现象**：多次在报告中写"ruff / mypy 通过"，实际跑的是 `python -m mypy pilotstd/ docker/`（**模块口径**），而门禁 `scripts/check_g_038_legacy_errors.py` 调用的是 `mypy` **可执行文件**且固定带 `--follow-imports=skip --ignore-missing-imports`。本机 PATH 上无该可执行文件 → **门禁从未真正执行**。
- **矛盾如何被发现**：审核指出"报告说 mypy 有 3 个存量错误，却又说全部门禁通过"——两者不能同时成立。
- **实测定位**：
  1. `Get-Command mypy` / 查 `Python314/Scripts` → 均为空，确认无独立可执行文件；
  2. `python scripts/check_g_038_legacy_errors.py` → 报"mypy 未安装"；
  3. 按门禁同参数手工复现 → **8 个错误**，全在 `docker/api/notification.py`；
  4. `git worktree add <tmp> 7835bd64~1` 后跑同口径 → `Success: no issues found` → **该组错误由 `7835bd64` 引入**。
- **修正**：标注改为真实类型（`mgr: StandardManager`、`cred_helper: CredentialHelper | None`、`masked_values: set[str]`）；门禁口径复现得 394 文件零错误。
- **判别性测试/命令**：
  ```bash
  # 判据：门禁本体（或其逐字同参命令），不是"等价"手工命令
  python scripts/check_g_038_legacy_errors.py     # 门禁本体
  python -m mypy pilotstd/ docker/ --follow-imports=skip --ignore-missing-imports  # 逐字同参
  ```
  无法执行时报告须写"**待 CI**"，不得写"通过"。

## V-2 清单不可复现

- **来源**：跨批次审计报告（**报告级**，无对应 commit）——两轮均写"广域回归（11 套件）"。
- **现象**：两轮报的数字为 598 与 509（当时报 530 / 504），但**未给套件清单**。读者无法复现，也无法判断差异来源。
- **矛盾如何被发现**：审核指出"同一批 11 套件应得出可比的交集计数，但按报告数字反推不成立（`530−191=339` 与 `504−107=397` 应有同一交集计数，实际不等）"。
- **实测定位**：以同一口径复算两轮套件：
  - 共有文件 **9** 个 → 两轮**均 397 例**（自洽）；
  - 仅首轮有的 7 文件 → 201 例；仅次轮有的 4 文件 → 112 例；
  - 故两轮**套件集不同**，总数不可比。报告中的"差额 84"与"93 ≈ 94"均为**算错的手工推导**。
- **修正**：报告改为给出**逐文件清单 + 程序化求和**，并确立"以 21 文件为唯一基准"的引用口径。
- **判别性测试/命令**：
  ```bash
  # 逐文件计数（程序求和，禁止手工），校验"清单求和 == 所引用的基准数"
  python -m pytest <套件清单> --collect-only -q | ... # 按文件分组求和
  ```
  判据：凡报"合计 N"必须同时给出可求和的清单；引用历史数字必须标注其套件集。

## V-3 修复未生效却宣称已修

- **来源**：`feffd990`（机制错误的首次修复）→ `d699d60f`（真正生效）。
- **现象**：声称"已修 `Scan Complete ({failed} unrecognized)` 的空值匹配"，但所述正则 `Scan\ Complete\((.+?)\ unrecognized\)` 要求 `Complete` 与 `(` 之间**无空格**，而渲染串是 `Complete (`（**有空格**）——该正则永不匹配。
- **矛盾如何被发现**：审核把"所述正则"与"所述渲染结果"并排比对，指出两者不能同时为真。
- **实测定位**：完整形 `fullmatch` 对原串为 `False`，实际命中靠**无关的"括号去掉"变体**绕过（机制错误、恰好给出正确结果）。根因两处：
  1. `re.split` 切出的前缀片段保留尾随空格，被 `strip` 掉；
  2. `_flexible_blank` 与 `_escape_with_placeholders` **叠加调用**致占位符二次转义。
- **修正**：`_escape_with_placeholders` 一次性完成——占位符 → `(.+?)`，**仅紧邻占位符的字面空白 → `\s*`**；删除折叠机制。
- **判别性测试/命令**：`tests/test_notification_aggregator_topic_i18n.py::test_scan_complete_empty_count_matches_via_full_pattern` —— **要求命中项含 `unrecognized` 字面量**，从而排除"靠括号去掉变体绕过"的假命中。旧实现下该用例 FAIL。

## V-5 验证工具过粗

- **来源**：L-06 性质分析（第 12 批）；相关提交 `c2c304e2`。**我先后三版检测器给出三个不同且全错的结论。**
- **现象**：为判定 e2e `EVENTS` 的 `level` 元数据是否漂移，三版检测器结论为"报 5 处漂移 → 报 5 处不可比对 → 报 3 处漂移"。实则 **39 事件零漂移**。
- **矛盾如何被发现**：审核要求逐条核对构建器源码；实读后发现 3 个被报"漂移"的构建器**都有 `info`/`warning` 双分支**，元数据完全正确。
- **实测定位**（三版失败史，每版给出失败原因，可直接复用）：

  | 版本 | 实现 | 失败原因 |
  |------|------|---------|
  | v1 | 正则 `level="(\w+)"` | **抓不到条件表达式**：`level="warning" if failed > 0 else "info"` 两端都是字面量，单字面量正则必漏 |
  | v2 | 正则 `level=([^,\n]+)` | **取值错位**：在 `NotificationMessage(` 内会先匹配到 `level` **之前**的参数（如 `event_type="..."`） |
  | v3 | AST `walk` 表达式内**所有** `str` 常量 | **把条件操作数当结果值**：`"warning" if "失败" in title else "info"` 中的 `"失败"` 被计为 level 取值 |
  | v4 | AST **语义遍历**：`IfExp` 只取 `body`/`orelse`，`Compare` 操作数不参与 | 39 事件零漂移（正确） |

  另一处同类失败（**独立案例，未并入上表**——它是「统计明细条目」而非「提取 level」）：

  | 版本 | 实现 | 失败原因 |
  |------|------|---------|
  | a1 | `re.findall(r"^    - ")` **整体扫描**文本块 | 把 `检查口径` 段的子项也计入明细条目数（报 `9 != 7`） |
  | a2 | `_section_items()` **只取目标段**的子项 | 条目数与豁免计数一致（正确） |

  两例同属"检测模式过粗"：**扫描范围大于语义范围**（a1 是文本范围 > 段落范围；
  v1-v3 是表达式范围 > 结果值范围）。

  **该反模式已两次在"核验环节"自伤**（a1 之外的第二例）：核验 V-7 实例表行数时，
  我以**整个 V-7 章节**为扫描域，把新增的"子类型定义表""三门禁输入性质表"的行一并计入，
  报出 `(a) 16 / (c) 8`（实际 12 / 3）。修正为**按表头字符串精确定位目标表**。
  两次自伤的形态完全一致——**用宽扫描替代按语义边界提取**（详见下方判别方式 ③）。

- **修正**：检测器改为语义遍历；**并为检测器本身加判别力自检**。
- **判别性测试/命令**：
  ```python
  # ① 检测器自检：对已知形态必须报出预期集合，不符即判"检测器无效"
  #    例：_build_scan_complete_message 必须报出 {"info","warning"}
  # ② 注入已知坏形态后必须 FAIL
  #    例：exemptions=[] -> 2 条 FAIL；_drop_trailing_blank 改恒等函数 -> 2 条 FAIL
  # ③ 扫描范围必须按语义边界显式限定（见下）
  ```
  **结论：检测器本身也需要判别力验证——"检测器报出的问题"在自检通过前不得当作代码缺陷。**

  **③ 扫描边界约束（本条特有，两次自伤后补入）**：扫描范围必须**按语义边界显式限定**
  （如按表头定位、按段落标记切分、按 AST 节点类型遍历），**不得依赖"全局扫描 + 后过滤"**——
  后者在文档/代码结构变化时会**静默扩大范围**。

  本反模式**已两次在核验环节自伤**：

  | 自伤实例 | 宽扫描 | 后过滤失效原因 | 正确做法 |
  |---------|-------|--------------|---------|
  | `re.findall(r"^    - ")` 统计明细条目 | 整个摘要文本块 | `检查口径` 段也用同一前缀，被一并计入（报 `9 != 7`） | 按段标题定位后只取其子项（`_section_items`） |
  | V-7 实例表行数核验 | 整个 V-7 章节的所有表格 | 新增的"子类型定义表""三门禁输入表"行被计入（报 `(a) 16 / (c) 8`） | 按表头字符串精确定位目标表 |

  **这与"用正则做 AST 工作"（v1-v3）是同一类问题**：都试图用"宽扫描 + 后过滤"替代
  "按语义边界精确提取"。共同根因可归纳为：**扫描范围必须等于语义范围**——
  放宽任一方向都会产生假命中（宽于语义）或漏检（窄于语义）。

  **边界说明（非本条）**：把扫描范围限定到语义边界**并不足以**防住所有误判——
  若**被测对象内部**携带了用于分类的字面量，即使扫描域正确也会歧义。该情形属
  **V-8（被测对象携带干扰验证的字面量）**，其修正位置在**对象内容**而非验证器。
  本条（V-5）只负责"扫描域过宽"，两类的失效方向相反，不可相互替代。

## V-6 把简化规则当稳定键（跨语言失效）

> 本条目曾用标题「跨语言/跨形态假设未验证」（`ecff27e0`），与 V-7「自我撤回」「提示词前提失准」
> 存在语义重叠（三者都含"假设未验证"）。`7512c3b4` 改名为「把简化规则当稳定键」以对齐
> **根因**（把不稳定的展示文本当成稳定键使用），并保留「跨语言失效」作为现象限定。
> 该条目的**技术内容与判别方式未变**。

- **来源**：`e163433c`（`_extract_topic` 改为 i18n 契约驱动）；缺陷自 `286bf124` 起长期存在。
- **现象**：`_extract_topic` 用**简体中文关键词**为通知标题推导分组键，只在少量简体标题上验证过。后果：繁体（`失敗` ≠ `失败`）与英文标题**全部落入"标题前 8 字符"兜底**，同一事件在不同语言下分入不同组。
- **矛盾如何被发现**：审核要求"用真实标题而非少数样例验证三语"。
- **实测定位**：以真实 `str.format` 渲染 39 事件 × 三语标题 → **65 条**落兜底。附带发现：用 `re.sub` 构造样本会产出渲染器**不会产出**的形态（如 `Scan Complete ()`），据此断言属无效验证。
- **修正**：改为 i18n 契约驱动（三语标题索引 134 条 + 9 条模板正则），索引跨三语构建。
- **判别性测试/命令**：`tests/test_notification_aggregator_topic_i18n.py`（53 例）——含"39 事件跨语言主题一致""无事件落兜底""判别力（旧实现 6/6 被污染）"；样本一律用 `str.format` 构造。

## V-7 未验证的结论写入报告

- **来源**：报告级，全程高频；典型实例见下表。
- **现象**：报告中出现**未经实测**的断言——既有对**提示词前提**的轻信，也有对**自己推理**的轻信。
- **矛盾如何被发现**：均由审核追问或后续实测推翻。
- **实测定位**（本会话实例。**仅举数例，非穷举**——抽样标准与无法穷举的原因见下）：

  **抽样标准**：按"该前提在仓库内有**可独立复核的痕迹**"抽样。凡提示词前提涉及仓库内可查对象
  （文件、接口名、事件、渲染行为）者优先收录，因其结论可用 `git` / 源码复核；纯流程类前提
  （如"本批范围应包含 X"）无法在仓库内留下痕迹，未收录。
  **无法穷举的客观原因**：原提示词文本**不在仓库中**（未被归档），本会话的早前回合已超出可见
  范围，故无法逐条回溯比对。**真正的穷举核验需要一份独立的提示词前提清单**——本仓库目前
  不存在该清单（见判别方式第 ③ 条的建议）。

  **(a) 对提示词前提轻信——12 处**

  (a) 内含四个**子类型**。判据分三个维度：**① 提示词所指对象是否为实际对象**；
  **② 所述处置对该对象是否仍有意义**；**③ 若有意义，是程度不符还是命名不符**。

  **注**：a-4 与 a-1/a-2/a-3 **失真来源不同**——前两者的判断主体都是**提示词自身**
  （对位置/状态/程度的判断错），而 **a-4 的根源是提示词所引用的上游文档过时，非提示词判断错**。
  因此 a-4 的修正动作是**改上游文档**，而非纠正提示词的理解。保留在 (a) 内的理由是：
  被采信的仍是"提示词提供的前提"（只是该前提抄自上游客过文档），其**失效机制**与 (a) 一致
  （未经核对即采信）。**若日后出现不依赖提示词的文档同步问题，应另立类别。**

  | 子类型 | 定义 | 判别方式 | 修正动作 | 本表内实例 |
  |--------|------|---------|---------|-----------|
  | **a-1 指错对象型** | 提示词**指错了位置**；所述处置对**实际对象也适用**（问题真实存在） | 核对提示词所指元素 vs 实际出问题的元素 | **改指对象** | 第 6 批（说 `header.title` 裸露，实际是 `table.header`——后者修复有效） |

## V-8 被测对象携带干扰验证的字面量

- **来源**：`87727ba8`（(a) 实例表 `security_login_failed` 行的脚注含 `a-2` 字面量，致该行按标签扫描时被误判为 a-2）。
- **现象**：表格中某行的**脚注**写了"故属 a-3 **非 a-2**"，导致按"行内是否含 `a-N` 标签"扫描时，该行同时含 `a-2` 与 `a-3`，分类归属出现 `a-2=3 / a-3=0`（实际应为 `a-2=2 / a-3=1`）。
- **矛盾如何被发现**：程序化归属核验的计数与预期不符（`a-3` 被吃掉一个），逐字符比对后定位到脚注字面量。
- **实测定位**：
  - **修复前**（脚注含 `a-2`）：该行 `re.findall(r"\ba-([1-4])\b", row)` 得 `['2','3']` → 归属歧义；
  - **修复后**（脚注改为"而非前提错型"）：归属 `a-1=1 / a-2=2 / a-3=1 / a-4=1 / 其他=7 = 12`，与预期一致。
  - **关键对照实验**：**按表头精确定位**（即 V-5 判别方式第 ③ 条要求的做法）后，扫描域已限于该表，**但歧义依旧存在**——因为冲突字面量位于**行内部**，而非扫描边界之外。
- **修正**：把脚注中的子类型编号字面量改写为自然语言（"程度描述不准而非前提错型"），使该行只含**一个**分类标签。
- **判别性测试/命令**：对每行统计其分类标签字面量个数，要求**恰为 1**：
  ```python
  # 约束：分类列之外的单元格不得出现该行自身的分类标签字面量
  tags = re.findall(r"\ba-([1-4])\b", row)
  assert len(set(tags)) == 1, f"行内标签歧义: {sorted(set(tags))}"
  ```
  更稳的形态（推荐）：把**机器可读标签**放进**独立的固定列**（如第 2 列），其余列允许自然语言——校验时只读该列，不全文扫描。

- **与 V-5 的方向差异**（决定二者必须分立）：

  | | V-5 验证工具过粗 | V-8 被测对象携带干扰字面量 |
  |---|---|---|
  | **缺陷主体** | **验证器** | **被测对象**（文档/表格/数据） |
  | **方向** | 扫描范围 **> 语义范围** | 扫描范围**正确**，但对象内有**非法字面量** |
  | **失效机制** | 把语义范围**外**的内容计入 | 语义范围**内**出现自指涉歧义 |
  | **修正位置** | **改验证器**（按语义边界限定） | **改对象内容**（或改为结构化列） |
  | **V-5 ③ 约束能否覆盖** | — | **不能**（实测：按表头定位后歧义仍在，冲突在行内） |

  故本条**不是 V-5 的变体**：V-5 的补救（限定扫描边界）对本条**无效**，二者根因与修正位置均不同。

## V-9 不可证伪的判据

- **来源**：L-01 实施批（S2 闸门测试设计）；审核建议 `captured["now"] == T0`，经实测识别为不可证伪。
- **现象**：为"证明某项契约成立"而写的断言，**在实现变坏时仍然通过**——即该断言无法区分
  "正确实现"与"注入的坏实现"。测试跑绿，但契约未被锁定（**假绿**）。
- **矛盾如何被发现**：设计 S2 闸门测试时，候补判据 `captured["now"] == T0` 看似直接
  （"闸门收到的 now 就是 login() 取的 T0"），但逐条推演"若实现改为在闸门内部另取
  `time.time()` 会怎样"时发现：**在 monkeypatch 时钟为常量 T0 的前提下，函数内另取同样返回 T0**
  → 断言仍通过 → 该判据对目标缺陷**不可证伪**。
- **实测定位**（本会话三例，含"审核建议被实测修正"的三次）：

  | # | 候补判据/建议 | 问题 | 改用 |
  |---|---|---|---|
  | 1 | 闸门用 `time.monotonic()` | 项目 4 处时间点**全为 `time.time()`**；混用会在系统时间跳变时形成**双时钟错位** | 复用 `login()` 的 `now`（同源，一致性由构造保证） |
  | 2 | `captured["now"] == T0` | mock 下**不可证伪**（另取时钟亦返回 T0） | 断言 `time.time` 调用次数（后进一步改基线差值） |
  | 3 | `clock_calls["n"] == 1` | 依赖"库内部不调用 `time.time()`"这一**不可穷举假设** | 基线差值 `lockout <= base`（相对断言）+ 纯函数黑盒（主判据） |

  本会话实施批中另有同类自伤：并发用例首版用"8 线程 + `setswitchinterval`"的概率构造，
  **注入"锁范围不足"时不稳定通过**（1 次 passed / 1 次 failed）→ 属不可靠判据；
  改为"首次读取后暂停 50ms"的窗口放大构造后可稳定捕获。

- **修正**：为每条"验证契约"的断言规定**可证伪性检验**——
  **把实现改成已知坏形态，这条断言会 FAIL 吗？若不会，它是假绿，必须改写。**
- **判别性测试/命令**：
  ```python
  # ① 对每条新断言做"注入坏形态"验证（本会话实测 5 例）：
  #    A 闸门恒不拦截 / B 闸门内另取时钟 / C 移除清理 / D 锁范围不足 / E 双次查询
  #    -> 每例对应断言必须 FAIL
  # ② 判据优先级：纯函数黑盒（不依赖 mock 时序）> 相对断言（基线差值）> 绝对计数
  #    > 依赖 mock 常量值的等值断言（最弱，最易不可证伪）
  ```
- **适用对象（含外部输入）**：本反模式不仅适用于自产断言，也适用于**来自审核/他人建议的
  判据**。建议、结论、断言三者都应先做**可证伪性检验**，再采信或执行。
- **与 V-7 的分工**：V-7 约束"结论是否经实测"；V-9 约束"判据本身能否证伪"。
  一条结论可以通过实测（满足 V-7）却仍建立在不可证伪的判据上（违反 V-9）。

## 收录标准与完整清单

**收录标准（三条全满足）**：

1. **已实测确认**——附具体实测输出或可复现命令，非推测；
2. **可判别**——能给出"自动检查"或"明确人工判据"的判别方式（纯口号不收）；
3. **本项目实际发生**——有具体实例（commit 或报告级出处）。

**判别方式的三种可执行层级**（由强到弱）：

| 层级 | 形态 | 例 |
|------|------|---|
| 自动检查 | 已有判别性测试，回归即 FAIL | V-3 / V-4 / V-5（注入坏形态）/ V-6 |
| 命令判据 | 可复跑命令 + 期望输出 | V-1（门禁本体或其逐字同参命令） |
| 清单判据 | 必须提供可求和/可复核的清单 | V-2（逐文件计数）、V-7（`文件:行号` + 实测输出） |
