# 验证反模式集（本项目实测确认）

> 用途：记录**在本项目实际发生并被实测确证**的验证失误模式，供交付前自审与下一批设计参考。
> 收录标准：只收录已由本项目实测确认的反模式，每条附**可复现的判别方式**。
> 不收录未经本项目实证的通用工程建议——那会使本文档失去"可复现"这一唯一价值。

统一记录格式：**现象 → 矛盾如何被发现 → 实测定位 → 修正 → 判别性测试**。

## V-1 用错口径即宣称通过

- **现象**：多次在报告中写"ruff / mypy 通过"，实际跑的是 `python -m mypy pilotstd/ docker/`（**模块口径**），而门禁 `scripts/check_g_038_legacy_errors.py` 调用的是 `mypy` **可执行文件**且带 `--follow-imports=skip --ignore-missing-imports`。本机 PATH 上无该可执行文件，故**门禁从未真正执行**。
- **矛盾如何被发现**：审核指出"报告说 mypy 有 3 个存量错误，却又说全部门禁通过"——两者不能同时成立。
- **实测定位**：`Get-Command mypy` 为空；`python scripts/check_g_038_legacy_errors.py` 报"mypy 未安装"。按门禁口径手工复现后得 **8 个错误**，全在 `docker/api/notification.py`；`git worktree` 检出该文件改动**之前**的提交跑同口径得 `Success: no issues found` → **该组错误由我引入**。
- **修正**：类型标注改为真实类型（`mgr: StandardManager`、`cred_helper: CredentialHelper | None`）；门禁口径复现得 394 文件零错误。
- **判别性测试/命令**：以**门禁本体**或其**逐字同参**命令判定，不得用等价的手工命令代替；无法执行时须标注"待 CI"，不得写"通过"。

## V-2 清单不可复现

- **现象**：两轮报告都写"广域回归（11 套件）"，数字分别为 598 与 509（当时报 530 / 504），但**未给套件清单**。读者无法复现，也无法判断差异来源。
- **矛盾如何被发现**：审核指出"同一批 11 套件应得出可比的交集计数，但按报告数字反推不成立"。
- **实测定位**：以同一口径复算两轮套件：共有文件 9 个在**两轮均 397 例**（自洽），但仅首轮有的 7 个文件贡献 201 例、仅次轮有的 4 个文件贡献 112 例 → 两轮**套件集不同**，故总数不可比。此前报告中的"差额 84"与"93 ≈ 94"均为**算错的手工推导**。
- **修正**：报告改为给出**逐文件清单 + 程序化求和**，并确立"以 21 文件为唯一基准"的引用口径。
- **判别性测试/命令**：`pytest <清单> --collect-only -q` 后**程序求和**（非手工），且校验"清单求和 == 所引用的基准数"。

## V-3 修复未生效却宣称已修

- **现象**：声称"已修 `Scan Complete ({failed} unrecognized)` 的空值匹配"，但所述正则 `Scan\ Complete\((.+?)\ unrecognized\)` 要求 `Complete` 与 `(` 之间**无空格**，而渲染串是 `Complete (`（**有空格**）——该正则永不匹配。
- **矛盾如何被发现**：审核把"所述正则"与"所述渲染结果"并排比对，指出两者不能同时为真。
- **实测定位**：完整形 `fullmatch` 对原串为 `False`，实际命中靠**无关的"括号去掉"变体**绕过（机制错误、恰好给出正确结果）。根因两处：① `re.split` 切出的前缀片段保留尾随空格被 `strip` 掉；② `_flexible_blank` 与 `_escape_with_placeholders` **叠加调用**致占位符二次转义。
- **修正**：`_escape_with_placeholders` 一次性完成——占位符 → `(.+?)`，**仅紧邻占位符的字面空白 → `\s*`**；删除折叠机制。
- **判别性测试/命令**：`test_scan_complete_empty_count_matches_via_full_pattern` —— **要求命中项含 `unrecognized` 字面量**，从而排除"靠括号去掉变体绕过"的假命中。

## V-4 抽象过早导致信息丢失

- **现象**：实现门禁覆盖摘要时把"豁免"抽象为纯计数（`exempted: int`），于是 G-044/G-045 只显示"豁免 26 / 豁免 38"而**不列名单**；G-043 因恰好传了明细而正常。
- **矛盾如何被发现**：审核追问"G-044 的 16 键 + 10 词、G-045 的 38 项也是豁免计数 > 0，为何无明细段？"——暴露"省略空段"的解释不成立。
- **实测定位**：三处数据源**都是可枚举名单**（`exempt_keys` 16 个具体键路径、`exempt_terms` 10 个具体术语词、`tracked` 38 个具体事件），是我传了 `exemptions=[]`。
- **修正**：改为传递实际名单；新增 `exemptions_label` 按语义区分段标题（G-045 用"跟踪项明细"）、`max_item_len` 控制截断；同时移除 `main()` 中"只显示前 5 项 + 另 33 项"的截断块。
- **判别性测试/命令**：`test_exempt_detail_lists_actual_items` —— 断言三处**均有**明细段且**条目数 == 检查项行的豁免计数**。注入 `exemptions=[]` 后该用例 FAIL。

## V-5 验证工具过粗

- **现象**：为判定 e2e `EVENTS` 的 `level` 元数据是否漂移，我先后写了三版检测器，给出三个不同结论：报 5 处漂移 → 报 5 处"不可比对" → 报 3 处漂移。**三个结论都是假的。**
- **矛盾如何被发现**：审核要求逐条核对构建器源码；实读后发现 3 个被报"漂移"的构建器**都有 `info`/`warning` 双分支**，元数据完全正确。
- **实测定位**：三版检测器各有缺陷——① 正则 `level="(\w+)"` 抓不到 `level="a" if cond else "b"`；② `re.findall(r"^    - ")` 整体扫描会把其它段的子项计入；③ AST `walk` 表达式内**所有**字符串常量会把条件里的比较串（如 `"失败" in title`）也算作结果值。改用**语义遍历**（`IfExp` 只取 `body`/`orelse`）后得 39 事件**零漂移**。
- **修正**：检测器改为语义遍历；**并为检测器本身加判别力自检**（见下）。
- **判别性测试/命令**：① 自检——已知 5 个构建器必须报出预期集合，不符即判"检测器无效"；② 注入已知坏形态（如 `exemptions=[]`、`_drop_trailing_blank` 改恒等函数）后必须 FAIL。**检测器本身也需要判别力验证。**

## V-6 跨语言/跨形态假设未验证

- **现象**：`_extract_topic` 用简体中文关键词为通知标题推导分组键，只在少量简体标题上验证过，因而漏掉：繁体（`失敗` ≠ `失败`）与英文标题**全部落入"标题前 8 字符"兜底**，同一事件在不同语言下分入不同组。
- **矛盾如何被发现**：审核要求"用真实标题而非少数样例验证三语"。
- **实测定位**：以真实 `str.format` 渲染 39 事件的三语标题，**65 条**落兜底；且用 `re.sub` 构造样本会产出渲染器**不会产出**的形态，据此断言属无效验证。
- **修正**：改为 i18n 契约驱动（三语标题索引 + 模板正则），标题索引跨三语构建。
- **判别性测试/命令**：`tests/test_notification_aggregator_topic_i18n.py`（53 例）——含"39 事件跨语言主题一致""无兜底""判别力（旧实现 6/6 被污染）"；样本一律用 `str.format` 构造。
