## V-1 用错口径即宣称通过

- **来源**：复核 G-038 执行能力时发现；回归由 `7835bd64`（第 2 批）引入，`e854f4cb` 修复。
- **现象**：多次在报告中写"ruff / mypy 通过"，实际跑的是 `python -m mypy pilotstd/ docker/`（**模块口径**），而门禁 `scripts/check_g_038_legacy_errors.py` 调用的是 `mypy` **可执行文件**且固定带 `--follow-imports=skip --ignore-missing-imports`。本机 PATH 上无该可执行文件 → **门禁从未真正执行**。
- **矛盾如何被发现**：审核指出"报告说 mypy 有 3 个存量错误，却又说全部门禁通过"——两者不能同时成立。
- **实测定位**：
  1. `Get-Command mypy` / 查 `Python314/Scripts` → 均为空，确认无独立可执行文件；
  2. `python scripts/check_g_038_legacy_errors.py` → 报"mypy 未安装"；
  3. 按门禁同参数手工复现 → **8 个错误**，全在 `docker/api/notification.py`；
  4. `git worktree add <tmp> 7835bd64~1` 后跑同口径 → `Success: no issues found` → **该组错误由 `7835bd64` 引入**。
- **修正**：标注改为真实类型（`mgr: StandardManager`、`cred_helper: CredentialHelper | None`、`masked_values: set[str]`）；门禁口径复现得 394 文件零错误。
- **判别性测试/命令**：
  ```bash
  # 判据：门禁本体（或其逐字同参命令），不是"等价"手工命令
  python scripts/check_g_038_legacy_errors.py     # 门禁本体
  python -m mypy pilotstd/ docker/ --follow-imports=skip --ignore-missing-imports  # 逐字同参
  ```
  无法执行时报告须写"**待 CI**"，不得写"通过"。

## V-2 清单不可复现

- **来源**：跨批次审计报告（**报告级**，无对应 commit）——两轮均写"广域回归（11 套件）"。
- **现象**：两轮报的数字为 598 与 509（当时报 530 / 504），但**未给套件清单**。读者无法复现，也无法判断差异来源。
- **矛盾如何被发现**：审核指出"同一批 11 套件应得出可比的交集计数，但按报告数字反推不成立（`530−191=339` 与 `504−107=397` 应有同一交集计数，实际不等）"。
- **实测定位**：以同一口径复算两轮套件：
  - 共有文件 **9** 个 → 两轮**均 397 例**（自洽）；
  - 仅首轮有的 7 文件 → 201 例；仅次轮有的 4 文件 → 112 例；
  - 故两轮**套件集不同**，总数不可比。报告中的"差额 84"与"93 ≈ 94"均为**算错的手工推导**。
- **修正**：报告改为给出**逐文件清单 + 程序化求和**，并确立"以 21 文件为唯一基准"的引用口径。
- **判别性测试/命令**：
  ```bash
  # 逐文件计数（程序求和，禁止手工），校验"清单求和 == 所引用的基准数"
  python -m pytest <套件清单> --collect-only -q | ... # 按文件分组求和
  ```
  判据：凡报"合计 N"必须同时给出可求和的清单；引用历史数字必须标注其套件集。

## V-3 修复未生效却宣称已修

- **来源**：`feffd990`（机制错误的首次修复）→ `d699d60f`（真正生效）。
- **现象**：声称"已修 `Scan Complete ({failed} unrecognized)` 的空值匹配"，但所述正则 `Scan\ Complete\((.+?)\ unrecognized\)` 要求 `Complete` 与 `(` 之间**无空格**，而渲染串是 `Complete (`（**有空格**）——该正则永不匹配。
- **矛盾如何被发现**：审核把"所述正则"与"所述渲染结果"并排比对，指出两者不能同时为真。
- **实测定位**：完整形 `fullmatch` 对原串为 `False`，实际命中靠**无关的"括号去掉"变体**绕过（机制错误、恰好给出正确结果）。根因两处：
  1. `re.split` 切出的前缀片段保留尾随空格，被 `strip` 掉；
  2. `_flexible_blank` 与 `_escape_with_placeholders` **叠加调用**致占位符二次转义。
- **修正**：`_escape_with_placeholders` 一次性完成——占位符 → `(.+?)`，**仅紧邻占位符的字面空白 → `\s*`**；删除折叠机制。
- **判别性测试/命令**：`tests/test_notification_aggregator_topic_i18n.py::test_scan_complete_empty_count_matches_via_full_pattern` —— **要求命中项含 `unrecognized` 字面量**，从而排除"靠括号去掉变体绕过"的假命中。旧实现下该用例 FAIL。

## V-4 抽象过早导致信息丢失

- **来源**：`c2c304e2`（覆盖摘要首版只给计数）→ `714889e0`（改为逐条名单）。
- **现象**：实现门禁覆盖摘要时把"豁免"抽象为纯计数（`exempted: int`），于是 G-044/G-045 只显示"豁免 26 / 豁免 38"而**不列名单**；G-043 因恰好传了明细而正常。
- **矛盾如何被发现**：审核追问"G-044 的 16 键 + 10 词、G-045 的 38 项也是豁免计数 > 0，为何无明细段？"——暴露我"省略空段"的解释不成立。
- **实测定位**：三处数据源**都是可枚举名单**（`exempt_keys` 16 个具体键路径、`exempt_terms` 10 个具体术语词、`tracked` 38 个具体事件），是我传了 `exemptions=[]`。
- **修正**：改为传递实际名单；新增 `exemptions_label` 按语义区分段标题（G-045 用"跟踪项明细"）、`max_item_len` 控制截断；同时移除 `main()` 中"只显示前 5 项 + 另 33 项"的截断块。
- **判别性测试/命令**：`tests/test_gate_coverage_summary.py::test_exempt_detail_lists_actual_items` —— 断言三处**均有**明细段，且**明细条目数 == 检查项行的豁免计数**（名单与计数一致）。注入 `exemptions=[]` 后该用例 FAIL（实测 2 条）。

## V-5 验证工具过粗

- **来源**：L-06 性质分析（第 12 批）；相关提交 `c2c304e2`。**我先后三版检测器给出三个不同且全错的结论。**
- **现象**：为判定 e2e `EVENTS` 的 `level` 元数据是否漂移，三版检测器结论为"报 5 处漂移 → 报 5 处不可比对 → 报 3 处漂移"。实则 **39 事件零漂移**。
- **矛盾如何被发现**：审核要求逐条核对构建器源码；实读后发现 3 个被报"漂移"的构建器**都有 `info`/`warning` 双分支**，元数据完全正确。
- **实测定位**（三版失败史，每版给出失败原因，可直接复用）：

  | 版本 | 实现 | 失败原因 |
  |------|------|---------|
  | v1 | 正则 `level="(\w+)"` | **抓不到条件表达式**：`level="warning" if failed > 0 else "info"` 两端都是字面量，单字面量正则必漏 |
  | v2 | 正则 `level=([^,\n]+)` | **取值错位**：在 `NotificationMessage(` 内会先匹配到 `level` **之前**的参数（如 `event_type="..."`） |
  | v3 | AST `walk` 表达式内**所有** `str` 常量 | **把条件操作数当结果值**：`"warning" if "失败" in title else "info"` 中的 `"失败"` 被计为 level 取值 |
  | v4 | AST **语义遍历**：`IfExp` 只取 `body`/`orelse`，`Compare` 操作数不参与 | 39 事件零漂移（正确） |

  另一处同类失败：用 `re.findall(r"^    - ")` **整体扫描**文本块统计明细条目，把 `检查口径` 段的子项也计入（报 `9 != 7`）——修正为只取目标段的子项（`_section_items`）。

- **修正**：检测器改为语义遍历；**并为检测器本身加判别力自检**。
- **判别性测试/命令**：
  ```python
  # ① 检测器自检：对已知形态必须报出预期集合，不符即判"检测器无效"
  #    例：_build_scan_complete_message 必须报出 {"info","warning"}
  # ② 注入已知坏形态后必须 FAIL
  #    例：exemptions=[] -> 2 条 FAIL；_drop_trailing_blank 改恒等函数 -> 2 条 FAIL
  ```
  **结论：检测器本身也需要判别力验证——"检测器报出的问题"在自检通过前不得当作代码缺陷。**

## V-6 把简化规则当稳定键

- **来源**：`e163433c`（`_extract_topic` 改为 i18n 契约驱动）；缺陷自 `286bf124` 起长期存在。
- **现象**：`_extract_topic` 用**简体中文关键词**为通知标题推导分组键，只在少量简体标题上验证过。后果：繁体（`失敗` ≠ `失败`）与英文标题**全部落入"标题前 8 字符"兜底**，同一事件在不同语言下分入不同组。
- **矛盾如何被发现**：审核要求"用真实标题而非少数样例验证三语"。
- **实测定位**：以真实 `str.format` 渲染 39 事件 × 三语标题 → **65 条**落兜底。附带发现：用 `re.sub` 构造样本会产出渲染器**不会产出**的形态（如 `Scan Complete ()`），据此断言属无效验证。
- **修正**：改为 i18n 契约驱动（三语标题索引 134 条 + 9 条模板正则），索引跨三语构建。
- **判别性测试/命令**：`tests/test_notification_aggregator_topic_i18n.py`（53 例）——含"39 事件跨语言主题一致""无事件落兜底""判别力（旧实现 6/6 被污染）"；样本一律用 `str.format` 构造。

## 收录标准与完整清单

**收录标准（三条全满足）**：

1. **已实测确认**——附具体实测输出或可复现命令，非推测；
2. **可判别**——能给出"自动检查"或"明确人工判据"的判别方式（纯口号不收）；
3. **本项目实际发生**——有具体实例（commit 或报告级出处）。

**判别方式的三种可执行层级**（由强到弱）：

| 层级 | 形态 | 例 |
|------|------|---|
| 自动检查 | 已有判别性测试，回归即 FAIL | V-3 / V-4 / V-5（注入坏形态）/ V-6 |
| 命令判据 | 可复跑命令 + 期望输出 | V-1（门禁本体或其逐字同参命令） |
| 清单判据 | 必须提供可求和/可复核的清单 | V-2（逐文件计数）、V-7（`文件:行号` + 实测输出） |
