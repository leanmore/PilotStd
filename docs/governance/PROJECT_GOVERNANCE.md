## 一、治理体系概览

PilotStd 项目治理由三份核心文档构成，形成联动闭环：

| 文档 | 职责 | 路径 |
|------|------|------|
| **能力登记簿** | 列出所有非功能性能力，每条标注守护它的门禁 | `docs/governance/capabilities_registry.md` |
| **门禁索引** | 列出所有门禁（已归档至历史快照） | `docs/archive/2026-06-30/GATE_INDEX.md` |
| **架构报告** | 定义四层架构 + 三端定位，约束能力和门禁的放置位置 | `docs/architecture_layers.md` |

**联动关系**：

```
能力登记簿 ←——— 守护 ———→ 门禁索引
      ↑                      ↑
      |                      |
      +—— 放置位置约束 ———————→ 架构报告
```

**核心原则**：

1. **能力必须有门禁守护**：任何非功能性能力（后台线程、观测日志、缓存、通知等）必须在能力登记簿中登记，并有至少一道门禁守护。
2. **门禁必须守护能力**：任何门禁必须至少守护一项能力，否则该门禁无存在价值。
3. **分层约束能力放置**：能力必须放在符合四层架构定义的层次中，门禁也必须在对应的层次中执行。
4. **三端共享**：通用能力必须在共享层实现，端侧只做交互适配。

## 二、治理流程

### 2.1 新增能力

```
识别新能力 → 在能力登记簿中登记
                ↓
判断能力放置层次 → 参考架构报告
                ↓
设计守护门禁 → 新增或复用现有 GATE
                ↓
更新门禁索引 → 建立能力与门禁的关联
                ↓
代码实现 → 在正确的分层中实现
                ↓
验证 → 运行门禁确认守护生效
```

### 2.2 新增门禁

```
识别需要守护的能力 → 查能力登记簿
                ↓
设计门禁脚本 → 放入 scripts/check_gate_XX.py
                ↓
注册门禁 → 更新 .pre-commit-config.yaml
                ↓
更新门禁索引 → 记录门禁与能力的关联
                ↓
验证 → 确认门禁能正确检测违规
```

### 2.3 重构/迁移

```
查询能力登记簿 → 确认涉及哪些能力
                ↓
查询门禁索引 → 确认哪些门禁守护这些能力
                ↓
运行 extract_capabilities.sh → 提取当前能力快照
                ↓
执行重构 → 迁移代码到新位置
                ↓
运行门禁 → 确认所有守护能力未丢失
                ↓
更新能力登记簿 → 记录能力的新位置
```
