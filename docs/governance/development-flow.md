# PilotStd 开发流程规范

本流程为强制执行规范。每个阶段的所有步骤必须依次完成，禁止跳过。

## 阶段一：问题发现与分析

| 步骤 | 角色 | 动作 |
|------|------|------|
| 1.1 问题触发 | 决策者 | 发现问题，告知参谋 |
| 1.2 信息收集 | 参谋 | 澄清操作、现象、日志、复现条件 |
| 1.3 根因定位 | 参谋→执行者 | 发出调查指令，执行者提供证据，参谋确认根因 |

## 阶段二：方案制定

| 步骤 | 角色 | 动作 |
|------|------|------|
| 2.1 方案设计 | 参谋 | 基于根因出方案，含修复逻辑、影响范围、门禁适配 |
| 2.2 数据影响评估 | 参谋 | 必须确认：是否影响存量数据？是否需要洗库脚本？ |
| 2.3 方案审核 | 决策者 | 确认方案，可要求修正 |
| 2.4 指令转化 | 参谋 | 转化为结构化执行指令（操作范围、门禁、验证闭环、禁止事项） |

## 阶段三：代码实现

| 步骤 | 角色 | 动作 |
|------|------|------|
| 3.1 改代码 | 执行者 | 按指令修改代码、编写测试 |
| 3.2 本地门禁预检 | 执行者 | 运行 `scripts/check_all.sh`，确保零错误。未通过则禁止继续 |
| 3.3 自审报告 | 执行者 | 逐项确认指令要求已满足 |
| 3.4 交付 | 执行者 | 提交代码 + 交付报告 |

## 阶段四：审核

| 步骤 | 角色 | 动作 |
|------|------|------|
| 4.1 交付审核 | 参谋 | 逐项核对文件、测试、门禁、自审报告 |
| 4.2 不通过 | 参谋 | 指出缺失项，直接退回 |
| 4.3 通过 | 参谋 | 确认交付物与指令一致 |

## 阶段五：CI 与部署

| 步骤 | 角色 | 动作 |
|------|------|------|
| 5.1 CI 运行 | 自动化 | push 触发全量测试 + 门禁扫描 |
| 5.2 CI 通过 | 自动化 | 触发部署 → 调用 `/api/health` → ok 通知 / degraded 告警 |
| 5.3 CI 失败 | 执行者 | 必须先写归因分析（含"如何防止同类问题再次发生"），再修代码。禁止跳过归因 |
| 5.4 修复 | 执行者 | 基于归因分析修改代码，重新走 3.2→3.4 |

## 阶段六：线上验证

| 步骤 | 角色 | 动作 |
|------|------|------|
| 6.1 健康检查 | 自动化 | `/api/health` 返回 ok → 流程结束 |
| 6.2 功能验证 | 决策者 | 手动验证原始问题是否解决 |

## CI 失败归因要求

归因分析必须包含以下四项，缺一不可：
1. 失败的具体测试/检查项
2. 根因分析（代码逻辑错误 / 测试未覆盖 / 门禁未拦住）
3. 修复思路
4. 如何防止同类问题再次发生（补测试 / 加门禁 / 改范式）
