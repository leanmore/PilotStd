## 测试设计原则

### 冷/热启动策略

PilotStd 压测覆盖系统生命周期的两端——首次启动（冷启）与长期运行后（热启），确保两种真实用户场景均得到验证。

**CLI 端 — 冷启动压测**

CLI 每次执行为独立进程（`python -m pilotstd.cli.commands`），启动时初始化 `LoggerManager`、`ConfigManager`、`StandardManager`（含 DB 连接 + 适配器加载），完成后进程退出。这与真实用户从终端执行命令的行为完全一致。

验证重点：
- 首次启动时的初始化性能（DB 连接、配置加载、适配器注册）
- 冷缓存下的查询效率（`standard_info_cache` / `announcement_cache` 均为空）
- 缓存填充开销（查询结果写入缓存、file_index 写入）

**WinUI 端 — 热启动压测**

WinUI 为常驻进程，用户长期运行。压测时 GUI 已启动、用户已登录、DB 连接和适配器已初始化完毕。这与真实用户"打开软件后反复使用"的行为一致。

验证重点：
- 稳态下的并发处理能力（8-worker 线程池复用）
- 缓存命中效果（复用 CLI 冷启写入的 `standard_info_cache` + Docker 填充的 `announcement_cache`）
- 资源管理表现（内存不泄漏、线程不堆积、QTimer 不漂移）
- 跨线程信号完整性（AutoWorker signal → UI slot 不丢失）

**互补关系**

| 维度 | CLI 冷启 | WinUI 热启 |
|------|---------|-----------|
| 进程生命周期 | 短命（执行完退出） | 长命（常驻） |
| 缓存状态 | 空（冷缓存） | 热（复用前步缓存） |
| 初始化开销 | 计入测试耗时 | 已摊销 |
| 模拟用户 | 首次使用 / 脚本调用 | 日常反复使用 |
| 验证侧重 | 冷启动性能 + 缓存填充 | 稳态并发 + 资源管理 |

两者互为补充，覆盖系统生命周期两端，确保压测结果对真实用户场景有实际参考价值。

## 1. 执行流程

```
stress_driver.py（总入口）
  ├── 启动前：rotator_state 清理（冷却状态重置）
  ├── 第一步前置检查：Python/源目录/网络/复位/清DB/selfcheck → 见各阶段 _step1_precheck()
  ├── 第一步：CLI 冷启（1.1 scan → 1.2 query → 1.3 download → 1.4 normalize
  │            → 1.5 organize → 1.6 expire → 1.7 announce → 1.7.1 cache_lookup → 1.8 task → 1.9 recheck）
  │     └── --stop-after=cli 可强制退出；否则 --yes 模式且 org_moved=0 自动继续
  ├── 第二步前置检查：Docker 可达/凭证/版本/Token/inbox/auto_announce → _step2_precheck()
  ├── 第二步：Docker Web API 验证（先于 WinUI 执行，填充 announcement_cache 供缓存命中验证）
  ├── 第三步前置检查：DB 非空/announce_sample.json/web_api_url → _step3_precheck()
  ├── 第三步：WinUI 热启交叉对比（甲轮本地回归 + 乙轮 Web 缓存验证）
  └── 第四步：汇总判定（流程状态 + 逐桶指标 + 适配器统计 + 凭证状态）
```

> 步骤顺序 CLI→Docker→WinUI。Docker 先行填充 announcement_cache，供 WinUI 乙轮验证缓存命中。

### 用法

```bash
# 完整压测
python tests/stress_driver.py --source D:\标准 --output E:\标准 --config tests/test_config.json --yes

# 只执行第一步（CLI 冷启），完成后退出
python tests/stress_driver.py --source D:\标准 --output E:\标准 --config tests/test_config.json --yes --stop-after=cli

# 跳过 CLI，从已有 step1.json 继续
python tests/stress_driver.py --source D:\标准 --output E:\标准 --config tests/test_config.json --yes --skip-cli --step1 <step1.json路径> --keep-db
```

### 核心参数

| 参数 | 作用 |
|------|------|
| `--source` / `--output` | 源目录和输出目录 |
| `--config` | JSON 配置文件路径（含 Docker/OCR/`web_api.url`） |
| `--yes` | 无人值守模式，跳过所有交互确认 |
| `--keep-db` | 跳过清 DB |
| `--skip-cli` / `--skip-winui` / `--skip-docker` | 跳过对应步骤 |
| `--stop-after cli` | CLI 后强制退出 |
| `--winui-only` | 仅执行 WinUI，需 `--step1` |
| `--step1` | step1.json 路径 |
| `--result-dir` | 统一输出目录 |
| `--timeout-query` | 查询超时（默认 3600s） |
| `--timeout-auto` | WinUI 超时（默认 1800s） |
| `--db-path` | 数据库路径 |

## 2. CLI 步骤失败处理决策表

| 步骤 | 失败条件 | 处理方式 | 原因 |
|------|---------|---------|------|
| 1.1 scan | 扫描文件数=0 或 rc≠0 | **终止** | 无有效数据 |
| 1.2 query | 成功率<10% 且 成功数<50 或 rc≠0 | **终止** | 数据不足 |
| 1.3 download | 任意下载失败 | 继续 | 不影响验证 |
| 1.4 normalize | rc≠0 | **终止** | 无法验证去重 |
| 1.5 organize | rc≠0 | **终止** | file_index 缺失 |
| 1.6 expire | rc≠0 | 继续 | 不影响核心 |
| 1.7 announce | rc≠0 | 继续 | 不影响核心 |
| 1.8 task | rc≠0 | 继续 | 不影响核心 |
| 1.9 recheck | 1.1~1.8 任一失败 | **跳过** | 数据不完整 |

## 3. 流程状态定义

| 状态 | 含义 |
|------|------|
| **FULL_PASS** | 1.1~1.9 全部通过 |
| **TERMINATED_EARLY ({step})** | scan/query/normalize/organize 失败 |
| **PARTIAL_FAIL** | 仅非关键步骤失败 |
| **SKIPPED** | 用户 --skip-* 跳过 |
