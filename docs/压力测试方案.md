## 测试设计原则

### 冷/热启动策略

PilotStd 压测覆盖系统生命周期的两端——首次启动（冷启）与长期运行后（热启），确保两种真实用户场景均得到验证。

**CLI 端 — 冷启动压测**

CLI 每次执行为独立进程（`python -m pilotstd.cli.commands`），启动时初始化 `LoggerManager`、`ConfigManager`、`StandardManager`（含 DB 连接 + 适配器加载），完成后进程退出。这与真实用户从终端执行命令的行为完全一致。

验证重点：
- 首次启动时的初始化性能（DB 连接、配置加载、适配器注册）
- 冷缓存下的查询效率（`standard_info_cache` / `announcement_cache` 均为空）
- 缓存填充开销（查询结果写入缓存、file_index 写入）

**WinUI 端 — 热启动压测**

WinUI 为常驻进程，用户长期运行。压测时 GUI 已启动、用户已登录、DB 连接和适配器已初始化完毕。这与真实用户"打开软件后反复使用"的行为一致。

验证重点：
- 稳态下的并发处理能力（8-worker 线程池复用）
- 缓存命中效果（复用 CLI 冷启写入的 `standard_info_cache` + Docker 填充的 `announcement_cache`）
- 资源管理表现（内存不泄漏、线程不堆积、QTimer 不漂移）
- 跨线程信号完整性（AutoWorker signal → UI slot 不丢失）

**互补关系**

| 维度 | CLI 冷启 | WinUI 热启 |
|------|---------|-----------|
| 进程生命周期 | 短命（执行完退出） | 长命（常驻） |
| 缓存状态 | 空（冷缓存） | 热（复用前步缓存） |
| 初始化开销 | 计入测试耗时 | 已摊销 |
| 模拟用户 | 首次使用 / 脚本调用 | 日常反复使用 |
| 验证侧重 | 冷启动性能 + 缓存填充 | 稳态并发 + 资源管理 |

两者互为补充，覆盖系统生命周期两端，确保压测结果对真实用户场景有实际参考价值。

### 分步执行原则

**每步执行前必须完成前置检查，确认通过后再继续，不走一键处理模式。** 三步串行：CLI → Docker → WinUI。各步之间边界清晰：

- CLI 做查询 → 生成数据库 → WinUI 甲轮复用验证本地缓存命中
- Docker 做公告抓取 → 生成 `announce_sample.json`（从 `announcement_fetch_log` 抽样，无论匹配结果） → WinUI 乙轮验证公告数据可检索率
- Docker→本机缓存传递链路：`POST /api/announcements/fetch`（异步抓取）→ `announcement_fetch_log`（写入）→ 抽样生成 `announce_sample.json` → WinUI 乙轮读取并逐条查询 `/api/announce/lookup`

## 1. 执行流程

```
stress_runner.py（总入口）
  ├── CLI 阶段前置检查 → run_cli_phase()（stress_cli.py）
  │     ├── 环境自检（Python/源目录/网络/DB清理/selfcheck）
  │     └── CLI 冷启动执行（scan→query→download→organize→announce→...）
  │     └── 生成缓存基线报告（scripts/check_cache_baseline.py）
  │           → tests/.cache/baseline/cache_baseline_{timestamp}.json
  │
  ├── Docker 阶段前置检查 → run_docker_phase()（stress_docker.py）
  │     ├── 输入/输出目录文件清单检查 → stress_docker_precheck.log
  │     ├── /api/health 可达 / Token 有效 / inbox 21 文件
  │     └── tasks.auto_announce_enabled=false
  │
  ├── Docker/Web 执行
  │     ├── POST /api/announcements/fetch → 验证 task_id + GET status/{task_id}（仅验证状态可查，不等待完成）
  │     ├── 46 端点验证（≥42 PASS）
  │     ├── 生成 announce_sample.json（从 announcement_fetch_log 抽样）
  │     └── 端到端管线验证
  │
  ├── WinUI 阶段前置检查 → run_winui_phase()（stress_winui.py）
  │     ├── 甲轮前置：缓存一致性核对
  │     │   ├── 读取最新基线报告（tests/.cache/baseline/cache_baseline_*.json）
  │     │   ├── 对比 standard_info_cache 当前状态与基线报告
  │     │   └── 一致 → 继续；不一致 → 终止测试并输出差异报告
  │     ├── 甲轮执行：本地缓存交叉对比（scan_count/query_exact 偏差 ≤10%）
  │     ├── 乙轮前置：announce_sample.json 存在且有效（从 announcement_fetch_log 抽样）
  │     └── 乙轮执行：公告数据可检索率验证（可检索率 ≥90%）
  │
  ├── WinUI 热启动执行（甲轮→配置切换→乙轮）
  │     ├── 甲轮：use_announcement_cache=false → 本地抓取回归
  │     └── 乙轮：use_announcement_cache=true → /api/announce/lookup 公告数据可检索率
  │
  └── 汇总判定 → verdict.json + report.md
```

> 步骤顺序 CLI→Docker→WinUI。Docker 先行填充 announcement_cache，供 WinUI 乙轮验证缓存命中。

### 用法

```bash
# ============================================================
# 方案 A：同机完整流程（CLI + Docker + WinUI 在同一台机器）
# ============================================================
python tests/stress_runner.py --source D:/标准 --output E:/标准 --config tests/test_config.json --result-dir tests/.cache/stress --yes

# 跳过 CLI，复用已有 step1.json
# 前提：CLI 已在当前执行机上完成，step1.json 存在于本地路径
# 用途：调试场景（仅修改了 Docker/WinUI 代码，CLI 结果仍有效）
python tests/stress_runner.py --skip-cli --step1 path/to/step1.json --config tests/test_config.json --result-dir tests/.cache/stress --yes

# ============================================================
# 方案 B：跨机部署（CLI/WinUI 在机器 A，Docker 在机器 B）
# ============================================================
# 机器 A：CLI 阶段
python tests/stress_cli.py --source D:/标准 --output E:/标准 --config tests/test_config.json --result-dir tests/.cache/stress --yes

# 机器 B（或能访问机器 B 的机器）：Docker 阶段（独立运行，无需 step1.json）
python tests/stress_docker.py --config tests/test_config.json --result-dir tests/.cache/stress --yes

# 机器 A：WinUI 阶段
python tests/stress_winui.py --config tests/test_config.json --result-dir tests/.cache/stress --yes
```

**`--skip-cli --step1` 使用前提：**
- CLI 阶段已在**当前执行机**上完成，且 `step1.json` 存在于本地路径
- 用途：调试场景（仅修改了 Docker/WinUI 代码，CLI 结果仍有效）
- 跨机场景不适用：Docker 在另一台机器时，Docker 阶段用 `stress_docker.py` 独立运行，无需 step1.json

| 参数 | 作用 |

## 跨机部署说明

实际部署环境中，CLI/WinUI 与 Docker 可能不在同一台机器上：

| 组件 | 机器 | 说明 |
|------|------|------|
| CLI | 机器 A（本地） | 执行扫描/查询/归档 |

| Docker | 机器 B（局域网） | `http://192.168.1.18:9028` |

**跨机场景执行方式：**

| 阶段 | 执行命令 | 数据依赖 |
|------|---------|----------|
| CLI | `stress_cli.py --source ... --output ...`（机器 A） | 无 |
| Docker | `stress_docker.py --config ...`（机器 B 或能访问机器 B 的机器） | 仅需 Docker 容器运行 + inbox 文件 |

- Docker 阶段 **不需要** step1.json，独立运行

- WinUI 乙轮通过 `web_api_url` 配置指向远程 Docker
- 各阶段结果通过 `verdict.json` 汇总，无需文件传递

## 缓存基线报告机制

### 设计目的

CLI 冷启结束后，`standard_info_cache` 表应被冻结——WinUI 甲轮只读不写，确保缓存环境未被污染。通过生成基线报告并校验，可发现 CLI 结束后到 WinUI 启动前的任何意外变更。

### 存储位置

`tests/.cache/baseline/cache_baseline_{timestamp}.json`，目录自动创建。

### 报告内容

```json
{
  "table": "standard_info_cache",
  "total": 547,
  "sources": {"njbz365": 198, "ahbz": 165, "std_gov": 130, "hbba": 43, "csres": 6, "iso_gov": 3, "dbba": 2},
  "records": [
    {"id": 1, "standard_number": "GB/T 1-2020", "source_site": "njbz365", "cached_at": "2026-06-24T13:17:49", "source": "network"}
  ],
  "time_range": {"earliest": "2026-06-24T13:17:49", "latest": "2026-06-24T13:29:48"},
  "hash": "md5_of_all_records",
  "generated_at": "2026-06-24T14:00:00"
}
```

### 一致性校验标准

| 维度 | 校验方式 | 失败判定 |
|------|---------|---------|
| 总记录数 | `baseline.total == current.total` | 数量不一致 |
| 来源分布 | 按 `source_site` 分组计数逐一比对 | 任一站点的记录数不同 |
| 逐条匹配 | 按 `id` 匹配，比对 `standard_number`、`source_site`、`cached_at`、`source` | 有新增/删除/修改的记录 |

### 校验失败行为

终止 WinUI 甲轮测试，输出差异报告（JSON 格式），列出新增、删除、修改的记录明细。

### 差异报告示例

```json
{
  "baseline": {"table": "standard_info_cache", "total": 547, "hash": "abc123"},
  "current": {"table": "standard_info_cache", "total": 550, "hash": "def456"},
  "diff": {
    "added": [
      {"standard_number": "GB/T 9999-2025", "source_site": "ahbz"}
    ],
    "removed": [],
    "modified": [
      {"id": 42, "field": "source_site", "old": "njbz365", "new": "hbba"}
    ],
    "summary": "新增 3 条, 删除 0 条, 修改 1 条 — 缓存环境污染，终止测试"
  }
}
```

### 脚本清单

| 脚本 | 用途 | 调用时机 |
|------|------|---------|
| `scripts/check_cache_baseline.py` | 生成基线报告 | CLI 结束后自动调用 |
| `scripts/check_cache_consistency.py` | 对比当前表与基线报告 | WinUI 甲轮前调用 |

- ❌ FAIL：触发接口返回非 200，或 status 接口不可达
- 不因任务未在指定时间内完成而判定为 FAIL

#### 公告抓取不设超时原因

Docker 阶段公告抓取验证**不设置超时限制**，原因：

1. **异步任务的设计意图是"触发即返回"**：`POST /api/announcements/fetch` 返回 `task_id` 后即视为触发成功，后台任务独立执行，不应由测试代码阻塞等待
2. **外部公告平台响应时间不可控**：取决于公告平台方（如 std.samr.gov.cn）的响应速度，设超时会导致测试误判
3. **测试验证范围限定**：
   - ✅ 验证 `POST /api/announcements/fetch` 返回有效的 `task_id`
   - ✅ 验证 `GET /api/announcements/status/{task_id}` 返回有效状态
   - ❌ 不验证任务是否在指定时间内完成
4. **完成状态由 WinUI 乙轮间接验证**：公告抓取完成后数据写入 `announcement_cache`，WinUI 乙轮通过 Web API 查询验证命中；缓存为空时相应验证自动标记为 N/A

**结论：** 测试代码不等待公告抓取完成，仅验证触发和状态查询。

### 审查标准

| 原则 | 检查要点 | 判定标准 |
|------|---------|---------|
| **真实性** | 并发数/间隔/顺序模拟真实用户行为 | 并发数 ≤ 实际使用场景上限（单机 ≤ 8 worker） |
| **可重复性** | 多次运行结果可复现，外部依赖可固化 | 有固化数据源（源目录文件固定），外部 API 失败不阻断 |
| **可观测性** | 关键指标可监控和记录 | 每场景有日志输出/断言采集点，判定结果可追溯 |
| **非破坏性** | 使用隔离环境，有数据回滚/清理 | 使用独立输出目录，清五表可恢复，不操作生产数据 |

## 附录 A.2：压测报告输出格式

`stress_driver.py` 在 `--result-dir` 下输出以下文件：

| 文件 | 内容 |
|------|------|
| `step1.json` | CLI 冷启结果（checkpoints + summary） |
| `step2.json` | WinUI 热启结果（rounds + verdict） |
| `step3.json` | Docker Web API 结果（extended 指标） |
| `verdict.json` | 汇总判定（verdict + steps + ts） |
| `report.md` | 人类可读的 Markdown 报告 |

### verdict.json（扩展字段）

```json
{
  "verdict": "PASS",
  "steps": ["流程状态: FULL_PASS", "第一步 CLI 冷启: PASS", "…"],
  "ts": "2026-06-23T14:30:00",
  "meta": {
    "timestamp": "2026-06-23T14:30:00",
    "version": "v9.4",
    "source_dir": "D:\\标准",
    "output_dir": "E:\\标准",
    "result_dir": "tests/.cache/stress_20260623_143000",
    "source_file_count": 2488,
    "duration_seconds": 7200
  },
  "summary": {
    "overall_verdict": "PASS",
    "voting": {
      "cli": "PASS",
      "docker": "PASS",
      "winui": "PASS"
    },
    "blocker_failures": []
  }
}
```

> `meta`/`summary.voting`/`summary.blocker_failures` 为 v9.0 新增字段，与现有 `verdict`/`steps`/`ts` 兼容共存。

### report.md 模板

```markdown
# PilotStd 全量压力测试报告

## 测试元信息
| 项目 | 值 |
|------|-----|
| 测试时间 | {timestamp} |
| 方案版本 | v9.4 |
| 源目录 | {source_dir} ({source_file_count} 文件) |
| 输出目录 | {output_dir} |
| 结果目录 | {result_dir} |
| 总耗时 | {duration_seconds} 秒 |

## 各阶段判定
### CLI 冷启 — {cli_verdict}
| 步骤 | 状态 | 关键指标 |
|------|------|---------|
| scan | {scan_status} | {scan_count} 文件入索 |
| query | {query_status} | 成功率 {query_success_rate}% |

| organize | {organize_status} | {organize_moved} 归档, 索引 {file_index_count} |

### Docker Web API — {docker_verdict}
| 检查项 | 状态 | 关键指标 |
|--------|------|---------|

### WinUI 热启 — {winui_verdict}
| 轮次 | 状态 | 关键指标 |
|------|------|---------|
| 甲轮（本地） | {round_a_status} | 公告 {announce_count} 条, 按钮启用 {button_enabled} |

**总体判定：{overall_verdict}**
```

### 兼容性说明

- `--step1` 导入机制仅读取 `step1.json` 的 `checkpoints`/`summary` 字段，新增的顶层 `meta` 字段不影响现有解析
- `verdict.json` 的 `meta`/`summary` 为附加字段，`verdict`/`steps`/`ts` 保持不变
- `report.md` 为新增文件，不影响任何现有逻辑
