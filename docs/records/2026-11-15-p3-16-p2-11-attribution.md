## 一、P3-16：604 条 `chain_exhausted` 归因

### 1. 日志证据（11-13 批量）

| 项 | 数值 |
|---|---|
| `[NG]` 总行 | **604**（全部来自 `_OVERF`），与 pending 604 一致 |

| `[LO]` 行 | **160**，全部来自 `_MINI_`，形态一律是 `[LO]<site>(=0)`（**match_status 为空串**） |
| 冷却跳过 / 临时冷却跳过 | **0 / 0** |
| 配额耗尽 / 溢出查询失败 | **0 / 0**（`溢出查询失败` 关键字 0 命中） |
| `[QUOTA]` 用量 | ahbz 50、csres 4、cssn 80、dbba 3、energy 2、gongbiaoku 50、hbba 50、jjg 3、mee 2、njbz365 20、std_gov 100 |

路由日志（同一批量）：
- `[v2 Router] 代号=SH/T 路由=(空)`（HG/T、NB/T、JB/T、AQ/T、ASME… 同类）
- `[v2 Router] 代号=GB/T 路由=csres`（配额耗尽过程中只剩 csres 有余额）
- `[v2 Router] 代号=NB 路由=energy`、`代号=HJ 路由=mee`（单站链）

### 2. 本地探针（证明"配额耗尽 → 空链"）

同一能力模型下：

```
fresh quota:   GB/T 3324-2017 -> ['std_gov','csres','cssn']
               SH/T 3126-2013 -> ['gongbiaoku','hbba','ahbz','njbz365']
耗尽全部站点后: 所有查询 -> []
```

### 3. 根因（三条，按影响排序）

1. **单次运行配额耗尽 → 空链**（445 条）：v2 `QuotaManager` 把 `constraints.batch_limit`
   当**本次运行总配额**，按每次请求扣减；825 批量把 21 站配额耗尽后，`route()` 三层都返回空链。
   溢出入口 `start = 1 if chain and chain[0] == _bucket_key(...)`——而 `_bucket_key` 就是
   `chain[0]`，所以非空链**永远跳过主站**；空链则一个站点都不试，直接 `[NG] tried=none`，
   并统一记成 `chain_exhausted`。
2. **"未找到"哨兵被当成 0 分结果**（160 条 `[LO]`）：`BaseAdapter.query_with_strategy`
   在完全无候选时返回 `QueryResult(standard_number=target, error_message="未找到匹配结果")`，
   `match_status` 默认空串；执行层只判 `if result:` → 记 `[LO](=0) 未达100分回池`。
   实际语义是"该站没搜到"，应记 `no_result`，不是"低分"。
3. **单站链无重试**（159 条 NG 的第二站尝试全部失败）：链长 1 时溢出无站点；
   链长 ≥2 时溢出只试 `chain[1:]`，主站失败后不重试。

### 4. 结论：改哪里

- **不是"补源"问题**：站点都真实回应了（0 条 `溢出查询失败`、无超时告警）。
- **不是"策略"问题为主**：LO 的 0 分是"未找到"哨兵，不是评分策略打低分。
- **要改路由/配额语义 + 溢出语义 + LO 判定**（代码）：
  a. 执行层把 `not result.is_found()` 判为 `no_result`（NG），不计 LO；
  b. 空链时区分 `quota_exhausted`（本次配额耗尽，留待下批）与 `no_result`（确实无源），
     不再统一标 `chain_exhausted`；
  c. `start=1` 只在"主站确实尝试过"时启用（用 tried 集合判定）；单站链是否允许同站重试需产品决定成本/收益。

## 二、P2-11：`file_index` 的 TSG 行为什么是 0

### 1. 证据

| 项 | 线上（11-15） | 11-09 备份（`pre_migration_v75_to_v76.bak`） |
|---|---|---|
| `file_index` 总行 | **204** | **820** |
| `TSG%` 行 | **0** | **34**（如 `/standards/TSG 特种设备安全技术规范/TSG 8001-2019 ….pdf`） |
| `standards` | 1534 | 1533 |
| `notification_log` | 2278 | 2054 |

关键日志（`app.log.9`）：

```
2026-11-11 21:41:42 [I] log.FILE_I file_index 启动校验完成（延迟 5.0s），清理 820 条失效记录
```

之后 11-13 21:56、22:34 与 11-15 08:52 的三次启动均为"清理 0 条"。

### 2. 根因

**`file_index` 启动校验按"容器内路径是否存在"删除记录；2026-11-11 21:41 启动时
`/standards` 挂载未就绪（或指向空目录），820 条全部判失效并被一次性删除。**
不是 TSG 从未归档（备份证明存在过 34 条）、不是清理任务、不是迁移（v56/v61/v74 均不删行）。
删除后 11-13 批量归档又写入 204 条，形成当前 204 的状态。

### 3. 影响与处置

- **P2-11 不能自动 merge**：脚本的判据是 `file_index` 唯一 `logical_code`，证据已被删，
  线上复算为 **0 merge / 7 manual**（11-09 备份上才是 5/2）。
- 恢复选项（需要产品/数据决定，未执行）：
  a. 从 11-09 备份恢复 `file_index`（820 行）→ 再跑 dry-run（生产写，需窗口）；
  b. 重新扫描宿主 `standards/` 重建索引（生产写 + 文件系统读）；
  c. 7 条按人工裁定（canonical 在 `standard_validity` 已存在，但缺文件证据）。
- **已修**：`validate_paths` 增加批量删除保护（缺失 ≥90% 且总行数 ≥50 → 跳过删除 + WARNING），
  防同类事故重演；见 `pilotstd/core/file_index.py` 与 `tests/test_file_index_validation_guard.py`。

现存类别（`/standards` 根 14 项）：GB/T 87、GB 32、SH/T 13、NB/T 11、SY/T 2 等；整类缺失：TSG、HG/T 55、JB/T 22、HG 12、API 9、T/SG 7、YB/T 6…

**结论：文件大面积不在**（≈19% 在，TSG 目录整体不存在）。按 2026-11-15 裁定进入"商量 a"：
- 不能直接用 11-09 备份覆盖：会丢 11-13 之后写入的 204 条，且 666 条指向已不存在文件；
- 新发现的约束：即使恢复备份，下次启动校验会按"缺失 666/820=81% < 90% 阈值"删除 666 条（保护只拦 ≥90%），所以"整表恢复"不可持久；
- 可行路径（需授权/数据决策）：① 用 11-09 备份**离线**跑 repair 脚本生成 5/2 计划，再把结论作为一次性数据修复（不恢复整表）；② 只把 TSG 等需要的元数据导入临时副本复算；③ 若宿主另有旧库目录未挂载，挂载后重扫重建（b）。
