### 2. 本地探针（证明"配额耗尽 → 空链"）

同一能力模型下：

```
fresh quota:   GB/T 3324-2017 -> ['std_gov','csres','cssn']
               SH/T 3126-2013 -> ['gongbiaoku','hbba','ahbz','njbz365']
耗尽全部站点后: 所有查询 -> []
```

### 3. 根因（三条，按影响排序）

1. **单次运行配额耗尽 → 空链**（445 条）：v2 `QuotaManager` 把 `constraints.batch_limit`
   当**本次运行总配额**，按每次请求扣减；825 批量把 21 站配额耗尽后，`route()` 三层都返回空链。
   溢出入口 `start = 1 if chain and chain[0] == _bucket_key(...)`——而 `_bucket_key` 就是
   `chain[0]`，所以非空链**永远跳过主站**；空链则一个站点都不试，直接 `[NG] tried=none`，
   并统一记成 `chain_exhausted`。
2. **"未找到"哨兵被当成 0 分结果**（160 条 `[LO]`）：`BaseAdapter.query_with_strategy`
   在完全无候选时返回 `QueryResult(standard_number=target, error_message="未找到匹配结果")`，
   `match_status` 默认空串；执行层只判 `if result:` → 记 `[LO](=0) 未达100分回池`。
   实际语义是"该站没搜到"，应记 `no_result`，不是"低分"。
3. **单站链无重试**（159 条 NG 的第二站尝试全部失败）：链长 1 时溢出无站点；
   链长 ≥2 时溢出只试 `chain[1:]`，主站失败后不重试。

### 4. 结论：改哪里

- **不是"补源"问题**：站点都真实回应了（0 条 `溢出查询失败`、无超时告警）。
- **不是"策略"问题为主**：LO 的 0 分是"未找到"哨兵，不是评分策略打低分。
- **要改路由/配额语义 + 溢出语义 + LO 判定**（代码）：
  a. 执行层把 `not result.is_found()` 判为 `no_result`（NG），不计 LO；
  b. 空链时区分 `quota_exhausted`（本次配额耗尽，留待下批）与 `no_result`（确实无源），
     不再统一标 `chain_exhausted`；
  c. `start=1` 只在"主站确实尝试过"时启用（用 tried 集合判定）；单站链是否允许同站重试需产品决定成本/收益。

### 3. 33 份 TSG 未触发：最可能的新目录监听缺口（高置信推断）

- 事实 A：12:29 启动补扫 `跳过 605`（若 TSG 已在，应为 638）⇒ TSG 目录/文件在 **12:29 之后**才出现。
- 事实 B：13:10 启动补扫 `跳过 572`（=605−33）⇒ 它们存在但 mtime ≤ watermark（12:29），被跳过。
- 事实 C：12:29~13:05 monitor 运行中，`检测到新文件` **0 命中**。
- 事实 D：19:02/19:06 的 572 个文件放在**已存在**的目录（GB/AQ/SH 等）→ 事件正常触发。
- 推断：watchdog 的 recursive 监听在启动时只对**当时已存在**的目录建 watch；新子目录依赖
  “目录创建事件”补 watch。本次 TSG 是**新建目录**（12:29 之后创建），目录创建事件未送达容器
  ⇒ 新目录及其文件从未被监听；而 572 个文件写入的是已 watch 的旧目录 ⇒ 正常触发。
- 结论/规则（当前部署）：
  - 文件放进**启动时已存在**的目录 → 实时事件可用；
  - 文件放进**启动后新建的目录** → 实时事件不可靠，需 `docker compose restart` 走补扫；
  - 62 批若要实时：先创建好 62 个目录并 restart 一次（让新目录被 watch），再投放文件；
    否则直接“投放 + restart”走补扫。
- 未证实项：无法在容器内查 `max_user_watches`；但 572 事件正常，watch 数量上限解释不了
  “仅新目录静默”，故按“新目录未建 watch”处理。
