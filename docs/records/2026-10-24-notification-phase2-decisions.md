# 通知二期裁决记录（2026-10-24）

> **性质**：决策记录（历史层）。18 项裁决由项目负责人逐项确认，作为 S2~S4 的实施依据。
> **来源**：`docs/plans/notification-system-design/00-framework.md` §七（11 项）、`02-framework-update.md` §五（5 项）、`07-impl-design-A.md`（N6/N7）。
> **规则**：实施中如发现裁决不可行，回到本文件改判并记原因，不在代码里静默偏离。

## 一、裁决表

| ID | 事项 | 裁决 | 影响 |
|---|---|---|---|
| Q1 | 3 个"多余事件"（首登记 / 规范化完成 / 下载开始） | **保留但不默认订阅** | 不改事件清单，只改默认订阅 |
| Q2 | 5 个"重复事件" | **保留、订阅层只留其一** | 禁止合并（会破坏 e2e `trigger_file` 契约） |
| Q3 | 缺失的"待确认"时刻 | **增强 `batch_query_summary` 文案**（含数量 + 入口） | 不新增事件，省掉 9 步准入 |
| Q4 | 聚合键 | **二元**（`notify_event × target_id`） | `correlation_id` 恒空，三元会退化 |
| Q5 | 阶段 3 范围 | **只做 URL 按钮 + 降级文本** | 4 渠道均拿不到消息 ID，双向交互不做 |
| Q6 | `_enabled` 语义 | **记录始终开、投递可关** | 关闭通知后 Web 端仍能看到历史 |
| Q7 | Windows 端 15 个共享事件 | **按端分流（Windows→托盘）** | 不切断调用，保留审计 |
| Q8 | CLI 文档冲突 | **只改帮助文档** | 不动打包入口 |
| Q9 | 是否新增"声明 vs 实现"门禁 | **新增独立门禁** | 需分配新编号（避开 G-048~G-050） |
| Q10 | 是否引入"用户时刻清单"第二 SSOT | **是**，门禁做双向闭包 | 与 41 事件 + 7 类并存 |
| Q11 | `/api/auto` 是否加管道级时刻 | **新增**（以 `02-framework-update.md` #4 为准，覆盖 00 的"暂维持"） | 分档策略的"终局档"落点 |
| N1 | 警告档与静默时段冲突 | **警告绕过静默** | 静默期只压普通/低优先 |
| N2 | 终局汇总能否改写前一条进度消息 | **明确不做**：终局另发一条，不原地改写 | 与"进度不做原地更新"一致；渠道编辑能力不再作为前置 |
| N3 | 分档阈值是否先补埋点 | **先补耗时埋点再用真实分布定稿** | S2 前置：桌面操作 / 定时任务耗时 |
| N4 | 企业级形态凭证迁移 | **平滑双读** | 旧形态凭证继续可用 |
| N5 | 企微/飞书证据缺口是否阻塞 | **不阻塞**，先做已取证渠道（TG/钉钉） | 企微/飞书能力补齐推迟 |
| N6 | 4 处硬编码英文标签 | **保持字面量** | 不为这 4 处扩 i18n |
| N7 | 新门禁误报期策略 | **接受缓阻断**（先警告一个迭代） | 限本阶段内 |

## 二、两处需要特别记住的

1. **N2 是"明确不做"**，不是"按渠道能力决定"——任何"改写上一条消息"的设计都视为越界。
2. **Q11 与 00-framework 的 Q11 相反**：以本文为准（新增管道级时刻），`02-framework-update.md` 是后一版。
